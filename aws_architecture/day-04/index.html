Private Subnet with Outbound Access

The database server must stay unreachable from the internet, but it still needs to download updates. A NAT Gateway gives it a one-way door: connections can start from inside, never from outside.

The diagram

Full picture: the database sends its request to the NAT Gateway in the public subnet, because the private route table says 0.0.0.0/0 → nat. The NAT Gateway forwards it through the Internet Gateway using its own Elastic IP. Replies come back the same way, but nobody outside can open a connection to the database.

Concepts

NAT Gateway

NAT means Network Address Translation. Many private instances share one public address to reach the internet.

  • Outbound only. It forwards replies to connections started from inside and drops everything else.
  • Managed by AWS: no patching, scales by itself.
  • It lives in one AZ. If that AZ fails, so does the NAT Gateway (fixed on Day 6).

Why it sits in the public subnet

This is the most common mistake in drawings. The NAT Gateway serves the private subnet but lives in the public one.

  • It needs its own way out, and only the public subnet has a route to the Internet Gateway.
  • It needs an Elastic IP, the fixed public address the internet sees.
  • Placed in a private subnet, it would have no path to the internet at all.

Private route table

The private subnet gets its own route table with a default route to the NAT Gateway.

  • 10.0.0.0/16 → local for traffic inside the VPC.
  • 0.0.0.0/0 → nat for everything else.
  • The subnet is still private: its route points to a NAT Gateway, not to an Internet Gateway.

Cost

Unlike the Internet Gateway, a NAT Gateway is not free.

  • You pay per hour it exists plus per GB it processes, roughly 30–40 US dollars a month before any data.
  • Delete it after practising in a real account, and release the Elastic IP too.
  • Traffic to S3 or DynamoDB can skip the NAT Gateway through VPC endpoints (Day 24).

Check yourself

Why does the NAT Gateway sit in the public subnet?

It needs a route to the Internet Gateway and a public address of its own. Only a public subnet provides the route. In a private subnet it would be as cut off as the instances it is meant to serve.

An external server receives a request from the database. Which source IP does it see?

The NAT Gateway's Elastic IP, 13.126.5.80. It never sees 10.0.2.10. This is useful when a partner needs to allow-list your address.

Can someone on the internet SSH into the database using the NAT Gateway's Elastic IP?

No. The NAT Gateway only passes replies to connections that were started from inside. An unsolicited incoming packet matches no connection and is dropped.

You point the private route table at the Internet Gateway instead of the NAT Gateway. The database has no public IP. Does it get internet access?

No. The Internet Gateway only works for instances that have a public IP. And if you did add one, the database would become reachable from outside, which is exactly what you wanted to avoid.

Does the web server use the NAT Gateway when it downloads updates?

No. It is in the public subnet and has its own public IP, so its traffic goes straight to the Internet Gateway.

Is the private subnet now a public subnet, since it can reach the internet?

No. A subnet is public only if its route table points to an Internet Gateway. This one points to a NAT Gateway.

The AZ holding the NAT Gateway fails. Private subnets in other AZs route through it. What happens?

They lose internet access. A NAT Gateway lives in one AZ, so the usual design is one NAT Gateway per AZ, each used by the private subnets of its own AZ. You draw that on Day 6.

You finished practising and deleted the NAT Gateway. Are you still paying for anything?

Yes, if you forgot the Elastic IP. AWS charges for public IPv4 addresses, so release it as well.
