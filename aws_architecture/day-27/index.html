Data Pipeline

A busy shop produces a million clicks an hour. No single click matters much, but together they show what sells, where people give up and which payments look like fraud. A data pipeline carries each event from the moment it happens to a chart that someone reads. Today you draw one, and you mark the point where the data stops moving and comes to rest.

The diagram

Full picture: events leave the producers and flow through a Kinesis data stream. Two consumers read it: Lambda reacts within a second, and Firehose collects records into files. In the top band the data is moving; in the bottom band it is at rest in the S3 data lake. Glue cleans it and catalogues it, Athena runs SQL on it and QuickSight draws the charts. Arrows show where the data goes. Solid arrows flow continuously or on request; dashed arrows run in batches.

Concepts

  

    

      
Kinesis Data Streams

      
    
        
  • A stream is made of shards. Each shard takes in up to 1 MB or 1,000 records a second. For more, add shards, or use on-demand mode and let AWS add them.
    • 
        
  • Every record carries a partition key. The same key always lands on the same shard, and order is kept within a shard.
    • 
        
  • Records stay for 24 hours by default, up to 365 days. Reading does not remove them, unlike SQS on Day 16.
    • 
        
  • So several consumers can read the same data, and one that failed can go back and replay.
    • 
      

    

    

      
Amazon Data Firehose

      
    
        
  • A delivery service: it takes records in and writes them to S3, Redshift or OpenSearch. No shards to size and no consumer code to write.
    • 
        
  • It buffers by size and by time, so it is near real time, not real time.
    • 
        
  • On the way it can compress, convert JSON to Parquet, or pass each record through a Lambda function.
    • 
        
  • It keeps nothing to re-read. Once delivered, the data is only at the destination.
    • 
        
  • Called Kinesis Data Firehose until 2024; you will see both names.
    • 
      

    

    

      
S3 data lake and Glue

      
    
        
  • A data lake is all your data as files in S3, in open formats. Storage is separate from whatever queries it, so many tools can share the same files.
    • 
        
  • Keep zones: raw/ exactly as it arrived, curated/ cleaned and ready to query. Raw is never edited, so you can always rebuild.
    • 
        
  • A Glue ETL job reads, cleans, converts and writes. It is serverless and runs on a schedule or a trigger.
    • 
        
  • A crawler fills the Data Catalog with table definitions. The catalog holds descriptions only, never the data.
    • 
      

    

    

      
Athena and QuickSight

      
    
        
  • Athena runs standard SQL on the files in place. There are no servers, and it costs nothing while nobody is querying.
    • 
        
  • It looks up the table in the Glue Data Catalog, reads the files, and saves the result to another S3 bucket.
    • 
        
  • Answers come in seconds to minutes. It is for analysis, not for serving an app's requests.
    • 
        
  • QuickSight turns queries into charts and dashboards. It can keep a copy of the data in SPICE, its in-memory store, so a dashboard does not pay for an Athena query on every view.
    • 
      

    

  


  
Data Streams vs Firehose

  

    

      
Kinesis Data StreamsData Firehose

      
Its jobHold a stream so that consumers can read itDeliver a stream to a destination

      
Who reads from itYour code: Lambda, applications, Flink. Several at once.Nobody. It writes to S3, Redshift or OpenSearch for you.

      
DelayUnder a secondSeconds to minutes, set by the buffer

      
Keeps the data24 hours to 365 days, replayableNo

      
ScalingShards you size, or on-demand modeAutomatic

      
Choose it whenYou must react in real time, or several consumers need the same eventsYou only need the data to land in a lake or warehouse

    

    
A way to remember: Data Streams holds; Firehose delivers. Producers can also send straight to Firehose when nothing needs the stream.

  


  
How fresh must the answer be?

  

    
That one question decides which part of the pipeline you read from.

    
    
      
  • Within a second (block a fraudulent payment): read the stream itself, with Lambda or with Managed Service for Apache Flink for running totals such as “orders in the last minute”.
    • 
      
  • Within minutes (today's sales so far): Firehose into S3, queried with Athena.
    • 
      
  • By tomorrow morning (the monthly report): a nightly Glue job over the lake. The slowest path and the cheapest.
    • 
    

    
Names you will meet around this drawing: MSK is managed Kafka, used in place of Kinesis. Redshift is a data warehouse, for heavy queries that run all day. Lake Formation controls who may see which tables and columns in the lake.

Check yourself

  
Where is the data at each stage: streaming or at rest?
In motion from the producer through Kinesis Data Streams, the Lambda consumer and the Firehose buffer. At rest from the moment Firehose writes a file to S3. Glue, Athena and QuickSight all work on data at rest: the catalog only describes the files, and Athena reads them where they are.

  
A shard stores records on disk for 24 hours. Why is that still called data in motion?
The storage is temporary and exists so that consumers can read the records and replay them. Nobody queries a shard, and the records expire. The lasting copy, the one you analyse, is the file in S3.

  
Data Streams or Firehose: what is the difference?
Data Streams holds records for your own consumers to read, in under a second, and lets them replay. Firehose is a delivery service that batches records and writes them to a destination such as S3, with a delay set by its buffer and no code to write.

  
Firehose can take records directly from producers. Why put a stream in front of it?
Because more than one thing needs the events. With a stream, a real-time consumer and Firehose both read the same records, a new consumer can be added later, and any of them can replay after a failure. If landing files in S3 is the only need, skip the stream.

  
Traffic doubles and producers start getting “throughput exceeded” errors. What do you change?
The stream's capacity. Each shard accepts 1 MB or 1,000 records a second, so add shards, or switch the stream to on-demand mode. Also check the partition key: if most records share one key they all go to one shard.

  
Two events from the same customer must be processed in order. How do you guarantee it?
Use the customer ID as the partition key. Records with the same key go to the same shard, and a shard keeps its records in order. There is no ordering across different shards.

  
Events arrive every millisecond, but a new file appears in S3 only every five minutes. Why?
Firehose buffers. It writes a file when the buffer reaches its size limit or its time limit, 5 MB or 300 seconds by default. With little traffic the time limit is reached first. Lower the interval for fresher data, at the cost of many small files.

  
Does the Glue Data Catalog contain your data?
No. It holds table definitions: the name, the columns and their types, the S3 location and the partitions. The data stays in S3, and Athena uses the catalog to find and read it.

  
One Athena query costs $18 every time it runs. Name two changes that cut it.
Store the data as Parquet, which is smaller and lets Athena read only the columns the query names. Partition it by date and filter on that date, so only the matching folders are read. Selecting named columns instead of SELECT * matters too.

  
The business wants a fraud alert within one second. Can Athena on the data lake do it?
No. The data reaches S3 minutes after the event, and Athena is built for analysis, not instant reaction. Read from the stream instead, with Lambda or Managed Service for Apache Flink.
