Disaster Recovery

The application from Day 14 survives a failed server and a failed Availability Zone. It does not survive the loss of the whole Region. Disaster recovery (DR) is the plan for that day. Two questions shape the plan: how much data can you afford to lose, and how long can you afford to be offline? Today you draw two Regions four times, from the cheapest plan to the fastest.

Concepts

RPO and RTO

  • RPO, recovery point objective: how much data you may lose, measured as time. “RPO 1 hour” means that after recovery, at most the last hour of data is missing. It looks back from the disaster.
  • RTO, recovery time objective: how long the service may be offline. It looks forward from the disaster.
  • The business sets both numbers. The architect finds the cheapest design that meets them.
  • RPO depends on how the data is copied. RTO depends on how much is already running.

Getting the data across

  • Backups are copies made on a schedule. AWS Backup can copy each one to a vault in another Region. The RPO is the time between two backups.
  • Replication sends every change as it happens: an RDS cross-Region read replica, S3 Cross-Region Replication (it needs versioning on both buckets), a DynamoDB global table.
  • Between Regions, replication is normally asynchronous: the copy is a little behind, usually by seconds for a database. S3 replication usually takes minutes, and has no time limit unless you turn on Replication Time Control. That delay is the RPO.
  • The Multi-AZ standby from Day 10 is in the same Region. It is no help when the Region is lost.

Failing over

To fail over is to move the users to the other Region. Three things must be true first.

  • The data accepts writes. A read replica must be promoted, which turns it into a normal database of its own.
  • There are enough servers. Switched on, or scaled up.
  • The traffic moves. Route 53 failover routing with a health check does this (Day 13). Keep the TTL short.

Going back later is failback. Data written in Singapore during the outage must be copied back to Mumbai first.

What makes it work on the day

  • Infrastructure as code: a template file (CloudFormation or Terraform) that describes the VPC, load balancer and servers, so the same setup can be created in the second Region without relying on memory.
  • Everything the servers need to start must be in the second Region too: server images (AMIs), secrets, encryption keys. Each of these belongs to one Region, so it must be copied or created again in the other.
  • Service quotas are per Region. Check that Singapore allows as many servers as Mumbai uses.
  • Practice. Run a real failover on a planned day. A plan that was never tested usually fails.

Three things that are not the same

  • High availability keeps the application running through small failures: a server, an Availability Zone. Multi-AZ and Auto Scaling do it automatically, inside one Region.
  • Disaster recovery brings the application back after a large failure, such as the loss of a Region. It needs a second Region and a plan.
  • Backup lets you go back in time. If someone deletes a table, replication copies the deletion to Singapore within seconds. Only a backup from before the mistake brings the data back. So every one of the four strategies still keeps backups.

Choosing the second Region: far enough away that one flood, earthquake or power failure cannot reach both. Check that it offers the services you use. Check the law too: if the data must stay in India, Hyderabad (ap-south-2) is the second Region inside the country.

Names you will meet around this drawing: AWS Elastic Disaster Recovery copies whole servers continuously to a low-cost staging area in the second Region and starts them when needed, a ready-made pilot light. Aurora Global Database is a relational database that replicates to other Regions, usually less than a second behind. Global Accelerator can move traffic between Regions without waiting for DNS answers to expire.

Check yourself

Rank the four strategies by RTO/RPO and cost.

From slowest and cheapest to fastest and most expensive: backup and restore (hours of downtime, hours of data lost, storage cost only), pilot light (tens of minutes; seconds to minutes of data), warm standby (minutes), multi-site active-active (near zero for both, about double the cost). The order is the same for all three measures: the more that is already running in the second Region, the faster the recovery and the higher the bill.

RPO and RTO: what does each one measure?

RPO is how much data you may lose, measured as time looking back from the disaster. RTO is how long the service may be offline, looking forward from the disaster. They are separate: a design can lose almost no data and still take hours to come back.

Pilot light and warm standby both keep a live copy of the data. What is the difference?

Whether the second Region can serve a request right now. In pilot light the servers are switched off, so nothing works until you start them. In warm standby a small copy of the whole application is running, so it can take traffic at once and then scale up.

The database is Multi-AZ. Is that a disaster recovery plan?

No. The standby is in another Availability Zone of the same Region. It covers the loss of a zone, which is high availability. When the Region is lost, the primary and the standby are lost together.

Backups run every 24 hours and are copied to Singapore. What is the RPO, and how do you make it smaller without changing strategy?

Up to 24 hours: everything written since the last backup. Run the backups more often and the RPO shrinks to that interval. The RTO does not change, because you still have to rebuild everything and restore the database.

At 10:00 someone deletes the orders table by mistake. There is a read replica in Singapore. Does it save you?

No. Replication copies the deletion within seconds, so both Regions now have no orders table. You need a backup from before 10:00, or point-in-time recovery. This is why every strategy keeps backups as well.

The business says: offline for at most one hour, lose at most a few seconds of data, and keep the bill as low as possible. Which strategy?

Pilot light. A few seconds of data loss needs continuous replication, which rules out backup and restore. One hour is enough time to promote the replica and start the servers, so there is no reason to pay for servers that run all year.

In active-active, why is an RDS primary in Mumbai with a read replica in Singapore not enough?

Only the primary accepts writes. Users served from Singapore would have to send every write to Mumbai, and if Mumbai fails nobody can write until the replica is promoted. Active-active needs data that both Regions can write to, such as a DynamoDB global table.

The DR plan was written two years ago and has never been run. What is likely to go wrong?

The templates no longer match what runs in Mumbai, the copied server images are old, the quotas in Singapore are too low, a secret or an encryption key was never copied, and nobody remembers the steps. Only a practice failover finds these before a real disaster does.

You failed over to Singapore. A day later Mumbai is healthy again. Can you simply switch the users back?

Not yet. Singapore has taken a day of writes that Mumbai does not have. First replicate that data back to Mumbai, then move the users at a quiet time, and set up the replication towards Singapore again.
