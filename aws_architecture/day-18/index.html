Containers on ECS Fargate

Lambda is perfect for short bursts of work, but some services need to run continuously, for longer than 15 minutes, or in a runtime of your choosing. Containers give you that, and Fargate runs them without any servers for you to manage. The network is the one you know from Week 2; only the boxes in the private subnets change.

Concepts

Container and image

A container packages your code with everything it needs to run, so it behaves the same on a laptop and in production.

  • An image is the packaged file; a container is a running copy of it.
  • ECR, Elastic Container Registry, is where you store images privately in AWS.
  • Each build gets a tag, such as shop-api:v2.

The four ECS words

  • Task definition: the recipe: which image, how much CPU and memory, which port, which roles. Versioned as revisions.
  • Task: one running copy of that recipe.
  • Service: keeps N tasks running, replaces failed ones, registers them with the load balancer, rolls out new revisions.
  • Cluster: a named group that services and tasks belong to.

Fargate

The way the tasks are run. You choose between two launch types.

  • Fargate: AWS finds the capacity. No instances to patch or scale; you pay per task for its CPU and memory per second.
  • EC2: tasks run on instances you manage in an Auto Scaling group. More work, more control, cheaper at large steady scale.
  • Each Fargate task gets its own private IP in your subnet and its own security group.

Networking is unchanged

  • Load balancer in public subnets, tasks in private subnets.
  • task-sg allows port 8080 only from alb-sg.
  • The target group holds IP addresses, not instances. The service adds and removes them as tasks come and go.
  • To pull the image, tasks need a way out: the NAT Gateway, or VPC endpoints for ECR and S3.

Check yourself

Task role and execution role: what is each for?

The execution role is used by ECS to start the task: pulling the image from ECR and sending logs to CloudWatch. The task role is used by your code while it runs, for its own calls to AWS services such as S3 or DynamoDB.

Tasks in private subnets fail to start with “cannot pull container image”. The NAT Gateways were deleted to save money. Why?

A task must reach ECR to download its image, and ECR is outside the VPC. With no NAT Gateway and no VPC endpoints there is no path. Add interface endpoints for ECR and a gateway endpoint for S3, or restore the NAT Gateways.

A task crashes. Who notices and what happens?

The ECS service. It sees fewer running tasks than desired and starts a replacement from the task definition, then registers the new task's IP with the load balancer.

Task IP addresses change on every restart. How does the load balancer keep up?

The target group uses IP targets, and the service registers each new task and deregisters each stopped one automatically.

How do you release a new version with no downtime?

Push the new image to ECR, register a new task definition revision that points to it, and update the service. The service starts new tasks, waits until they pass the load balancer's health check, then stops old ones, a few at a time.

The application must read from an S3 bucket. Which role do you change?

The task role. Add permission to read that one bucket. The execution role is not involved in what the application does.

When would you choose the EC2 launch type over Fargate?

For large, steady workloads where managing your own instances is cheaper, or when you need something Fargate does not offer, such as GPUs or special instance types.

Why run this API in containers rather than Lambda?

It may hold long connections, run tasks longer than 15 minutes, need a custom runtime, or have steady traffic where always-on tasks are cheaper and have no cold starts. If traffic were spiky and short, Lambda would be the better fit.
