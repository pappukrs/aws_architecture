Read Scaling and Caching

The app tier can now grow to any size, but every server still queries one database. Most of those queries are reads, and many are the same read repeated. Today you take that load off the primary in two ways: a cache that answers repeated reads from memory, and a read replica that answers the rest.

The diagram

Full picture: for a read, an app server first asks ElastiCache (1). Only on a cache miss does it query the read replica (2) and then save the answer in the cache. Every write goes to the RDS primary (3), which copies it synchronously to the standby and asynchronously to the read replica. App servers in both zones use the same three endpoints.

Concepts

Read replica

A read-only copy of the database that you can send SELECT queries to.

  • Replication is asynchronous, so the replica can be a moment behind the primary. This is replication lag.
  • It has its own endpoint. The application must send reads there and writes to the primary.
  • You can add several, in any AZ or even another Region.
  • A replica can be promoted to a standalone database, but that is a manual step.

ElastiCache

A managed in-memory store, Redis or Memcached. It answers in under a millisecond because nothing is read from disk.

  • Holds results of expensive or repeated queries.
  • Holds user sessions, which is how the app servers from Day 9 stay stateless.
  • Lives in private subnets with its own security group: 6379 from app-sg.
  • With a replica node in a second AZ it fails over automatically.

Cache-aside pattern

The application manages the cache itself. This is the pattern in the diagram.

  1. Look for the key in the cache.
  2. Hit: return it. Done.
  3. Miss: read from the database, store the result in the cache with a TTL, return it.
  4. On a write, update the database and delete the cached key.

TTL and stale data

TTL, time to live, is how long a cached value is kept before Redis drops it.

  • Long TTL: more hits, but users may see old data.
  • Short TTL: fresher data, but more load on the database.
  • The cache is never the source of truth. If it is lost, the application still works, only slower.

Check yourself

Multi-AZ standby and read replica: what is each for?

The standby is for availability. It is a synchronous copy that takes over automatically and serves no traffic until then. The read replica is for performance. It is an asynchronous copy that serves read queries and does not take over by itself.

Can the application write to a read replica?

No. It is read-only. All writes go to the primary, which is why the primary can still be a bottleneck for write-heavy workloads.

A user changes their display name and the next page still shows the old one. Give two possible causes.

The cached copy was not deleted on the write and is still within its TTL. Or the read went to the replica before the change had replicated. Fix the first by deleting the key on every write; fix the second by reading from the primary right after a user's own write.

The cache hit rate is 90%. What does that mean for the database?

Only one read in ten reaches it. Database read load is a tenth of what it would be without the cache, which is often the cheapest performance gain available.

The Redis primary node fails and there is no replica node. What happens to the application?

If it is written correctly, it treats every lookup as a miss and reads from the database, so it keeps working but slower, and database load jumps. If sessions were stored only there, users are logged out. That is why a replica node in a second AZ matters.

Why store sessions in ElastiCache rather than on the app server?

App servers are added, removed and replaced by Auto Scaling. A session kept on one server is lost when it goes, and other servers cannot see it. In a shared store, any server can handle any user's request.

What has to change in the application code to use a read replica?

It needs two connections: the primary endpoint for writes and the replica endpoint for reads, and it must choose the right one for each query. Multi-AZ, by contrast, needs no code change.

The database is slow. In what order would you try these: bigger instance, read replica, cache?

Usually cache first, since it removes repeated reads entirely and is cheap. Then read replicas for the reads that remain. A bigger instance is the simplest change but the least scalable, and it is the only one of the three that helps writes.
