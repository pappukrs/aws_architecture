Load-Balanced Web Tier

Week 1 ended with two web servers and nothing to share users between them. Today you put an Application Load Balancer in front: one address for users, traffic spread over both zones, and failed servers skipped automatically. The web servers move into the private subnets.

Concepts

Application Load Balancer (ALB)

A managed service that receives requests and spreads them over many servers. It works at the HTTP level (layer 7).

  • Users get one DNS name; they never see individual servers.
  • You give it subnets in at least two AZs. It places a node in each.
  • AWS scales it and replaces failed nodes; you manage nothing.
  • Draw it across the public subnets, straddling the AZs.

Listener and rules

A listener is a port the load balancer listens on, plus rules for what to do with each request.

  • Here: HTTPS 443 → forward to web-tg.
  • Rules can route by path or host: /api/* to one target group, /images/* to another.
  • HTTPS is decrypted here, using a certificate from ACM. This is called TLS termination.

Target group and health checks

A target group is the list of servers that can receive traffic, with one health check definition for all of them.

  • Targets can be instances, IP addresses or a Lambda function.
  • A target that fails several checks in a row is marked unhealthy and gets no traffic.
  • When it passes again it is put back automatically.
  • The load balancer does not repair or replace the server. That is Auto Scaling, tomorrow.

Why the servers moved to private subnets

In Week 1 the web servers had public IPs. Now only the load balancer faces the internet.

  • Servers have no public IP, so they cannot be attacked directly.
  • web-sg allows port 80 only from alb-sg: security group chaining again.
  • They still use the NAT Gateway for their own outbound updates.
  • What stays in the public subnets: the load balancer and the NAT Gateways.

Check yourself

Why does the load balancer need subnets in at least two AZs?

It places one node in each subnet you give it. With nodes in two AZs, the loss of one zone leaves a working node in the other, so the load balancer itself is not a single point of failure. AWS will not let you create an ALB with fewer than two.

Web server A fails its health check. What does the load balancer do, and what does it not do?

It stops sending requests to A and sends everything to B. It does not restart, repair or replace A. When A passes the check again, traffic returns to it.

What is the source in the inbound rule of web-sg?

The security group alb-sg. Only the load balancer may reach the servers on port 80; nothing else can, even from inside the VPC.

The web server logs show every request coming from 10.0.1.x or 10.0.3.x. Why, and where is the real client IP?

Those are the load balancer nodes' private addresses; the load balancer opens a new connection to the server. The original client address is in the X-Forwarded-For header.

Can you point your domain at the load balancer's IP address?

No. Its IP addresses change as AWS scales it. You point the domain at its DNS name, using a Route 53 alias record (Day 13).

Where is HTTPS decrypted in this design?

At the load balancer. Traffic from the load balancer to the servers is plain HTTP on port 80 inside the VPC. If policy requires encryption all the way, the target group can use HTTPS as well.

Do the web servers still need the NAT Gateways?

Yes, for connections they start themselves, such as downloading updates. Requests from users arrive through the load balancer, and replies go back through it, so that traffic does not use the NAT Gateway.

Both servers are healthy but traffic doubles and they are overloaded. Does the load balancer help?

Only by sharing the load evenly. It cannot add servers. Adding and removing servers automatically is Auto Scaling, on Day 9.
