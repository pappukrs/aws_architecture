      6. Explain it out loud

      Answer each one aloud in a few sentences before opening it.

      Trace a request for a product image from a user in Delhi.

      The resolver asks Route 53 for example.com and gets CloudFront addresses. The browser connects over HTTPS to the Delhi edge. On a hit, the edge returns the image at once. On a miss, it fetches it from the private S3 bucket using origin access control, caches it, and returns it. No server in the VPC is involved.

      Trace “add to cart”, a dynamic request that writes data.

      Route 53 → CloudFront, which does not cache it and forwards it to the load balancer through the Internet Gateway → a healthy app server in either AZ (8080, allowed by app-sg from alb-sg) → a write to the RDS primary (3306, db-sg from app-sg), copied synchronously to the standby. The app server then deletes the cached cart so the next read is fresh.

      AZ a is lost completely. Walk through what each layer does.

      The load balancer keeps serving from its node in AZ b and stops sending to targets in AZ a. The Auto Scaling group launches replacements in AZ b to restore desired capacity. RDS promotes the standby in AZ b within a minute or two, and ElastiCache promotes its replica node. NAT Gateway B and private route table B were always independent. Users see a short interruption on writes, then normal service.

      Where is the weakest point of this design?

      Inside the Region, the single read replica: if the app has no fallback to the primary, read queries fail when it is lost. Beyond that, the Region itself: nothing here survives the loss of Mumbai. And no design protects against a bad deployment or bad data.

      Traffic grows tenfold during a sale. Which component struggles first, and what do you do?

      Not the stateless parts: CloudFront, the load balancer and the Auto Scaling group all grow by themselves. The database primary is the limit, because all writes go to one instance. Raise the cache hit rate, add read replicas, and scale the primary up before the sale.

      How would you release a new version of the app with no downtime?

      Create a new launch template version and let the Auto Scaling group replace instances a few at a time, an instance refresh, while the load balancer only sends traffic to those passing health checks. For more caution, run the new version behind a second target group and shift a small weighted share of traffic to it first.

      Which parts of this drawing cost money even with zero visitors?

      The two NAT Gateways, the load balancer, the minimum two app servers, the RDS primary plus standby plus read replica, and the two Redis nodes, all billed per hour. S3, CloudFront and Route 53 queries cost almost nothing without traffic.
