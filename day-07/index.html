      5. Explain it out loud

      Answer each one aloud in two or three sentences before opening it. Being able to say it is the real test.

      Trace a user's HTTPS request to the web server in AZ a, naming every component it passes.

      Internet → Internet Gateway (maps the public IP to the private IP) → public NACL (allows it) → web-sg (allows 443 from anywhere) → web server. The reply returns the same way; the security group lets it out automatically.

      Trace the app server in AZ b downloading a package from the internet.

      App server → private route table B matches 0.0.0.0/0 → nat-b → NAT Gateway B in public subnet B (source becomes its own IP) → public route table matches 0.0.0.0/0 → igw → Internet Gateway (source becomes the Elastic IP) → internet.

      Why are there three route tables and not two or four?

      Both public subnets have the same default route, so they share one. Each private subnet needs a different NAT Gateway as its target, so each needs its own. One plus two is three.

      Which components in the drawing would you still have with only one of each, and why is that safe?

      The VPC and the Internet Gateway. Both are regional services that AWS already runs across AZs, so they are not a single point of failure.

      An admin wants to SSH into the app server in AZ b. What path, and which rules allow it?

      Laptop → Internet Gateway → bastion in public subnet A (bastion-sg allows 22 from the admin's IP) → app server in private subnet B over the local route (app-sg allows 22 from bastion-sg). One bastion reaches both AZs because the VPC's local route covers every subnet.

      The bastion is only in AZ a. Is that a problem?

      For users, no: the application does not depend on it. For administrators, yes: if AZ a fails they lose their way in. Either keep a second bastion in AZ b, or use Session Manager, which needs no bastion at all.

      What is still missing before this could serve real users reliably?

      Nothing spreads users across the two web servers or moves them when one fails, and the number of servers is fixed. A load balancer (Day 8) and Auto Scaling (Day 9) solve those.

      Next — Day 8: Load-balanced web tier. Week 2 starts. You put an Application Load Balancer across the two public subnets and move the web servers into the private subnets, so users reach a single address and traffic is spread over both zones.
