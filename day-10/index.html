Classic 3-Tier Application

This is the most drawn architecture in AWS. The application is split into three layers, each in its own subnets with its own security group: a load balancer in front, application servers in the middle, and a database at the back that survives the loss of a zone.

The diagram

Full picture: a request passes through three tiers. The load balancer in the public subnets receives it, an application server in the Auto Scaling group processes it, and the RDS primary stores the data. Every write is copied to a standby in the other zone before it is confirmed. Each tier accepts traffic only from the tier in front of it.

Concepts

Why three tiers

  • Security: the database is two firewalls away from the internet. Breaking into the web tier does not give access to the data.
  • Scaling: each tier grows independently. More app servers do not require a bigger database.
  • Change: you can replace one tier without touching the others.

A common variant adds web servers as their own Auto Scaling group and a second, internal load balancer in front of the app tier.

Amazon RDS

A managed relational database: MySQL, PostgreSQL, MariaDB, Oracle, SQL Server, or Aurora.

  • AWS handles installation, patching, backups and failover.
  • You never log in to the server; you connect to an endpoint, a DNS name.
  • You place it using a DB subnet group: a list of subnets in at least two AZs.

Multi-AZ

RDS keeps a second copy of the database, the standby, in another AZ.

  • Synchronous: a write is confirmed only after both copies have it, so failover loses no committed data.
  • Automatic failover in about one to two minutes. The endpoint name stays the same.
  • The standby serves no traffic. Multi-AZ is for availability, not for speed. Read scaling is tomorrow.

The security group chain

Each group's source is the group of the tier in front.

  • alb-sg ← the internet, on 443.
  • app-sg ← alb-sg, on 8080.
  • db-sg ← app-sg, on 3306.

The load balancer cannot reach the database, and nothing on the internet can reach the app servers. Draw this chain on every 3-tier diagram.

Check yourself

Which security group references which?

app-sg references alb-sg as its source, and db-sg references app-sg. alb-sg references nothing; its source is 0.0.0.0/0. Each tier trusts only the tier directly in front of it.

Can the load balancer connect straight to the database?

No. db-sg allows 3306 only from app-sg, and the load balancer carries alb-sg.

The app servers are slow on read-heavy pages. Can they read from the Multi-AZ standby?

No. In this deployment the standby accepts no connections; it exists only to take over. For read scaling you add read replicas, which is tomorrow.

The primary fails. What must change in the application's configuration?

Nothing. The application connects to the RDS endpoint name, and RDS repoints that name to the standby. Open connections break, so the application must retry.

Why can Multi-AZ fail over without losing committed data?

Replication is synchronous: the primary confirms a write only after the standby has stored it too. Anything the application was told is saved exists in both zones.

Someone runs DELETE FROM orders by mistake. Does the standby save you?

No. The delete is replicated to the standby immediately. Multi-AZ protects against infrastructure failure, not against bad data. For that you need backups and point-in-time recovery.

Why do the data subnets have no NAT route?

The database never needs to start a connection to the internet, so there is no reason to give it a path. Removing the route means that even a mistake in a security group cannot expose it outward.

The whole Mumbai Region becomes unavailable. Does this design survive?

No. Multi-AZ covers the loss of a zone, not of a Region. Surviving that needs a copy in another Region, which is disaster recovery on Day 28.
