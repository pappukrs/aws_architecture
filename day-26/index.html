Monitoring and Logging

An architecture you cannot see into is one you cannot run. When the site is slow, when a setting changed overnight, when an auditor asks who had access, you need records. Four services collect them, and each answers a different question. Today you draw where every record comes from and where it ends up.

Concepts

CloudWatch metrics and alarms

  • AWS services send metrics automatically: CPU, request counts, latency, queue depth.
  • Not everything is visible from outside a server. Memory and disk use on EC2 need the CloudWatch agent installed.
  • An alarm watches one metric against a threshold over several periods, and has three states: OK, ALARM, INSUFFICIENT_DATA.
  • Alarm actions: notify through SNS, scale a group, stop or reboot an instance.

CloudWatch Logs

  • Lambda and many services write here automatically; EC2 needs the agent.
  • Organised into log groups. By default they are kept forever, so set a retention period or the bill grows quietly.
  • Logs Insights searches across them with queries.
  • A metric filter counts matching lines, such as ERROR, and turns the count into a metric you can alarm on.

CloudTrail

A record of every API call in the account: creating, changing, deleting, signing in.

  • Each event says who, what, when, from which IP.
  • The last 90 days are viewable by default. A trail delivers events to S3 to keep them longer.
  • One organisation-wide trail can cover every account and Region.
  • It is the evidence in any security investigation.

Flow Logs and Config

  • VPC Flow Logs record each connection: source, destination, port, and whether it was accepted or rejected. They do not contain the data itself.
  • AWS Config records each resource's settings and every change, so you can see what something looked like on any past date.
  • Config rules check settings continuously: “no security group open to the world on port 22”, “all volumes encrypted”. A broken rule can trigger an automatic fix.

A way to remember: CloudWatch watches the system; CloudTrail follows the trail people leave.

Why a central bucket in another account

  • Tamper-proof: an attacker, or an employee, who gains control of the application account cannot erase the record of what they did.
  • One place to search: an investigation across twenty accounts starts in one bucket.
  • Cheap to keep: lifecycle rules move old logs to archival storage; regulations often require years.
  • Locked down: services may write, a few security staff may read, nobody may delete.

For requests that cross several services, as in Day 20's microservices, add tracing with X-Ray: it follows one request through every hop and shows where the time went.

Check yourself

CloudWatch or CloudTrail: what is the difference?

CloudWatch monitors how resources perform: metrics, logs and alarms. CloudTrail records who called which API, when and from where. One tells you the server is overloaded; the other tells you who resized it.

You look for a memory metric on an EC2 instance and it is not there. Why?

AWS can only see what is visible from outside the instance, such as CPU and network. Memory and disk space are inside the operating system, so they are reported only if the CloudWatch agent is installed.

Can VPC Flow Logs show you what data was sent?

No. They record addresses, ports, protocol, byte counts and whether the connection was accepted or rejected, not the contents.

An alarm fires and clears every few minutes all night. How do you fix it without ignoring real problems?

Require the threshold to be breached for several periods in a row, for example 3 out of 3 minutes, and check that the threshold is realistic. Brief spikes then no longer trigger it.

The auditor wants API activity from three years ago, and the console shows only 90 days. What should have been set up?

A trail delivering CloudTrail events to an S3 bucket, ideally the central one, with a lifecycle rule that keeps them for the required period.

CloudTrail and Config both relate to changes. How do they differ?

CloudTrail records the action: who made the API call. Config records the result: what the resource's settings were before and after, and whether they now comply with your rules. You often use both together.

Why send logs to a separate account instead of a bucket next to the application?

So that whoever compromises or misuses the application account cannot delete the evidence. The log archive account has very few users and its bucket does not allow deletion.

Someone opens port 22 to the whole internet on a security group. How could that be caught within minutes, automatically?

An AWS Config rule that checks for unrestricted SSH marks the group non-compliant and can trigger a remediation that removes the rule. CloudTrail then tells you who added it.
