Week 3 Review: Serverless Web Application

You put Week 3 together into one complete application with no servers and no VPC: a static front end, sign-in, an API, a database and a queue. One service is new today, Cognito, which handles the sign-in. Then you trace a login from the first click to the data coming back.

New today: Cognito

Cognito user pool

A managed user directory. It stores accounts and does sign-up, sign-in, password reset and multi-factor login, so you write none of that.

  • The browser sends the username and password to Cognito, never to your API.
  • On success Cognito returns signed tokens.
  • It can also let people sign in with Google, Apple or a company directory.
  • Regional service: draw it inside the Region, outside any VPC.

Tokens and the authorizer

A token is a small signed document (a JWT) saying who the user is and until when it is valid.

  • The browser attaches the access token to every API call.
  • API Gateway's JWT authorizer checks the signature and expiry using Cognito's public keys.
  • A bad or expired token gets 401 from API Gateway. Your function never runs and you are not billed for it.
  • Your function receives the verified user ID and trusts only that.

      6. Explain it out loud

      Answer each one aloud in a few sentences before opening it.

      It is 3 a.m. and nobody is using the app. What is running, and what are you paying for?

      Nothing is running: no function, no server. You pay for stored data in S3 and DynamoDB and little else. Compare Day 14, where NAT Gateways, a load balancer, servers and databases are billed every hour regardless.

      Why does the browser send the password to Cognito and not to your API?

      So your code never handles passwords. Cognito verifies them and hands back a signed token. Your API only has to check a signature, which API Gateway does before your function is invoked.

      How does the function know whose notes to return?

      From the user ID inside the verified token, which API Gateway passes along. It must not use an ID supplied in the request body or URL, since any caller could change that to read someone else's notes.

      A campaign brings ten thousand sign-ups in a minute. What does each part do?

      CloudFront serves the page from edge caches. Cognito, API Gateway and DynamoDB on-demand scale by themselves. Lambda runs many copies at once, up to the concurrency limit. The welcome emails queue up and are sent as fast as the second function works, without slowing any sign-up.

      Users ask for “export all my notes as a PDF”, which takes five minutes. How do you add it?

      Not inside the API request: API Gateway stops waiting after about 30 seconds. The API puts a job on a queue and answers at once. A worker, Lambda or a Fargate task, builds the PDF, saves it to S3 and notifies the user with a link.

      When would you choose the Day 14 architecture instead of this one?

      When the application needs a relational database with complex queries, long-lived connections, steady heavy traffic that makes always-on servers cheaper, or software that expects a normal server. Many real systems mix both.

      Is anything in this design a single point of failure?

      Not within the Region; every service runs across several AZs. The Region itself is: Cognito, the API, the functions and the table all live in one. DynamoDB global tables and a second Region address that, on Day 28.
