Lambda and API Gateway in depth

Lambda's promise is that you write a function and AWS runs as many copies of it as the traffic needs. The small print is in the word "copies". Every copy is an execution environment, a Firecracker micro-VM that is created on demand (the cold start), reused for one request at a time, frozen between requests and thrown away when AWS decides; the number of them running at once is your concurrency, and concurrency is the thing Lambda limits, counts and bills. Most production surprises come from forgetting that concurrency is requests per second times duration: a downstream database that slows from 100 ms to 2 seconds multiplies your concurrency by twenty without a single extra request, and the account's thousand-environment pool runs dry for every function at once. This page goes inside that model: the three ways a function is invoked and what a throttle means for each, the lifecycle of an environment and what a cold start costs, reserved and provisioned concurrency, how a function reaches into a VPC, layers, SnapStart, destinations and the limits. Then the front door: API Gateway's REST, HTTP and WebSocket APIs, authorisers, throttling and usage plans, and Cognito for the users behind the tokens. The centre of the page is the interview question: Lambda is throttled at peak. What do you check, and what are the three fixes?

Model: concurrency needed is the peak rate times the duration (Little's law). Traffic steps from a tenth of the peak to the peak; on-demand concurrency for the function grows by 1,000 environments every 10 seconds from what it already has (provisioned environments count from the start), up to the lesser of its reserved concurrency and what the account has left after the other functions. Throttled requests per second are the share of the rate that does not fit: (needed − available) ÷ duration. A synchronous caller gets the error; an asynchronous invocation is kept and retried for up to six hours, so it turns into delay; an SQS mapping leaves the message in the queue. Provisioned concurrency is priced at $0.0000041667 per GB-second kept warm, at 512 MB, all month; on-demand duration at $0.0000166667 per GB-second and $0.20 per million requests, for the peak hour only.

Cold starts: who pays, how often, and what removes them

A cold start is the INIT phase on a user's request: the code is fetched, the runtime starts, your imports and clients are built. How long it takes depends on the runtime, the package and the memory; how often it happens depends on the traffic's shape. How it works inside

Three ways to invoke

  • Synchronous (RequestResponse): the caller holds the connection until the function returns or fails. API Gateway, ALB, function URLs, Cognito triggers and your SDK calls. Payload 6 MB each way (more with response streaming). Errors and throttles go back to the caller; Lambda retries nothing, and the AWS SDK retries throttles a few times with backoff on its own.
  • Asynchronous (Event): Lambda answers 202 at once and puts the event in an internal queue. S3, SNS, EventBridge, CloudWatch Logs and SES invoke this way. A function error is retried twice by default (0–2) with delays; a throttle or a system error is retried with backoff for up to the maximum event age (6 hours by default, from 60 s). Then the event is discarded, or sent to an on-failure destination if you set one.
  • Event source mapping: a poller inside Lambda reads SQS, Kinesis, DynamoDB Streams, MSK, self-managed Kafka, Amazon MQ or DocumentDB change streams, batches records and invokes synchronously. The mapping owns retries: SQS by visibility timeout and the queue's DLQ; streams by MaximumRetryAttempts, MaximumRecordAgeInSeconds, BisectBatchOnFunctionError and an on-failure destination.
  • The model picks the failure behaviour, not you. The same function behind API Gateway shows a throttle to a user; behind SNS it shows a delay; behind Kinesis it stalls a shard.

The execution environment

  • Each environment is a Firecracker micro-VM on a Lambda worker, with the memory you configured and CPU in proportion: 1,769 MB is one vCPU, 10,240 MB is six. It handles one invocation at a time; a second concurrent request gets a second environment.
  • INIT: extensions start, the runtime starts, your code outside the handler runs (imports, SDK clients, config). Limit 10 seconds for on-demand functions. INVOKE: the handler runs, up to the timeout (max 15 minutes). SHUTDOWN: extensions get up to 2 seconds when AWS retires the environment.
  • Between invocations the environment is frozen: background threads stop, timers stop, and an open database connection may be cut by the server while you are frozen. On the next invoke it thaws with memory, globals and /tmp intact. Initialise clients outside the handler to reuse them; never keep request state in globals.
  • Environments are recycled after hours even under steady traffic, and immediately after a deploy (a new version means new environments). Since August 2025 the INIT phase is billed as duration on every on-demand function, so a heavy init is now a line on the bill as well as on the latency graph.

Cold starts: where the time goes

  • A cold start is platform (place the micro-VM, fetch the code; tens to a few hundred ms, more for an uncached container image) + runtime (Node.js and Python start in about 100–200 ms, the JVM and .NET in several hundred) + your init, which is usually the largest part: a Spring context, an ORM that reflects a schema, a 200 MB dependency tree.
  • The REPORT log line carries Init Duration on cold invocations; X-Ray shows the Initialization segment. That is how you measure, not by feel.
  • Levers, cheapest first: smaller package and fewer imports (tree-shake, lazy-import what one route uses); more memory, because init is CPU-bound and gets more vCPU; arm64; SDK clients built once; no network calls during init that can wait. Then SnapStart or provisioned concurrency.
  • How many requests pay it is a matter of shape: steady traffic reuses environments for hours and cold starts are a fraction of a percent; spiky traffic pays one per new environment at each spike; traffic that sleeps for ten minutes between requests pays it nearly every time.

Concurrency, reserved and unreserved

  • Concurrency is the number of environments busy at once: requests per second × average duration. 1,000 requests a second at 200 ms is 200; at 2 seconds it is 2,000. The default account limit is 1,000 per Region (new accounts can start lower), shared by every function, and raisable by request to tens of thousands.
  • Scaling rate: each function can add 1,000 concurrent environments every 10 seconds until it reaches the account limit or its own cap. A spike from zero to 5,000 takes about 50 seconds to absorb, and requests above the curve are throttled.
  • Reserved concurrency does two things: it carves a slice out of the account pool that no other function can take, and it is a hard ceiling for this function. Setting it to 0 disables the function, which is how you stop a runaway. The account keeps at least 100 unreserved for everyone else.
  • The trap: one function with no reservation goes wild (a retry storm, a recursive trigger, a backfill) and drains the pool; every other unreserved function in the account is throttled at the same moment. Reserve for the critical path; cap the batch jobs.

Provisioned concurrency

  • Lambda creates N environments on a version or alias, runs their INIT ahead of time and keeps them ready. Requests up to N never see a cold start; above N they spill over to on-demand environments (ProvisionedConcurrencySpilloverInvocations).
  • Billed whether used or not: about $0.0000041667 per GB-second kept, plus a lower duration rate ($0.0000097222) while it runs. At 1 GB, one provisioned environment is about $11 a month; a thousand is $11,000. It pays for itself only when it is well used: above roughly 60% utilisation it is cheaper than on-demand for the same work.
  • Allocation takes minutes, not seconds. Use Application Auto Scaling: scheduled actions before a known peak (08:55 on weekdays), target tracking on ProvisionedConcurrencyUtilization around 0.7 for the rest. It counts against the account and the function's reserved concurrency.
  • It solves two problems: latency (no cold starts for the first N) and the ramp (N environments exist before the spike, so the 1,000-per-10-seconds curve starts at N). It does not raise the account limit.

SnapStart

  • On publishing a version, Lambda runs INIT once, takes a Firecracker snapshot of memory and disk, encrypts and caches it. A cold start then restores the snapshot instead of initialising: a 4-second Spring Boot start becomes a few hundred ms.
  • Supported for Java 11 and later, Python 3.12 and later, and .NET 8 and later, on published versions (use an alias). Free for Java; Python and .NET pay for the cached snapshot and each restore. Not combinable with provisioned concurrency, EFS, or ephemeral storage above 512 MB.
  • The catch is uniqueness: every environment restored from one snapshot starts with the same memory, so a random seed, a UUID generator state, a cached timestamp or a network connection opened during INIT is shared or stale. Use the runtime hooks (beforeCheckpoint / afterRestore, or the Python decorators) to reseed and reconnect.
  • Choose it over provisioned concurrency when the cold start is long, the traffic is spiky or unpredictable, and a few hundred ms on the first request is acceptable; choose provisioned when even that is too much, or the traffic is steady enough to keep the environments busy.

Lambda in a VPC

  • A function attached to subnets and security groups gets a Hyperplane ENI: one per subnet-and-security-group combination, created when the function is created or its VPC config changes (the function is Pending for a minute or two), shared by all its environments and by other functions with the same combination. The old per-environment ENI and its 10-second cold start are gone since 2019.
  • An attached function has no internet access and no public IP, ever, even in a public subnet. Egress to AWS APIs goes through VPC endpoints or a NAT gateway in a public subnet; forgetting this is the classic "times out calling Secrets Manager" bug.
  • Each Hyperplane ENI handles 65,000 connections; the per-VPC quota of Lambda ENIs is 500 (raisable). A function idle for weeks loses its ENI and becomes Inactive; the next invoke waits while it is recreated.
  • Attach only when the function needs something in the VPC (RDS, ElastiCache, an internal ALB). A function that only calls DynamoDB, S3 and public APIs is simpler, cheaper and has fewer failure modes outside the VPC; IAM, not the network, is its boundary.

Packaging, versions, layers, extensions

  • Zip: 50 MB uploaded directly (larger via S3), 250 MB unzipped including all layers. Container image: up to 10 GB from ECR, lazily loaded in chunks and cached, so a large image is not a 10 GB cold start, but the first cold start after a deploy is slower.
  • Versions are immutable snapshots of code and configuration; aliases point at a version and can split traffic between two (weighted aliases), which is how CodeDeploy runs a canary for Lambda. Provisioned concurrency and SnapStart live on versions, never on $LATEST.
  • Layers: up to five per function, shared code or binaries unpacked into /opt. Good for a common runtime dependency; bad as a substitute for packaging, since a layer version change does not redeploy the functions that use it, and the 250 MB limit includes them.
  • Extensions run beside the function in the same environment (an observability agent, a secrets cache) and share its memory and CPU; they add to INIT and can delay the response. Environment variables total 4 KB; secrets belong in Secrets Manager or Parameter Store, read once and cached.

Destinations, retries and loops

  • Destinations for asynchronous invocations send the result record (request, response or error, and metadata) to SQS, SNS, EventBridge or another function on success or on failure; S3 is available as an on-failure destination. They replace the older DLQ setting, which carried only the event, only on failure, and only to SQS or SNS.
  • Event source mappings for streams and Kafka have their own on-failure destination; for SQS the DLQ belongs to the queue, not the function.
  • Recursive loop detection: a function that writes to the queue, topic or bucket that triggers it is stopped after about 16 hops of the same chain, and the event is dropped or sent to the failure destination (RecursiveInvocationsDropped). It catches SQS, SNS, S3 and Lambda loops; a loop through your own API is still yours to prevent.
  • Every retry is another invocation of code that already ran once. The idempotency rules of Day 11 apply to every asynchronous and polled function: a business key, a claim, an idempotent act.

API Gateway: REST, HTTP, WebSocket

  • REST API (v1): the full feature set. API keys and usage plans, request validation, mapping templates in VTL, response caching, AWS WAF, resource policies, private APIs reachable only through an execute-api VPC endpoint, edge-optimised endpoints, canary stages, X-Ray. $3.50 per million requests.
  • HTTP API (v2): fewer features, lower latency, $1.00 per million. Native JWT authorisers (any OIDC issuer, Cognito included), Lambda authorisers with simple responses, IAM, CORS in one setting, automatic deploys, private integrations through VPC links. No WAF, no caching, no usage plans or API keys, no request validation.
  • WebSocket API: clients keep a connection; routes are chosen by a field of each message ($connect, $disconnect, $default, your own); the backend replies to a client by POSTing to the @connections endpoint with its connection id, which you store (usually in DynamoDB). Connections last at most 2 hours and drop after 10 minutes idle.
  • All three share the 29-second integration timeout for synchronous backends (raisable for Regional and private REST APIs, at the cost of account throttle quota), a 10 MB payload, and a Regional endpoint you can put behind CloudFront and a custom domain with mutual TLS.

Authorisers

  • IAM (SigV4): the caller signs with AWS credentials; the policy decides. For service-to-service calls and for apps that got credentials from a Cognito identity pool. No code, no extra latency.
  • JWT authoriser (HTTP API) or Cognito user pool authoriser (REST): API Gateway fetches the issuer's public keys, checks signature, expiry, issuer, audience or client id, and optionally scopes per route. No function to run or pay for. Claims are passed to the integration.
  • Lambda authoriser: your function receives the token (TOKEN type) or the request's headers and parameters (REQUEST type) and returns an IAM policy or, on HTTP APIs, a simple allow/deny. For custom tokens, API keys checked against a database, or tenant rules. Its result is cached by identity source for a TTL (300 s default, up to 3,600): fast and cheap, but a revoked token keeps working until the cache expires, and a policy cached for one path can wrongly allow or deny another if the policy is not written for the whole API.
  • The authoriser is also a function with concurrency. Behind a 10,000-request spike with caching off, it is the first thing to throttle, and the client sees a 500 that is not about your API at all.

Throttling and usage plans

  • API Gateway throttles with token buckets at four levels, narrowest first: per API key in a usage plan (REST), per route or method, per stage, and the account: 10,000 requests a second steady with a burst of 5,000 per Region (lower in some newer Regions), shared by every API in the account and raisable. Over any of them: 429 Too Many Requests, and the backend never sees it.
  • Usage plans attach API keys to a rate, a burst and a quota (requests per day, week or month). They are for metering and fair use between customers, not for authentication: an API key is an identifier, sent in a header, and AWS calls the enforcement best-effort.
  • Throttling at the gateway is the cheap defence of a Lambda backend: set the stage limit below what the function's concurrency can serve, and the overflow is a fast 429 at the door instead of a slow throttle, a retry and a 5xx behind it.
  • REST APIs can cache responses per stage (0.5 GB to 237 GB, per hour), keyed by path and chosen parameters, with a TTL up to an hour. A 90% hit rate removes 90% of the Lambda concurrency for read-heavy APIs; it is often the cheapest fix for a throttled GET.

Cognito

  • A user pool is a user directory and an OIDC identity provider: sign-up, sign-in, MFA, password policy, account recovery, a managed login page, and federation with Google, Apple, Facebook, SAML and OIDC providers. A successful sign-in returns three JWTs: an ID token (who the user is, for your app), an access token (scopes and groups, for your API; 5 minutes to 1 day, 1 hour by default) and a refresh token (up to 10 years, 30 days by default).
  • Lambda triggers customise the flow: pre sign-up, post confirmation, pre token generation (add claims), custom auth challenges, user migration from an old directory. They are synchronous invocations with a 5-second limit; a slow trigger is a failed sign-in.
  • An identity pool exchanges a token (from a user pool, a social provider, SAML, or none for guests) for temporary AWS credentials via STS, with a role chosen per authenticated, unauthenticated or rule-matched user. That is how a mobile app uploads straight to S3 with SigV4 and no server in between.
  • Pricing is per monthly active user by feature tier (Lite, Essentials, Plus); machine-to-machine clients are billed per app client and token request. Quotas are per API category (sign-in, sign-up, token) and per second; a login storm after an outage meets them.

Which compute behind the door, in a sentence

  • Lambda: spiky or low traffic, short requests, event handlers, glue; you pay per millisecond of work and nothing at zero. Wrong for steady high load (a container is cheaper above roughly 30–50% steady utilisation), for work over 15 minutes, for long-lived connections, and for code that needs a warm in-memory state.
  • Fargate / ECS: steady traffic, long requests, WebSocket servers, large frameworks with slow starts, connection pools you want to keep. App Runner when you want that without the cluster.
  • The front door: HTTP API by default; REST when you need keys, usage plans, WAF, caching, validation or a private API; ALB when the targets are mixed (containers and functions) or traffic is high and steady; a function URL for a webhook or an internal tool with IAM auth; AppSync for GraphQL and push.
  • What all of them share with Lambda: the backend must be stateless per request, idempotent where it is retried, and protected by a throttle in front that is lower than what it can serve.
