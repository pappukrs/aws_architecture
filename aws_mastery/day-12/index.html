Lambda and API Gateway in depth

Lambda's promise is that you write a function and AWS runs as many copies of it as the traffic needs. The small print is in the word "copies". Every copy is an execution environment, a Firecracker micro-VM that is created on demand (the cold start), reused for one request at a time, frozen between requests and thrown away when AWS decides; the number of them running at once is your concurrency, and concurrency is the thing Lambda limits, counts and bills. Most production surprises come from forgetting that concurrency is requests per second times duration: a downstream database that slows from 100 ms to 2 seconds multiplies your concurrency by twenty without a single extra request, and the account's thousand-environment pool runs dry for every function at once. This page goes inside that model: the three ways a function is invoked and what a throttle means for each, the lifecycle of an environment and what a cold start costs, reserved and provisioned concurrency, how a function reaches into a VPC, layers, SnapStart, destinations and the limits. Then the front door: API Gateway's REST, HTTP and WebSocket APIs, authorisers, throttling and usage plans, and Cognito for the users behind the tokens. The centre of the page is the interview question: Lambda is throttled at peak. What do you check, and what are the three fixes?

Model: concurrency needed is the peak rate times the duration (Little's law). Traffic steps from a tenth of the peak to the peak; on-demand concurrency for the function can add 1,000 environments at once and 1,000 more every 10 seconds after that, from what it already has (provisioned environments count from the start; an SQS mapping adds 300 a minute instead), up to the lesser of its reserved concurrency and what the account has left after the other functions. Throttled requests per second are the share of the rate that does not fit: (needed − available) ÷ duration. A synchronous caller gets the error; an asynchronous invocation is kept and retried for up to six hours, so it turns into delay; an SQS mapping leaves the message in the queue. Provisioned concurrency is priced at $0.0000041667 per GB-second kept warm, at 512 MB, all month; on-demand duration at $0.0000166667 per GB-second and $0.20 per million requests, for the peak hour only.

Cold starts: who pays, how often, and what removes them

A cold start is the INIT phase on a user's request: the code is fetched, the runtime starts, your imports and clients are built. How long it takes depends on the runtime, the package and the memory; how often it happens depends on the traffic's shape. How it works inside

Three ways to invoke

  • Synchronous (RequestResponse): the caller holds the connection until the function returns or fails. API Gateway, ALB, function URLs, Cognito triggers and your SDK calls. Payload 6 MB each way (more with response streaming). Errors and throttles go back to the caller; Lambda retries nothing, and the AWS SDK retries throttles a few times with backoff on its own.
  • Asynchronous (Event): Lambda answers 202 at once and puts the event in an internal queue. S3, SNS, EventBridge, CloudWatch Logs and SES invoke this way. A function error is retried twice by default (0–2) with delays; a throttle or a system error is retried with backoff for up to the maximum event age (6 hours by default, from 60 s). Then the event is discarded, or sent to an on-failure destination if you set one.
  • Event source mapping: a poller inside Lambda reads SQS, Kinesis, DynamoDB Streams, MSK, self-managed Kafka, Amazon MQ or DocumentDB change streams, batches records and invokes synchronously. The mapping owns retries: SQS by visibility timeout and the queue's DLQ; streams by MaximumRetryAttempts, MaximumRecordAgeInSeconds, BisectBatchOnFunctionError and an on-failure destination.
  • The model picks the failure behaviour, not you. The same function behind API Gateway shows a throttle to a user; behind SNS it shows a delay; behind Kinesis it stalls a shard.

The execution environment

  • Each environment is a Firecracker micro-VM on a Lambda worker, with the memory you configured and CPU in proportion: 1,769 MB is one vCPU, 10,240 MB is six. It handles one invocation at a time; a second concurrent request gets a second environment.
  • INIT: extensions start, the runtime starts, your code outside the handler runs (imports, SDK clients, config). Limit 10 seconds for on-demand functions. INVOKE: the handler runs, up to the timeout (max 15 minutes). SHUTDOWN: extensions get up to 2 seconds when AWS retires the environment.
  • Between invocations the environment is frozen: background threads stop, timers stop, and an open database connection may be cut by the server while you are frozen. On the next invoke it thaws with memory, globals and /tmp intact. Initialise clients outside the handler to reuse them; never keep request state in globals.
  • Environments are recycled after hours even under steady traffic, and immediately after a deploy (a new version means new environments). Since August 2025 the INIT phase is billed as duration on every on-demand function, so a heavy init is now a line on the bill as well as on the latency graph.

Cold starts: where the time goes

  • A cold start is platform (place the micro-VM, fetch the code; tens to a few hundred ms, more for an uncached container image) + runtime (Node.js and Python start in about 100–200 ms, the JVM and .NET in several hundred) + your init, which is usually the largest part: a Spring context, an ORM that reflects a schema, a 200 MB dependency tree.
  • The REPORT log line carries Init Duration on cold invocations; X-Ray shows the Initialization segment. That is how you measure, not by feel.
  • Levers, cheapest first: smaller package and fewer imports (tree-shake, lazy-import what one route uses); more memory, because init is CPU-bound and gets more vCPU; arm64; SDK clients built once; no network calls during init that can wait. Then SnapStart or provisioned concurrency.
  • How many requests pay it is a matter of shape: steady traffic reuses environments for hours and cold starts are a fraction of a percent; spiky traffic pays one per new environment at each spike; traffic that sleeps for ten minutes between requests pays it nearly every time.

Concurrency, reserved and unreserved

  • Concurrency is the number of environments busy at once: requests per second × average duration. 1,000 requests a second at 200 ms is 200; at 2 seconds it is 2,000. The default account limit is 1,000 per Region (new accounts can start lower), shared by every function, and raisable by request to tens of thousands.
  • Scaling rate: each function can add 1,000 concurrent environments every 10 seconds until it reaches the account limit or its own cap. A spike from zero to 5,000 takes about 50 seconds to absorb, and requests above the curve are throttled.
  • Reserved concurrency does two things: it carves a slice out of the account pool that no other function can take, and it is a hard ceiling for this function. Setting it to 0 disables the function, which is how you stop a runaway. The account keeps at least 100 unreserved for everyone else.
  • The trap: one function with no reservation goes wild (a retry storm, a recursive trigger, a backfill) and drains the pool; every other unreserved function in the account is throttled at the same moment. Reserve for the critical path; cap the batch jobs.

Provisioned concurrency

  • Lambda creates N environments on a version or alias, runs their INIT ahead of time and keeps them ready. Requests up to N never see a cold start; above N they spill over to on-demand environments (ProvisionedConcurrencySpilloverInvocations).
  • Billed whether used or not: about $0.0000041667 per GB-second kept, plus a lower duration rate ($0.0000097222) while it runs. At 1 GB, one provisioned environment is about $11 a month; a thousand is $11,000. It pays for itself only when it is well used: above roughly 60% utilisation it is cheaper than on-demand for the same work.
  • Allocation takes minutes, not seconds. Use Application Auto Scaling: scheduled actions before a known peak (08:55 on weekdays), target tracking on ProvisionedConcurrencyUtilization around 0.7 for the rest. It counts against the account and the function's reserved concurrency.
  • It solves two problems: latency (no cold starts for the first N) and the ramp (N environments exist before the spike, so the 1,000-per-10-seconds curve starts at N). It does not raise the account limit.

SnapStart

  • On publishing a version, Lambda runs INIT once, takes a Firecracker snapshot of memory and disk, encrypts and caches it. A cold start then restores the snapshot instead of initialising: a 4-second Spring Boot start becomes a few hundred ms.
  • Supported for Java 11 and later, Python 3.12 and later, and .NET 8 and later, on published versions (use an alias). Free for Java; Python and .NET pay for the cached snapshot and each restore. Not combinable with provisioned concurrency, EFS, or ephemeral storage above 512 MB.
  • The catch is uniqueness: every environment restored from one snapshot starts with the same memory, so a random seed, a UUID generator state, a cached timestamp or a network connection opened during INIT is shared or stale. Use the runtime hooks (beforeCheckpoint / afterRestore, or the Python decorators) to reseed and reconnect.
  • Choose it over provisioned concurrency when the cold start is long, the traffic is spiky or unpredictable, and a few hundred ms on the first request is acceptable; choose provisioned when even that is too much, or the traffic is steady enough to keep the environments busy.

Lambda in a VPC

  • A function attached to subnets and security groups gets a Hyperplane ENI: one per subnet-and-security-group combination, created when the function is created or its VPC config changes (the function is Pending for a minute or two), shared by all its environments and by other functions with the same combination. The old per-environment ENI and its 10-second cold start are gone since 2019.
  • An attached function has no internet access and no public IP, ever, even in a public subnet. Egress to AWS APIs goes through VPC endpoints or a NAT gateway in a public subnet; forgetting this is the classic "times out calling Secrets Manager" bug.
  • Each Hyperplane ENI handles 65,000 connections; the per-VPC quota of Lambda ENIs is 500 (raisable). A function idle for weeks loses its ENI and becomes Inactive; the next invoke waits while it is recreated.
  • Attach only when the function needs something in the VPC (RDS, ElastiCache, an internal ALB). A function that only calls DynamoDB, S3 and public APIs is simpler, cheaper and has fewer failure modes outside the VPC; IAM, not the network, is its boundary.

Packaging, versions, layers, extensions

  • Zip: 50 MB uploaded directly (larger via S3), 250 MB unzipped including all layers. Container image: up to 10 GB from ECR, lazily loaded in chunks and cached, so a large image is not a 10 GB cold start, but the first cold start after a deploy is slower.
  • Versions are immutable snapshots of code and configuration; aliases point at a version and can split traffic between two (weighted aliases), which is how CodeDeploy runs a canary for Lambda. Provisioned concurrency and SnapStart live on versions, never on $LATEST.
  • Layers: up to five per function, shared code or binaries unpacked into /opt. Good for a common runtime dependency; bad as a substitute for packaging, since a layer version change does not redeploy the functions that use it, and the 250 MB limit includes them.
  • Extensions run beside the function in the same environment (an observability agent, a secrets cache) and share its memory and CPU; they add to INIT and can delay the response. Environment variables total 4 KB; secrets belong in Secrets Manager or Parameter Store, read once and cached.

Destinations, retries and loops

  • Destinations for asynchronous invocations send the result record (request, response or error, and metadata) to SQS, SNS, EventBridge or another function on success or on failure; S3 is available as an on-failure destination. They replace the older DLQ setting, which carried only the event, only on failure, and only to SQS or SNS.
  • Event source mappings for streams and Kafka have their own on-failure destination; for SQS the DLQ belongs to the queue, not the function.
  • Recursive loop detection: a function that writes to the queue, topic or bucket that triggers it is stopped after about 16 hops of the same chain, and the event is dropped or sent to the failure destination (RecursiveInvocationsDropped). It catches SQS, SNS, S3 and Lambda loops; a loop through your own API is still yours to prevent.
  • Every retry is another invocation of code that already ran once. The idempotency rules of Day 11 apply to every asynchronous and polled function: a business key, a claim, an idempotent act.

API Gateway: REST, HTTP, WebSocket

  • REST API (v1): the full feature set. API keys and usage plans, request validation, mapping templates in VTL, response caching, AWS WAF, resource policies, private APIs reachable only through an execute-api VPC endpoint, edge-optimised endpoints, canary stages, X-Ray. $3.50 per million requests.
  • HTTP API (v2): fewer features, lower latency, $1.00 per million. Native JWT authorisers (any OIDC issuer, Cognito included), Lambda authorisers with simple responses, IAM, CORS in one setting, automatic deploys, private integrations through VPC links. No WAF, no caching, no usage plans or API keys, no request validation.
  • WebSocket API: clients keep a connection; routes are chosen by a field of each message ($connect, $disconnect, $default, your own); the backend replies to a client by POSTing to the @connections endpoint with its connection id, which you store (usually in DynamoDB). Connections last at most 2 hours and drop after 10 minutes idle.
  • All three share the 29-second integration timeout for synchronous backends (raisable for Regional and private REST APIs, at the cost of account throttle quota), a 10 MB payload, and a Regional endpoint you can put behind CloudFront and a custom domain with mutual TLS.

Authorisers

  • IAM (SigV4): the caller signs with AWS credentials; the policy decides. For service-to-service calls and for apps that got credentials from a Cognito identity pool. No code, no extra latency.
  • JWT authoriser (HTTP API) or Cognito user pool authoriser (REST): API Gateway fetches the issuer's public keys, checks signature, expiry, issuer, audience or client id, and optionally scopes per route. No function to run or pay for. Claims are passed to the integration.
  • Lambda authoriser: your function receives the token (TOKEN type) or the request's headers and parameters (REQUEST type) and returns an IAM policy or, on HTTP APIs, a simple allow/deny. For custom tokens, API keys checked against a database, or tenant rules. Its result is cached by identity source for a TTL (300 s default, up to 3,600): fast and cheap, but a revoked token keeps working until the cache expires, and a policy cached for one path can wrongly allow or deny another if the policy is not written for the whole API.
  • The authoriser is also a function with concurrency. Behind a 10,000-request spike with caching off, it is the first thing to throttle, and the client sees a 500 that is not about your API at all.

Throttling and usage plans

  • API Gateway throttles with token buckets at four levels, narrowest first: per API key in a usage plan (REST), per route or method, per stage, and the account: 10,000 requests a second steady with a burst of 5,000 per Region (lower in some newer Regions), shared by every API in the account and raisable. Over any of them: 429 Too Many Requests, and the backend never sees it.
  • Usage plans attach API keys to a rate, a burst and a quota (requests per day, week or month). They are for metering and fair use between customers, not for authentication: an API key is an identifier, sent in a header, and AWS calls the enforcement best-effort.
  • Throttling at the gateway is the cheap defence of a Lambda backend: set the stage limit below what the function's concurrency can serve, and the overflow is a fast 429 at the door instead of a slow throttle, a retry and a 5xx behind it.
  • REST APIs can cache responses per stage (0.5 GB to 237 GB, per hour), keyed by path and chosen parameters, with a TTL up to an hour. A 90% hit rate removes 90% of the Lambda concurrency for read-heavy APIs; it is often the cheapest fix for a throttled GET.

Cognito

  • A user pool is a user directory and an OIDC identity provider: sign-up, sign-in, MFA, password policy, account recovery, a managed login page, and federation with Google, Apple, Facebook, SAML and OIDC providers. A successful sign-in returns three JWTs: an ID token (who the user is, for your app), an access token (scopes and groups, for your API; 5 minutes to 1 day, 1 hour by default) and a refresh token (up to 10 years, 30 days by default).
  • Lambda triggers customise the flow: pre sign-up, post confirmation, pre token generation (add claims), custom auth challenges, user migration from an old directory. They are synchronous invocations with a 5-second limit; a slow trigger is a failed sign-in.
  • An identity pool exchanges a token (from a user pool, a social provider, SAML, or none for guests) for temporary AWS credentials via STS, with a role chosen per authenticated, unauthenticated or rule-matched user. That is how a mobile app uploads straight to S3 with SigV4 and no server in between.
  • Pricing is per monthly active user by feature tier (Lite, Essentials, Plus); machine-to-machine clients are billed per app client and token request. Quotas are per API category (sign-in, sign-up, token) and per second; a login storm after an outage meets them.

Which compute behind the door, in a sentence

  • Lambda: spiky or low traffic, short requests, event handlers, glue; you pay per millisecond of work and nothing at zero. Wrong for steady high load (a container is cheaper above roughly 30–50% steady utilisation), for work over 15 minutes, for long-lived connections, and for code that needs a warm in-memory state.
  • Fargate / ECS: steady traffic, long requests, WebSocket servers, large frameworks with slow starts, connection pools you want to keep. App Runner when you want that without the cluster.
  • The front door: HTTP API by default; REST when you need keys, usage plans, WAF, caching, validation or a private API; ALB when the targets are mixed (containers and functions) or traffic is high and steady; a function URL for a webhook or an internal tool with IAM auth; AppSync for GraphQL and push.
  • What all of them share with Lambda: the backend must be stateless per request, idempotent where it is retried, and protected by a throttle in front that is lower than what it can serve.

Hands-on lab

Goal: see a cold start in the REPORT line and watch memory change both the cold start and the CPU time; throttle a function on purpose with reserved concurrency and compare what a synchronous and an asynchronous caller experience; send a failed asynchronous event to an on-failure destination; remove the cold start with provisioned concurrency on an alias; put an HTTP API in front, throttle it at the stage and watch the 429s come from the gateway instead of the function; and protect it with a Cognito user pool and a JWT authoriser. Interview questions

Lambda is throttled at peak. What do you check, and what are the three fixes?

First I find whose throttle it is. A 429 can come from API Gateway, its account limit of 10,000 requests a second, a stage or route limit, or a usage plan, and then Lambda never ran; or it can come from Lambda, which shows as the Throttles metric on the function. If it is Lambda, I compare ConcurrentExecutions with the ceilings: the function's reserved concurrency, which is often a number someone set during an old incident; the account limit, shared with every other function, which ClaimedAccountConcurrency shows against the quota; and the scaling rate, a thousand new environments every ten seconds per function, which throttles a sudden step even when the limit is far away. Then I look at Duration, because concurrency is requests per second times duration: if p99 went from 200 milliseconds to two seconds because the database is slow, the same traffic needs ten times the environments, and the "traffic spike" is really a latency spike. The three fixes, in the order I would reach for them. One, need less concurrency: cut the duration by fixing the slow dependency, setting client timeouts shorter than the function's so a dead dependency fails fast, giving CPU-bound code more memory, reusing connections through RDS Proxy, caching at the gateway. Two, have more concurrency in the right place: raise the account quota, reserve concurrency for the critical function so a neighbour cannot starve it and cap the batch jobs that could, schedule provisioned concurrency before a known peak so the ramp starts high, and move noisy workloads to their own account. Three, stop needing it all at once: anything that does not need an answer in the request goes through a queue, API to SQS to Lambda with maximum concurrency on the mapping, or an asynchronous invocation, so the peak becomes a backlog drained at a safe rate; and throttle at the gateway with stage limits and usage plans, with clients that retry with backoff and jitter. I finish with the alarms: Throttles above zero on any synchronous function, and claimed account concurrency above eighty percent of the limit.

What is a cold start? How do you measure it and make it smaller?

A cold start is the INIT phase landing on a user's request: Lambda places a new micro-VM, fetches the code, starts the runtime and runs everything outside the handler, imports, SDK clients, configuration, a framework's dependency injection. It happens when there is no idle environment for the request: the first call, a scale-out, a deploy that retires the old environments, and the periodic recycling of environments. I measure it rather than guess: the REPORT log line has Init Duration on cold invocations, X-Ray has an Initialization segment, and a Logs Insights query gives me the share of invocations that were cold and the distribution of their length. To make it smaller I start with the code, because the platform part is usually a hundred milliseconds or so and the init code is the rest: fewer and lighter dependencies, lazy imports for what only one route uses, no network calls in init that can wait, clients built once. Then memory, because init is CPU-bound and 1,769 MB is a full vCPU. Then arm64, which is often faster as well as cheaper. Then the two platform features: SnapStart, which restores a snapshot taken after INIT and turns seconds into a few hundred milliseconds for Java, Python and .NET; and provisioned concurrency, which removes it entirely for the first N concurrent requests at a cost per hour. And I ask how much it matters: a cold start that affects 0.1% of requests is not in the p99, and paying for provisioned concurrency to remove it is money spent on a graph.

Reserved concurrency versus provisioned concurrency.

They solve different problems and are often confused because both are a number on the function. Reserved concurrency is about capacity: it sets aside a slice of the account's concurrency pool that no other function can use, and it is also a hard ceiling for the function itself. It costs nothing. I use it to guarantee capacity to a critical function, to cap a function that could otherwise drain the pool or overwhelm a database, and set to zero as an emergency stop. Provisioned concurrency is about latency and ramp: it keeps N environments initialised on a version or alias, so the first N concurrent requests never see a cold start, and because they exist before the spike, the scaling curve starts at N instead of zero. It is billed every second it exists, about eleven dollars a month per gigabyte, whether used or not, and requests above N spill over to normal on-demand environments. It does not raise the account limit and it counts against the function's reservation if there is one. So for "checkout must never be starved" I reserve; for "checkout must answer in under 100 milliseconds at 09:00 even on its first request" I provision, on a schedule and with target tracking; and for a function that needs both, I do both, with the reservation larger than the provisioned number.

Provisioned concurrency or SnapStart?

Both attack the cold start; they differ in what is left and what it costs. Provisioned concurrency leaves nothing: N environments are already initialised, and the cost is a constant charge per GB-hour plus a reduced duration rate, which pays off when the environments are busy, above roughly sixty percent utilisation, and is waste overnight unless scheduled. SnapStart leaves a restore, typically a couple of hundred milliseconds, on each new environment, and costs nothing for Java and a small cache and restore fee for Python and .NET; it scales with traffic without any capacity planning. So I pick SnapStart for spiky or unpredictable traffic with a long init, typically a Java or Spring service, where a few hundred milliseconds on the first request is acceptable. I pick provisioned concurrency for steady, latency-critical traffic where even that is too much, or where I need the ramp to start high for a known event. They cannot be combined on the same version. With SnapStart I check one thing in code review: nothing unique is created during INIT, no random seed, no UUID state, no connection, no cached credentials with an expiry, because every environment restored from the snapshot shares it; the runtime hooks are there to reseed and reconnect after restore.

A Lambda function in a VPC times out calling Secrets Manager. Why, and what changes when you attach a function to a VPC?

A function attached to a VPC sends all its traffic through a Hyperplane ENI in the subnets I chose, and those ENIs never have public IPs. So it has no internet path, even in a public subnet with an internet gateway, and Secrets Manager's public endpoint is unreachable: the call hangs until the function's timeout. The fix is either a NAT gateway in a public subnet with the function in private subnets routed to it, or an interface VPC endpoint for Secrets Manager (and a gateway endpoint for S3 and DynamoDB, which are free), with the security group allowing 443 from the function. What else changes: the ENIs are created at deploy time, per subnet and security group combination, and shared, so the old ten-second VPC cold start no longer exists, but a function sits in Pending for a minute when its VPC configuration changes, and goes Inactive after weeks without traffic. ENIs count against a per-VPC quota. The function's egress now pays NAT data processing. And the security group becomes part of the function's access, so a database's security group can reference the function's. My rule is to attach only when the function needs a private resource, a database, a cache or an internal service; a function that talks to DynamoDB, S3 and public APIs is simpler outside the VPC, protected by IAM rather than by the network.

REST API or HTTP API?

HTTP API by default: it costs a dollar a million instead of three and a half, adds less latency, has native JWT authorisers for Cognito or any OIDC provider, CORS in one setting and automatic deploys. I move to a REST API when I need something only it has: API keys and usage plans to meter and limit customers, AWS WAF directly on the API, response caching per stage, request validation and VTL mapping templates to transform requests without a function, a private API reachable only through a VPC endpoint, edge-optimised endpoints, or canary deployments at the stage. Some of those have workarounds for an HTTP API, WAF on a CloudFront distribution in front, caching in CloudFront, validation in the function, so the question is whether the workaround is cheaper than the extra $2.50 per million. For a public partner API sold by tier, REST, for the usage plans. For a mobile app's backend with Cognito users, HTTP. For an internal API between services in one account, HTTP with IAM auth, or a private REST API if it must not be reachable from the internet at all. I avoid mixing both for one product without reason, since custom domains, logging formats and authorisers differ between them.

Design authentication and authorisation for an API used by a mobile app and by partners.

Two kinds of callers, two flows. Users of the mobile app sign in through a Cognito user pool, with social or SAML federation if needed and MFA for sensitive accounts, and the app sends the access token as a bearer token. The API checks it at the gateway with a JWT authoriser on an HTTP API or a Cognito authoriser on a REST API, so no function runs to authenticate and per-route scopes decide which routes a token may call; the backend reads the user id from the claims and enforces ownership of the data itself, because the gateway knows who, not which rows. If the app also talks directly to AWS services, uploading to S3, an identity pool exchanges the token for short-lived credentials with a role scoped to the user's prefix. Partners are machines: each gets an app client with the client-credentials grant in the same or a separate user pool, scopes per partner, and a short-lived access token they cache, or SigV4 with a role in their account for AWS-native partners. If I sell tiers, I put a REST API in front with usage plans and an API key per partner for metering and quotas, never as the authentication itself. Throttles at every layer: usage plans per partner, route limits for expensive routes, WAF rate rules for the public paths. Access tokens of an hour or less, refresh tokens revocable, and a pre-token-generation trigger only if claims really need enriching, since it runs on every sign-in with a five-second limit.

A request takes 45 seconds and API Gateway returns 504. What do you do?

The integration timeout is 29 seconds, and raising it, which a REST API now allows, only moves the problem: the client still waits, a mobile network drops it, a retry starts a second 45-second job, and long requests hold concurrency. I make it asynchronous. The API accepts the request, validates it, writes a job record with an id, puts the work on a queue or starts a Step Functions execution, and returns 202 with the job id in a few milliseconds. A worker does the 45 seconds, Lambda if it fits in 15 minutes, Fargate or Batch if not, and writes the result. The client learns the result by polling a status route, by a WebSocket or AppSync subscription, or by a webhook for a server client. The job id doubles as the idempotency key, so a client that retries the POST gets the same job. If the slow part is the response size rather than the work, Lambda response streaming through a function URL or the REST API sends bytes as they are produced. And I set the function's timeout below the gateway's for the synchronous routes, so a slow call fails inside the function, where I can log it, rather than continuing to run and bill after the client has gone.

Lambda and a relational database: what goes wrong, and how do you fix it?

Connections. Each execution environment opens its own connection, so a spike to two thousand concurrent environments is two thousand connections to a database configured for a few hundred, and the database spends its memory on connections and refuses new ones. Frozen environments keep their connections open while idle, and connections that time out on the server side while an environment is frozen produce a reset on the next request. The fixes. RDS Proxy pools and multiplexes connections between the functions and the database, survives failovers faster, and can use IAM authentication; it is the default for Lambda in front of RDS or Aurora. Reserved concurrency on the function, or maximum concurrency on its event source mapping, sized to what the database can actually serve, so the ceiling is enforced by Lambda and not discovered by the database. The connection opened outside the handler and reused, with a retry on a reset connection. Short queries and short transactions, since duration times rate is concurrency and therefore connections. And where the workload allows, the Aurora Data API or DynamoDB, which have no connections to pool. The question behind the question is that Lambda scales faster than most databases can, so something has to hold the line, and it should be a setting rather than an outage.

When would you not use Lambda?

When the shape of the work fights the model. Steady high traffic: Lambda bills every millisecond of every request, and a function that is busy all day at a few hundred requests a second costs several times what the same work costs on Fargate or EC2; the crossover is roughly when a container would be thirty to fifty percent utilised. Long work: over fifteen minutes is impossible, and over a few minutes is usually cheaper and simpler as a container task or a Batch job. Long-lived connections: WebSocket servers, gRPC streams, a database driver that wants a warm pool. Large in-memory state or models that take seconds to load and should be shared across requests, since an environment serves one request at a time. Very low-latency paths where even a rare cold start breaks the SLO and provisioned concurrency is more expensive than a container. And workloads that need a specific OS, GPU, or more than ten gigabytes of memory. Lambda shines for spiky and low traffic, event handlers on S3, queues and streams, glue between services, scheduled jobs, and APIs whose traffic has a strong daily shape. The right question is not Lambda or containers for the company, but which one for each workload, measured in cost per request at the real utilisation.

What happens when the function fails, for a synchronous, an asynchronous and a polled invocation?

Synchronously, the error goes back to the caller: API Gateway turns it into a 502 or 500, the SDK raises it, and Lambda retries nothing; the caller decides. Asynchronously, Lambda has already returned 202, so it owns the retry: a function error is retried up to twice with delays, a throttle or a service error is retried with backoff for up to the maximum event age, six hours by default; after that the event goes to the on-failure destination, SQS, SNS, EventBridge, another function or S3, with the error and the original request, or it is dropped. With an event source mapping, the mapping owns it, and the source's semantics apply. For SQS, a failed batch is not deleted and comes back after the visibility timeout, and the queue's redrive policy moves it to its DLQ after maxReceiveCount; with partial batch responses only the failed messages return. For Kinesis and DynamoDB Streams, the batch is retried and the shard waits, by default until the records expire, which is why I set a maximum retry count, a maximum record age, bisect on error and an on-failure destination. In every retried case the function runs more than once for the same event, so it must be idempotent; and in every case I want a place where the failures end up that someone is alarmed on.

How do you deploy a Lambda function safely?

With versions, aliases and a gradual shift. Every deploy publishes an immutable version; clients call an alias, live, never the bare function name or $LATEST. CodeDeploy, driven by SAM, CDK or the pipeline, shifts the alias's traffic weight from the old version to the new one, canary ten percent for five minutes or linear ten percent a minute, while CloudWatch alarms on the new version's errors, throttles and p99 duration watch, and a pre-traffic hook can run a smoke test against the new version first. If an alarm fires, the alias goes back to the old version in seconds, because the old version still exists and is still warm. Provisioned concurrency, if used, must be on the new version before it takes traffic, which CodeDeploy handles when it is configured on the alias. The other half is what makes rollback possible: the function's dependencies, schema changes and event formats must be backward compatible for the length of the deployment, because both versions run at once; and the event source mappings and API integrations point at the alias, so they follow the shift. Layers and configuration changes deserve the same treatment, since a new layer version changes behaviour without a code change.

A Lambda authoriser is in front of the API. What can go wrong?

Three things, all about the cache and the concurrency. The result is cached by the identity source for the TTL, five minutes by default: a token revoked or a user removed keeps working until the cache expires, so the TTL is a security decision, not a performance one. On a REST API, the cached result is an IAM policy, and if the authoriser returns a policy that allows only the method of the first request, the next request from the same token to a different method hits the cached policy and is denied; or, worse, the authoriser returns a policy with a wildcard to fix that, and a user with access to one tenant's path is allowed every path until the cache expires. The fix is to return a policy that covers exactly what the identity may call across the whole API, or to put the tenant check in the backend. Second, with caching off or the TTL low, the authoriser runs on every request and needs the same concurrency as the API itself; when it throttles or times out, clients get a 500 or 401 that has nothing to do with them, which is why it gets its own reserved concurrency and a fast path with no database call on the hot route. Third, it is code that decides who gets in: it needs tests for expired, malformed, wrong-audience and wrong-algorithm tokens, and if the token is a standard JWT, a JWT or Cognito authoriser does the same job with no code, no cost and no concurrency.
