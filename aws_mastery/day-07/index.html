Case 1 · Day 1 · IAM

The ABAC policy that denies its own team

00:00
Target 5:00

Symptom. The payments team's role is meant to manage only instances tagged team=payments. A developer assumes the role and stops one of their own instances:

$ aws sts get-caller-identity --query Arn --output text
arn:aws:sts::111122223333:assumed-role/payments-dev/alice

$ aws ec2 stop-instances --instance-ids i-0f3a9c1d2e4b5a678
An error occurred (UnauthorizedOperation) when calling the StopInstances operation:
You are not authorized to perform this operation. User: arn:aws:sts::111122223333:assumed-role/payments-dev/alice
is not authorized to perform: ec2:StopInstances on resource: arn:aws:ec2:ap-south-1:111122223333:instance/i-0f3a9c1d2e4b5a678
because no identity-based policy allows the ec2:StopInstances action

What you can see.

$ aws ec2 describe-tags --filters Name=resource-id,Values=i-0f3a9c1d2e4b5a678 --query 'Tags[].[Key,Value]' --output text
Name    payments-worker-3
team    payments

$ aws iam get-role-policy --role-name payments-dev --policy-name abac --query PolicyDocument.Statement
[ { "Effect": "Allow",
    "Action": [ "ec2:StartInstances", "ec2:StopInstances", "ec2:RebootInstances" ],
    "Resource": "*",
    "Condition": { "StringEquals": { "aws:ResourceTag/team": "${aws:PrincipalTag/team}" } } } ]

$ aws iam list-role-tags --role-name payments-dev
{ "Tags": [] }

$ aws iam get-role --role-name payments-dev --query 'Role.[PermissionsBoundary,AssumeRolePolicyDocument.Statement[0].Action]'
[ null, "sts:AssumeRole" ]
Clues

The error says “no identity-based policy allows”. There is no explicit Deny anywhere. The Allow statement exists but did not match.

The only thing in that statement that can fail to match is the condition. Ask what ${aws:PrincipalTag/team} evaluates to for this session.

A policy variable that does not exist does not become an empty string. The condition key is simply absent, and StringEquals on an absent key is false. Where would a principal tag have come from: the role, or the session?

The fault is

The fault. ABAC compares the resource's tag with the principal's tag. The principal's tag comes from one of two places: tags on the IAM role or user, or session tags passed at AssumeRole time. This role has neither. The variable ${aws:PrincipalTag/team} therefore has no value; the condition key is missing from the request context and StringEquals evaluates to false. No Allow matched, so the implicit deny stands, which is exactly what the error message says.

How you would find it without multiple choice. Read the error: “no identity-based policy allows” means look for the Allow that should have matched, not for a Deny. Find the statement, find its condition, and evaluate each key by hand for this session. aws:ResourceTag/team is payments; aws:PrincipalTag/team is unset. The policy simulator with the role shows the same thing in a minute if you remember to add the principal tags to the simulation; the trap is that it lets you type them in and then the simulation passes while reality fails.

Fix. Tag the role, since this role belongs to one team. Session tags are the answer when one role is shared by many teams or when an identity provider supplies the attribute; then the trust policy must also allow sts:TagSession.

aws iam tag-role --role-name payments-dev --tags Key=team,Value=payments
# or, for session tags:
aws sts assume-role --role-arn arn:aws:iam::111122223333:role/payments-dev --role-session-name alice \
  --tags Key=team,Value=payments        # needs "sts:TagSession" in the trust policy

Why D is a trap. The caller ARN shows an assumed role, so assumption worked; sts:TagSession is only needed when tags are passed. C is wrong because EC2 supports resource-level permissions on instances, which is what makes ABAC on EC2 possible at all. A is wrong because aws:ResourceTag is the global key and works for EC2; ec2:ResourceTag is an older alias.

Case 2 · Day 2 · VPC

The private subnet that cannot download updates

00:00
Target 5:00

Symptom. A new VPC was built from a hardened template. Application servers in the private subnet cannot run dnf update and cannot call any public API. Every connection hangs and then times out. There is no TLS error and no connection refused. The NAT Gateway shows as available.

What you can see.

$ aws ec2 describe-route-tables --filters Name=association.subnet-id,Values=subnet-0priv1a --query 'RouteTables[].Routes[].[DestinationCidrBlock,GatewayId,NatGatewayId,State]' --output text
10.0.0.0/16   local   None            active
0.0.0.0/0     None    nat-0a7c3e9f1b2d4c6e8   active

$ aws ec2 describe-nat-gateways --nat-gateway-ids nat-0a7c3e9f1b2d4c6e8 --query 'NatGateways[].[State,SubnetId,ConnectivityType]' --output text
available   subnet-0pub1a   public

$ aws ec2 describe-route-tables --filters Name=association.subnet-id,Values=subnet-0pub1a --query 'RouteTables[].Routes[].[DestinationCidrBlock,GatewayId]' --output text
10.0.0.0/16   local
0.0.0.0/0     igw-0d2f8a1c3b5e7f9a0

$ aws ec2 describe-security-groups --group-ids sg-0app --query 'SecurityGroups[].IpPermissionsEgress[].[IpProtocol,IpRanges[0].CidrIp]' --output text
-1   0.0.0.0/0

$ aws ec2 describe-network-acls --filters Name=association.subnet-id,Values=subnet-0priv1a \
    --query 'NetworkAcls[].Entries[].[Egress,RuleNumber,Protocol,PortRange.From,PortRange.To,CidrBlock,RuleAction]' --output text
False  100    6    22     22     10.0.0.0/16   allow
False  110    6    8080   8080   10.0.0.0/16   allow
False  32767  -1   None   None   0.0.0.0/0     deny
True   100    -1   None   None   0.0.0.0/0     allow
True   32767  -1   None   None   0.0.0.0/0     deny

# Flow Logs, one attempt to reach 93.184.216.34:443 from the app server 10.0.11.14
10.0.11.14      93.184.216.34   41712  443    6   ACCEPT
93.184.216.34   10.0.11.14      443    41712  6   REJECT
Clues

Read the two flow-log lines as a pair. The outbound SYN was accepted. Something rejected the reply on the way back in.

Two things sit between the internet and the instance on the way back: the security group and the network ACL. One of them is stateful and one is not.

The reply arrives on destination port 41712, an ephemeral port. Which inbound rule in the NACL allows that?

The fault is

The fault. The hardened template wrote an inbound NACL that only allows the ports the subnet serves, and forgot that a NACL also sees the replies to connections the subnet opens. The SYN to port 443 leaves under the outbound allow-all rule; the SYN-ACK comes back to port 41712, matches no inbound rule, and hits the default deny. Every outbound connection fails identically, as a timeout, because the instance never sees the reply.

How you would find it. A timeout means the packet or its reply did not arrive, so start with the path, not with permissions. Route table: fine. NAT Gateway: available, in a public subnet with an IGW route, so A is ruled out in one command. Security group egress: open. Then the two stateless things: the NACL, and Flow Logs to prove it. The REJECT line with the ephemeral destination port is the whole diagnosis. Reachability Analyzer from the ENI to the internet would name the NACL entry explicitly.

Fix. Add the ephemeral inbound rule, and remember that the public subnet's NACL needs the same for the NAT Gateway's replies if it was hardened the same way.

aws ec2 create-network-acl-entry --network-acl-id acl-0priv --ingress --rule-number 120 \
  --protocol 6 --port-range From=1024,To=65535 --cidr-block 0.0.0.0/0 --rule-action allow

Why C is a trap. Security groups are stateful: the reply to an allowed outbound connection is always allowed in, no inbound rule needed. If the security group were the problem, Flow Logs would show the REJECT at the ENI the same way, so the flow-log line alone does not separate B from C; the rule listing does. D is wrong: using a NAT Gateway in another AZ works, it just costs cross-AZ data transfer and fails with that AZ.

Case 3 · Day 3 · Transit Gateway

Dev can still reach prod after “segmentation”

00:00
Target 5:00

Symptom. The network team split the Transit Gateway into separate route tables for dev, prod and shared services. A penetration test a week later shows a dev instance reaching prod's internal load balancer on 10.20.3.10:443 and getting a 200.

What you can see.

$ aws ec2 describe-transit-gateways --query 'TransitGateways[].Options.[DefaultRouteTableAssociation,DefaultRouteTablePropagation]' --output text
disable   enable

$ aws ec2 get-transit-gateway-route-table-associations --transit-gateway-route-table-id tgw-rtb-dev \
    --query 'Associations[].[TransitGatewayAttachmentId,ResourceType,State]' --output text
tgw-attach-dev      vpc   associated

$ aws ec2 get-transit-gateway-route-table-associations --transit-gateway-route-table-id tgw-rtb-prod \
    --query 'Associations[].[TransitGatewayAttachmentId,ResourceType,State]' --output text
tgw-attach-prod     vpc   associated

$ aws ec2 get-transit-gateway-route-table-propagations --transit-gateway-route-table-id tgw-rtb-dev \
    --query 'TransitGatewayRouteTablePropagations[].[TransitGatewayAttachmentId,State]' --output text
tgw-attach-dev      enabled
tgw-attach-prod     enabled
tgw-attach-shared   enabled

$ aws ec2 search-transit-gateway-routes --transit-gateway-route-table-id tgw-rtb-dev --filters Name=state,Values=active \
    --query 'Routes[].[DestinationCidrBlock,Type,TransitGatewayAttachments[0].TransitGatewayAttachmentId]' --output text
10.10.0.0/16   propagated   tgw-attach-dev
10.20.0.0/16   propagated   tgw-attach-prod
10.0.0.0/16    propagated   tgw-attach-shared

# dev VPC route table
10.10.0.0/16  local
10.0.0.0/8    tgw-0c4e...
Clues

Association decides which table an attachment's incoming packets are looked up in. Propagation decides which tables learn an attachment's CIDR. They are set independently.

The dev table knows a route to 10.20.0.0/16. Where did it learn it from, and should it have?

Look at the Transit Gateway options. One of the two defaults was left on.

The fault is

The fault. Segmentation on a Transit Gateway is two separate decisions per attachment. The team made the first: each attachment is associated with its own table, so packets from dev are looked up in the dev table. They left the second at its default: every new attachment propagates into every table that has default propagation on, so the dev table learned 10.20.0.0/16 from the prod attachment. A packet from dev to prod is looked up in the dev table, finds the propagated route, and is forwarded. Prod's own table has the dev route for the same reason, so the reply comes back and the connection completes.

How you would find it. Start from the table the packet is looked up in: the one associated with the source attachment. List its routes. If a route to the destination exists, the segmentation is not there, whatever the diagram says. The search-transit-gateway-routes output is the proof; the route's type, propagated, and its attachment tell you how it got there. Then describe-transit-gateways shows why.

Fix. Turn off default propagation, remove prod's propagation from the dev table (and dev's from prod), propagate both only into the shared table, and add static routes from the shared table back. Add blackhole routes as a belt-and-braces measure so that a future propagation cannot reopen the path.

aws ec2 modify-transit-gateway --transit-gateway-id tgw-0c4e... --options DefaultRouteTablePropagation=disable
aws ec2 disable-transit-gateway-route-table-propagation --transit-gateway-route-table-id tgw-rtb-dev  --transit-gateway-attachment-id tgw-attach-prod
aws ec2 disable-transit-gateway-route-table-propagation --transit-gateway-route-table-id tgw-rtb-prod --transit-gateway-attachment-id tgw-attach-dev
aws ec2 create-transit-gateway-route --transit-gateway-route-table-id tgw-rtb-dev --destination-cidr-block 10.20.0.0/16 --blackhole

Why C is a trap. The VPC route is coarse but harmless: the Transit Gateway's own table decides what to do with a packet, and a blackhole or missing route there drops it. Making the VPC route precise is good practice, not the fault. A would make dev behave like prod, the opposite of segmentation. D gets cause and effect backwards: prod should not even receive the packet.

Case 4 · Day 3 · Route 53 Resolver

On-premises can ping the database but cannot name it

00:00
Target 5:00

Symptom. Direct Connect is up. Servers in the data centre reach the database at 10.40.5.20 by IP. The application is configured with db.internal.example, which resolves inside the VPC but not on premises. The on-premises DNS team added a conditional forwarder for internal.example pointing at 10.40.0.2, “the VPC DNS server, as documented”.

What you can see.

# from an EC2 instance in the VPC (10.40.0.0/16)
$ dig +short db.internal.example
10.40.5.20

$ aws route53 list-hosted-zones-by-vpc --vpc-id vpc-0a1b2c3d --vpc-region ap-south-1 --query 'HostedZoneSummaries[].Name' --output text
internal.example.

$ aws ec2 describe-vpc-attribute --vpc-id vpc-0a1b2c3d --attribute enableDnsSupport --query EnableDnsSupport.Value
true

# from an on-premises server (192.168.10.5)
$ ping -c1 10.40.5.20
64 bytes from 10.40.5.20: icmp_seq=1 ttl=62 time=4.1 ms

$ dig @10.40.0.2 db.internal.example
;; connection timed out; no servers could be reached

$ aws route53resolver list-resolver-endpoints --query 'ResolverEndpoints[].[Name,Direction,Status]' --output text
(empty)
Clues

The private hosted zone works: an instance in the VPC resolves the name. The problem is only with who is asking.

The .2 address is not a server in the VPC. It is a link-local service that answers only on ENIs inside the VPC. Packets to it from across Direct Connect are dropped before any DNS happens.

There is a Route 53 Resolver feature whose entire purpose is to give the .2 resolver real, routable IP addresses in your subnets. The last command shows it was never created.

The fault is

The fault. The Amazon-provided resolver at VPC CIDR + 2 is reachable only from network interfaces in that VPC; it is not on any route that Direct Connect or VPN can deliver to. A conditional forwarder pointed at it times out, which looks like a routing problem and is not. The Resolver inbound endpoint exists for exactly this: it creates ENIs with real addresses in two subnets of your choice, each a front door to the same resolver, and the on-premises forwarder targets those addresses. Outbound endpoints are the reverse, for VPC workloads that need to resolve on-premises names.

How you would find it. Split the problem in two with the first two commands: does the zone resolve from inside the VPC? Yes, so the zone, its association and the VPC's DNS attributes are fine. Then: can on-premises reach the resolver it was given? The timeout against an address that pings in the same /16 elsewhere is the clue that the .2 address is special. list-resolver-endpoints returning nothing confirms what was never built.

Fix.

aws route53resolver create-resolver-endpoint --name inbound-dc --direction INBOUND --creator-request-id $(uuidgen) \
  --security-group-ids sg-0dns \
  --ip-addresses SubnetId=subnet-0a,Ip=10.40.1.53 SubnetId=subnet-0b,Ip=10.40.2.53
# sg-0dns: allow TCP and UDP 53 from 192.168.0.0/16
# on-premises: conditional forwarder for internal.example -> 10.40.1.53, 10.40.2.53

Why B is a trap. Route advertisement is per prefix, and it is plausible that a /24 was missed; but the VIF advertises the VPC CIDR as one block, and in any case the fault would remain after fixing the route, because .2 does not answer off-VPC traffic. A is ruled out by the first command. D: enableDnsHostnames controls whether instances get public DNS names; it does not gate private zone resolution, and enableDnsSupport is already true.

Case 5 · Day 4 · EC2 and IMDS

Containers lose their credentials after the security change

00:00
Target 5:00

Symptom. On Monday the security team changed the launch template so that every instance requires IMDSv2. Since the next rollout, an application that runs in Docker containers on those instances, using the instance profile for credentials, logs Unable to locate credentials and nothing works. A test process started directly on the host, with the same SDK version, works.

What you can see.

$ aws ec2 describe-instances --instance-ids i-0b1c2d3e4f5a6b7c8 --query 'Reservations[].Instances[].[IamInstanceProfile.Arn,MetadataOptions]' --output json
[ [ "arn:aws:iam::111122223333:instance-profile/app-host",
    { "State": "applied", "HttpTokens": "required", "HttpPutResponseHopLimit": 1,
      "HttpEndpoint": "enabled", "InstanceMetadataTags": "disabled" } ] ]

# on the host
$ TOKEN=$(curl -s -X PUT http://169.254.169.254/latest/api/token -H "X-aws-ec2-metadata-token-ttl-seconds: 60")
$ curl -s -H "X-aws-ec2-metadata-token: $TOKEN" http://169.254.169.254/latest/meta-data/iam/security-credentials/
app-host

# inside a container (default bridge network)
$ docker run --rm curlimages/curl -s -m 5 -X PUT http://169.254.169.254/latest/api/token -H "X-aws-ec2-metadata-token-ttl-seconds: 60"
(no output; exit 28, timed out)
$ docker run --rm curlimages/curl -s -i http://169.254.169.254/latest/meta-data/
HTTP/1.1 401 Unauthorized

$ docker run --rm --network host curlimages/curl -s -X PUT http://169.254.169.254/latest/api/token -H "X-aws-ec2-metadata-token-ttl-seconds: 60"
AQAAAN1q...   (a token)
Clues

The same request works from the host and from a container on the host network, and fails from a container on the bridge network. The difference is one network hop.

The 401 on the plain GET is correct behaviour for IMDSv2-required; it is not the fault. The fault is that the PUT for a token never gets an answer.

Read the metadata options again. One number is a hop count.

The fault is

The fault. IMDSv2's protection against SSRF and misconfigured proxies is the token PUT, and part of that protection is the hop limit: the response packet carrying the token is sent with an IP TTL equal to HttpPutResponseHopLimit. At 1, the packet reaches the instance's network stack and no further. A container on the bridge network is one NAT hop away, so the TTL expires and the token never arrives. The subsequent GET without a token is refused with 401, which is the designed behaviour. Everything looks like “the container cannot do IMDSv2” when the real fault is a single integer in the launch template.

How you would find it. The pattern “host works, container does not” points at the network path between them before anything else. Reproducing the token PUT from both places with a short timeout takes a minute. The 401 is a red herring that costs people hours because they then go and read about SDK versions. Once you see that the PUT times out, describe-instances shows the hop limit.

Fix. Set the hop limit to 2 in the launch template and on running instances. That is what AWS recommends for containers on EC2. Better still, stop containers from using the host's role at all: ECS task roles or EKS Pod Identity give each workload its own credentials and leave the hop limit at 1.

aws ec2 modify-instance-metadata-options --instance-id i-0b1c2d3e4f5a6b7c8 --http-tokens required --http-put-response-hop-limit 2

Why A is a trap. It is the most common wrong answer because it fits the 401. But the host test uses the same SDK and works. C is ruled out by the profile ARN in the output and by the fact that the host obtains the credential name live. D: security groups are on the ENI, not per container, and never apply to the link-local metadata address.

Case 6 · Day 4 · EBS

The database paid for 16,000 IOPS and gets 3,600

00:00
Target 5:00

Symptom. PostgreSQL on an EC2 instance became slow after a nightly batch job was added. The team upgraded the data volume from gp3 to io2 with 16,000 provisioned IOPS. Nothing changed. Queries are fine for the first half hour of the batch, then latency climbs and stays high until it finishes.

What you can see.

$ aws ec2 describe-volumes --volume-ids vol-0db --query 'Volumes[].[VolumeType,Size,Iops,Throughput,Attachments[0].InstanceId]' --output text
io2   500   16000   None   i-0db

$ aws ec2 describe-instances --instance-ids i-0db --query 'Reservations[].Instances[].[InstanceType,EbsOptimized]' --output text
m5.large   True

# CloudWatch, 1-minute period, during the batch (values per second)
VolumeReadOps + VolumeWriteOps   first 30 min: ~14,800/s   then: ~3,600/s flat for 2 h
VolumeQueueLength                first 30 min: 4            then: 38
VolumeThroughputPercentage       100 throughout (io2 reports this when the volume is not the limit)
EBSIOBalance%   (instance metric) 100 -> 0 over the first 30 min, then 0
EBSByteBalance% (instance metric) 100 -> 61
Clues

Two components can limit IOPS: the volume and the instance it is attached to. The volume metric says the volume is not the limit.

Something is being burst and then exhausted over exactly thirty minutes. io2 volumes do not burst. Instances do.

An m5.large has a baseline of about 3,600 EBS IOPS and can burst to 18,750 for 30 minutes a day. The number in the graph is the baseline.

The fault is

The fault. Each EBS volume has a performance figure, and so does each instance type: a baseline IOPS and bandwidth, plus a burst balance that lets smaller instances exceed their baseline for 30 minutes in a 24-hour window. A volume cannot deliver more than the instance's share. An m5.large tops out at about 3,600 IOPS sustained; the 16,000 IOPS volume is a Ferrari in a car park. The graph is the textbook shape: full speed while EBSIOBalance% drains, then a flat line at the baseline with the queue backing up.

How you would find it. “Flat ceiling after a period of good performance” is a burst-credit signature; look for a balance metric. The volume says VolumeThroughputPercentage 100, which rules out the volume. The instance metrics EBSIOBalance% and EBSByteBalance% exist for exactly this question. Then check the instance type's EBS limits in the EC2 instance-types table. Day 4's rule: when sizing storage, size the instance for the volume as well as the volume for the workload.

Fix. Move to an instance whose baseline covers the need: m5.4xlarge (18,750 IOPS baseline) or better a memory-optimised r6i.2xlarge (12,000 baseline; 40,000 burst) or r6i.4xlarge (20,000 baseline). Nitro instances with higher baselines are usually cheaper than the IOPS being wasted. Then ask whether 16,000 provisioned IOPS were needed at all, or whether gp3 at 16,000 IOPS is enough at a third of the price.

aws ec2 stop-instances --instance-ids i-0db
aws ec2 modify-instance-attribute --instance-id i-0db --instance-type '{"Value": "r6i.2xlarge"}'
aws ec2 start-instances --instance-ids i-0db

Why A is a trap. The ratio is real but 500 GiB × 500 = 250,000, far above 16,000, and the API rejects an invalid ratio rather than silently accepting it. C: volume modifications report optimizing during the change and the new type applies live; there is no pending state visible as the old type. D would show as a periodic spike, not a sustained plateau after exactly the burst window.

Case 7 · Day 5 · ALB

Every target is unhealthy, and the app is fine

00:00
Target 5:00

Symptom. A new service was put behind an Application Load Balancer with an HTTPS listener. Every request through the ALB returns 503 Service Unavailable. The instances are running, the application answers on the instance, and the on-call engineer can log in and fetch pages with curl.

What you can see.

$ aws elbv2 describe-target-health --target-group-arn arn:...:targetgroup/web/abc --query 'TargetHealthDescriptions[].[Target.Id,TargetHealth.State,TargetHealth.Reason,TargetHealth.Description]' --output text
i-0web1   unhealthy   Target.ResponseCodeMismatch   Health checks failed with these codes: [301]
i-0web2   unhealthy   Target.ResponseCodeMismatch   Health checks failed with these codes: [301]

$ aws elbv2 describe-target-groups --target-group-arns arn:...:targetgroup/web/abc \
    --query 'TargetGroups[].[Protocol,Port,HealthCheckProtocol,HealthCheckPort,HealthCheckPath,Matcher.HttpCode]' --output text
HTTP   80   HTTP   traffic-port   /health   200

# on i-0web1
$ curl -s -i http://localhost/health | head -3
HTTP/1.1 301 Moved Permanently
Location: https://localhost/health

$ curl -s -i -H "X-Forwarded-Proto: https" http://localhost/health | head -1
HTTP/1.1 200 OK

# nginx.conf
if ($http_x_forwarded_proto != "https") { return 301 https://$host$request_uri; }
Clues

The reason code is the diagnosis. ResponseCodeMismatch means the health checker connected, got an HTTP answer, and the status was not in the matcher. The network is fine.

User requests carry X-Forwarded-Proto: https because the listener is HTTPS. The health checker is not a user request and sends no such header.

Which status does the app return to a request that has no X-Forwarded-Proto?

The fault is

The fault. TLS terminates at the ALB, so the targets see plain HTTP and learn the original scheme from X-Forwarded-Proto. The application's “force HTTPS” rule redirects anything without that header, which is correct for users and wrong for the one client that never sets it: the health checker. It gets a 301 for /health, the matcher wants 200, the target is marked unhealthy, and with no healthy target the ALB returns 503 to everyone. The application is perfectly healthy; it is just saying so in the wrong status code.

How you would find it. 503 from an ALB with no healthy targets is a target-health problem by definition, so the first command is describe-target-health, and the reason code sorts the possibilities: Timeout means security group or NACL; ResponseCodeMismatch means the app answered; FailedHealthChecks with a connection error means nothing listening. From there, reproduce the exact health-check request on the target: HTTP, the health-check port, the path, no extra headers.

Fix. Exempt the health path from the redirect. Expanding the matcher to 200,301 also “works” and is a mistake, because then a target that redirects everything, or has lost its backend and only its redirect rule still runs, looks healthy.

# nginx
location = /health { return 200 "ok\n"; }
# everything else keeps the redirect

Why A is a trap. A security-group block produces Target.Timeout, never a status code. C would be a 404. D is simply false: an HTTPS listener forwarding to HTTP targets is the normal pattern.

Case 8 · Day 5 · Auto Scaling

The group that scales out and eats its own instances

Target 5:00

Symptom. Every morning at nine the CPU alarm fires and the Auto Scaling group adds instances, but the alarm never clears, the service stays slow, and the bill shows ten times the expected instance-hours. In the console, instances appear and vanish every few minutes.

What you can see.

$ aws autoscaling describe-scaling-activities --auto-scaling-group-name web --max-items 6 --query 'Activities[].[StartTime,Cause]' --output text
2026-10-07T03:41:10Z  At 2026-10-07T03:41:08Z an instance was taken out of service in response to an ELB system health check failure.

2026-10-07T03:32:48Z  At 2026-10-07T03:32:46Z a user request created an instance ... policy cpu-target ... capacity from 4 to 6.
...

$ aws autoscaling describe-auto-scaling-groups --auto-scaling-group-names web \
    --query 'AutoScalingGroups[].[HealthCheckType,HealthCheckGracePeriod,DefaultInstanceWarmup,MinSize,DesiredCapacity,MaxSize]' --output text
ELB   60   None   4   6   12

$ aws elbv2 describe-target-groups --names web --query 'TargetGroups[].[HealthCheckIntervalSeconds,HealthyThresholdCount,UnhealthyThresholdCount]' --output text
10   2   3

# EC2 console output of a new instance (user data: install packages, pull a 1.2 GB image, start the service)
[   12.4] cloud-init: running user data
[  104.7] docker: pulling app:4.2 ...
[  188.2] app: listening on :8080
[  191.0] app: GET /health 200
Clues

Count the seconds. The instance is ready at about 190 s. The group starts believing ELB health checks after 60 s. The target group declares a target unhealthy after 3 × 10 s of failures.

So from roughly 90 s after launch the ELB says unhealthy, the group believes it, and replaces the instance, which then starts the same 190-second boot.

The grace period is the only setting here whose job is to describe how long a boot takes.

The fault is

The fault. With HealthCheckType ELB, the group trusts the target group's opinion of each instance once the grace period has passed. The grace period is 60 s; the application is not listening until about 190 s. Between 60 s and 190 s the target group reports unhealthy, the group terminates the instance, launches another, and the cycle repeats every four minutes. Desired capacity never actually rises, so CPU stays high, the alarm stays in ALARM, and the group keeps paying for instances that live for four minutes each.

How you would find it. The scaling activity history is the first stop for any Auto Scaling mystery, and the cause text here says exactly what happened: “taken out of service in response to an ELB system health check failure”, over and over, a few minutes after each launch. Then compare three numbers: grace period, boot time from the console log, and the health check's time-to-unhealthy. Day 5's rule: the grace period must exceed the slowest boot you will ever see, with margin.

Fix. Set the grace period above the boot time, then remove the boot time: bake the image into the AMI with Image Builder so the instance is ready in 30 s, and consider a warm pool for the morning peak. Also set DefaultInstanceWarmup so the policy stops counting instances that are still starting.

aws autoscaling update-auto-scaling-group --auto-scaling-group-name web --health-check-grace-period 300 --default-instance-warmup 240

Why A is a trap. The health check settings are ordinary, and they are the ones that make deploys cut over quickly; they only matter here because the grace period does not cover the boot. C describes a real second problem (and the fix includes it), but scale-in by policy would appear as a policy activity, not as an ELB health check failure. D is backwards: ELB health checks are the better signal for instance replacement; the problem is when they are consulted, not whether.

Case 9 · Days 2 and 6 · S3 and VPC endpoints

The same role works from a laptop and fails from the VPC

00:00
Target 5:00

Symptom. A Lambda function in a private subnet reads an object from app-assets-prod and gets AccessDenied. A developer assumes the function's role on their laptop, runs the same get-object, and it succeeds.

What you can see.

# CloudTrail, the failed call
{ "eventName": "GetObject", "errorCode": "AccessDenied",
  "userIdentity": { "arn": "arn:aws:sts::111122223333:assumed-role/asset-reader/asset-fn" },
  "sourceIPAddress": "10.0.12.40", "vpcEndpointId": "vpce-0a1b2c3d4e5f6a7b8",
  "requestParameters": { "bucketName": "app-assets-prod", "key": "banners/q4.png" } }

# the role's policy
{ "Effect": "Allow", "Action": ["s3:GetObject"], "Resource": "arn:aws:s3:::app-assets-prod/*" }

# bucket policy
{ "Effect": "Allow", "Principal": { "AWS": "arn:aws:iam::111122223333:role/asset-reader" },
  "Action": "s3:GetObject", "Resource": "arn:aws:s3:::app-assets-prod/*" }

$ aws s3api head-object --bucket app-assets-prod --key banners/q4.png --query ServerSideEncryption
"AES256"

$ aws ec2 describe-vpc-endpoints --vpc-endpoint-ids vpce-0a1b2c3d4e5f6a7b8 --query 'VpcEndpoints[].[ServiceName,VpcEndpointType,PolicyDocument]' --output text
com.amazonaws.ap-south-1.s3   Gateway   {"Statement":[{"Effect":"Allow","Principal":"*","Action":"s3:*",
  "Resource":["arn:aws:s3:::central-logs","arn:aws:s3:::central-logs/*"]}]}
Clues

Same identity, same object, different result. The only difference between the two calls is the path the request took. CloudTrail records that path in one field.

A request that passes through a VPC endpoint is subject to one more policy than a request from the internet. Day 6 listed it among the seven layers.

Read the endpoint policy's Resource list and look for the bucket name.

The fault is

The fault. The gateway endpoint was created for a logging pipeline with a policy scoped to one bucket, and then the whole private subnet started using it, because a gateway endpoint is a route table entry and every S3 request from that subnet goes through it. The endpoint policy is evaluated alongside IAM and the bucket policy, and it does not allow app-assets-prod, so the request fails. From the laptop the request goes over the internet, the endpoint policy is not in the path, and everything that is in the path allows.

How you would find it. An AccessDenied with the same identity succeeding elsewhere is a path difference, and CloudTrail's vpcEndpointId field names the path. Walk the Day 6 layers for that path: SCP, IAM (allows), bucket policy (allows), Block Public Access (irrelevant, not public), object encryption (SSE-S3, no key policy), endpoint policy: does not allow. The laptop test is not a waste of time; it is the control experiment that halves the search.

Fix. Decide what the endpoint policy is for. If it is a guardrail against exfiltration, extend it to the account's buckets by condition rather than by name, and keep it. If it was never meant as a guardrail, open it. Then put a condition in the bucket policy requiring this endpoint, so the control is deliberate in both places.

{ "Effect": "Allow", "Principal": "*", "Action": "s3:*", "Resource": "*",
  "Condition": { "StringEquals": { "aws:ResourceAccount": "111122223333" } } }

Why C is a trap. head-object shows AES256, which is SSE-S3 and needs no KMS permission; and the developer assumed the function's role, so there is no “own session” with extra rights. A is wrong because the bucket policy shown has no condition. D: without a route the request would time out and there would be no CloudTrail event at all, since S3 never received it.

Case 10 · Days 1 and 6 · S3 and KMS

PUT works, LIST works, GET says no

00:00
Target 5:00

Symptom. A reporting service uses the role report-reader. It can list the bucket, it can upload its own files, and it can read objects under public-reports/. Reading anything under exports/ returns AccessDenied. The objects under exports/ are written by a different role, export-writer.

What you can see.

$ aws s3api head-object --bucket reports-prod --key exports/2026-10-06.csv --query '[ServerSideEncryption,SSEKMSKeyId]'
[ "aws:kms", "arn:aws:kms:ap-south-1:111122223333:key/9f1e2d3c-4b5a-6978-8f0e-1d2c3b4a5968" ]

$ aws s3api head-object --bucket reports-prod --key public-reports/summary.csv --query '[ServerSideEncryption,SSEKMSKeyId]'
[ "AES256", null ]

# CloudTrail, in order
GetObject    errorCode AccessDenied   userIdentity report-reader   key exports/2026-10-06.csv
Decrypt      errorCode AccessDenied   userIdentity report-reader   errorMessage "User: arn:aws:sts::111122223333:assumed-role/report-reader/svc is not authorized to perform: kms:Decrypt on resource: arn:aws:kms:...:key/9f1e... because no resource-based policy allows the kms:Decrypt action"

# report-reader identity policy
{ "Effect": "Allow", "Action": ["s3:GetObject","s3:PutObject","s3:ListBucket"], "Resource": ["arn:aws:s3:::reports-prod","arn:aws:s3:::reports-prod/*"] },
{ "Effect": "Allow", "Action": ["kms:Decrypt"], "Resource": "arn:aws:kms:ap-south-1:111122223333:key/9f1e2d3c-4b5a-6978-8f0e-1d2c3b4a5968" }

$ aws kms get-key-policy --key-id 9f1e2d3c-4b5a-6978-8f0e-1d2c3b4a5968 --policy-name default --output text
{ "Statement": [
  { "Sid": "Admins",  "Effect": "Allow", "Principal": { "AWS": "arn:aws:iam::111122223333:role/kms-admin" },     "Action": ["kms:Create*","kms:Describe*","kms:Enable*","kms:Put*","kms:Update*","kms:Revoke*","kms:Disable*","kms:Get*","kms:Delete*","kms:ScheduleKeyDeletion"], "Resource": "*" },
  { "Sid": "Writer",  "Effect": "Allow", "Principal": { "AWS": "arn:aws:iam::111122223333:role/export-writer" }, "Action": ["kms:GenerateDataKey*","kms:Encrypt","kms:Decrypt"], "Resource": "*" } ] }
Clues

The S3 permissions are fine: the same role reads public-reports/. The difference between the two prefixes is in the head-object output.

The second CloudTrail line is the real error. Read its message to the end: “no resource-based policy allows”. For KMS, the resource-based policy is the key policy.

An IAM policy can grant KMS permissions only if the key policy lets IAM do so, which is what the usual "Principal": {"AWS": "arn:aws:iam::ACCOUNT:root"} statement is for. Look for it.

The fault is

The fault. KMS is the one service where the resource policy is not optional and does not merge with IAM by default. A key policy that contains no statement for the account root principal does not “let IAM in”, so the role's identity-based kms:Decrypt is irrelevant; only the principals named in the key policy can use the key. export-writer is named and can write. report-reader is not, so when S3 asks KMS to decrypt the data key on the reader's behalf, KMS refuses, and S3 reports the refusal as its own AccessDenied. Reading public-reports/ works because those objects use SSE-S3, which needs no key.

How you would find it. “GET fails, PUT works, same bucket” is the Day 6 signature for encryption; head-object on a failing key and on a working key makes it concrete in two commands. CloudTrail then shows the KMS Decrypt failure next to the S3 call, and its message literally says which kind of policy is missing. Finally the key policy, read for two things: is the caller named, and is there a root statement that delegates to IAM? Neither, so the diagnosis is complete.

Fix. Either add the reader to the key policy, or add the standard root statement and let IAM policies decide, which scales better across many roles. Grants are the third option for temporary or programmatic access.

{ "Sid": "EnableIAM", "Effect": "Allow",
  "Principal": { "AWS": "arn:aws:iam::111122223333:root" }, "Action": "kms:*", "Resource": "*" }
# then the role's own kms:Decrypt statement starts to work

Why C is a trap. Object ownership would also produce “owner cannot read what another principal wrote”, and it is the first thing many people reach for. But head-object succeeded, which it would not against a foreign-owned object with no grant, and CloudTrail points at KMS, not at S3. A: GetObjectVersion is only needed when a version id is specified. D describes a common PUT-side condition and cannot affect GET.

Explain it out loud

Can you find each fault in under five minutes? What makes that possible?

Yes, if I let the error decide where I look instead of starting from the diagram. A timeout means the request never arrived, so I follow the packet: route table, security group, NACL in both directions, the gateway or endpoint in the path, Flow Logs to prove where it died. An AccessDenied means the request arrived and one layer refused it, so I go to CloudTrail, read the message to the end because it usually names the kind of policy that is missing, and walk the layers in order: SCP, boundary, identity policy, resource policy, endpoint policy, key policy. A 5xx from a load balancer means the network is fine and the target is unhealthy, so I read the target health reason code and reproduce the exact health-check request on the target. A flat ceiling means nothing is wrong and something is at a limit, so I find the balance or throttle metric and compare it with the quota of the smallest component in the path. The second half of being fast is the control experiment: find the version of the request that works, and the single difference between it and the one that fails is usually the answer.

You have an AccessDenied and the policy simulator says the call is allowed. What now?

The simulator evaluates the policies it is shown with the context it is given, and the real request has a different context. I ask what the simulator could not see. The request may have come through a VPC endpoint with its own policy, or the object may be SSE-KMS encrypted with a key whose policy does not include the caller, and the simulator does not evaluate either. The session may lack tags or a source identity that a condition needs; the simulator lets me type them in, reality does not. The caller may be a session with a session policy that narrowed the role, or the account may have an SCP that the simulator only includes if I run it from the right account. So I go to CloudTrail, find the actual event, and read errorMessage, vpcEndpointId and the neighbouring KMS event, because the real evaluation leaves its reason in the log.

Timeout, connection refused, connection reset, 502, 503, 504: what does each one tell you?

A timeout means no reply at all: the packet or its answer was dropped on the way, so it is routing, a security group, a NACL, or a destination that does not exist. Connection refused means the packet arrived at a host and nothing was listening on that port: the process is down or on another port, and the network is innocent. Connection reset means something accepted the connection and then tore it down: a process that crashed, a TLS mismatch, or an idle timeout on one side shorter than the other's. From a load balancer, 503 means it has no healthy target to send to, 504 means a target took longer than the idle timeout to answer, and 502 means the target answered with something the load balancer could not use: a closed connection, a malformed response, or a target that went away between the health check and the request, which is what a deploy without connection draining looks like. Each one tells me whether to open the network tools, the process tools, or the load balancer's target health page.

You fixed the fault. What do you do before you close the ticket?

Three things. I check whether the same fault exists anywhere else, because a hardened NACL template or a scoped endpoint policy was applied by something that applied it in more than one place; a Config rule or a quick script across accounts answers that. I make the fault impossible to repeat silently: an alarm on the signal that would have caught it earlier, such as unhealthy host count, EBSIOBalance%, or an Access Analyzer finding, and where possible a guardrail, such as an SCP that blocks disabling the setting or a launch-template default for the hop limit. And I write it down in a form the next on-call engineer can use at three in the morning: symptom, the one command that shows it, the fix. That last line is the whole value of this week.
