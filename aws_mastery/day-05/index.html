Load Balancing and Auto Scaling

Yesterday you opened one instance. One instance is a single point of failure, so today you put a fleet behind a load balancer and let an Auto Scaling group keep the fleet at the right size. How does the load balancer decide where a request goes, and when does it stop using a target? How does the group know that it needs more instances, and how long until they help? The centre of the page is one deploy: an instance leaves, a new one arrives, and for 30 seconds some clients get a 502. Which settings decided that?

The diagram

Full picture: a fleet behind a load balancer. Clients resolve a DNS name and reach a load balancer node in one of the AZs. The listener ends TLS and its rules choose a target group. Each node sends requests to the healthy targets, in every AZ when cross-zone is on. A target that fails its health check gets no requests. A target that leaves is draining: it finishes what it has and gets nothing new. The instances belong to an Auto Scaling group, which keeps the desired number running and changes that number when a scaling policy asks. Lifecycle hooks make the group wait at launch and at termination, and a warm pool keeps prepared instances ready. Instance refresh replaces the fleet in batches. A Network Load Balancer does the same job at layer 4, and Global Accelerator gives fixed addresses in front of it all.

How it works inside

What a load balancer is made of

  • A load balancer is not one machine. It is a DNS name and a set of nodes, at least one in every AZ that you enable.
  • An ALB needs two AZs or more. In each, it needs a subnet of /27 or larger with 8 free addresses. The nodes take addresses from it when they scale.
  • The addresses of an ALB change. Point to it with a Route 53 alias record, never with an IP address. An NLB has one fixed address per AZ.
  • Internet-facing nodes have public addresses. Internal nodes have private ones only. In both cases the targets can be in private subnets.
  • An ALB adds capacity within minutes. A jump of several times within seconds can be faster than that. Before a known event, reserve capacity for it (an LCU reservation).
  • The ALB has a security group. The security group of the targets allows the application port from that group and from nothing else.

ALB: listeners and rules

  • A listener is a protocol and a port: HTTP or HTTPS. It also carries HTTP/2, gRPC and WebSockets.
  • A listener has rules with a priority. The load balancer tries them from the lowest number up. The first match wins. The default rule is last.
  • Conditions: host header, path, any HTTP header, method, query string, source IP.
  • Actions: forward to one target group, or to several by weight. Redirect, for example HTTP to HTTPS. Return a fixed response. Authenticate the user with OIDC or Cognito first.
  • The weighted forward is how blue/green and canary releases work on an ALB (Day 16).
  • The target sees the address of the load balancer node as the source. The client's address is in the header X-Forwarded-For.

Target groups and target types

  • A target group is a protocol, a port, a health check and a list of targets. The routing settings also belong to it: algorithm, stickiness, slow start, deregistration delay.
  • instance: targets by instance ID. An Auto Scaling group registers them for you.
  • ip: any private address. ECS tasks, Kubernetes pods, servers on premises through Direct Connect.
  • lambda: ALB only. One function. Request and response are limited to 1 MB.
  • alb: NLB only. It puts the fixed addresses of an NLB, or PrivateLink, in front of an ALB.
  • You cannot change the type of a target group later.
  • Algorithm: round robin by default. Least outstanding requests is better when requests differ much in duration, or instances in size.
  • Slow start (30 to 900 s) raises the share of a new target step by step. Stickiness ties a client to one target with a cookie. Avoid it where you can: the load becomes uneven.

Health checks

  • Every load balancer node checks every target: a path, an interval, a timeout and the status codes that count as success.
  • After the unhealthy threshold of failures in a row, the target gets no new requests. After the healthy threshold of successes in a row, it gets them again. A new target starts as initial and must pass the healthy threshold first.
  • ALB defaults: every 30 s, 5 s timeout, 5 successes, 2 failures. So a failure is found after about 60 s, and a new target waits 2.5 minutes for its first request.
  • A health check finds a failure after it has happened. For a removal that you planned, deregister the target instead.
  • Keep the check shallow: “this process can serve”. A check that calls the database marks every target unhealthy at the same moment when the database is slow.
  • If all targets of a group are unhealthy, the ALB sends to all of them. It fails open.
  • The Auto Scaling group looks only at EC2 status checks unless you set its health check type to ELB. Then it replaces the instances that the load balancer calls unhealthy.

Cross-zone load balancing

  • DNS spreads the clients over the nodes, about evenly. Each node then divides its share among targets.
  • Off: a node uses only the targets in its own AZ. With 2 targets in one AZ and 8 in the other, each of the 2 gets 25% of all requests and each of the 8 gets 6.25%.
  • On: every node uses every target. Each of the 10 gets 10%.
  • On an ALB it is always on; you can turn it off for one target group. On an NLB and a Gateway Load Balancer it is off by default.
  • On an NLB, traffic that crosses to another AZ is charged as data transfer between AZs. On an ALB it is not charged.
  • Off has one use: each AZ is independent, so you can move traffic away from a bad AZ cleanly (Day 24). Then every AZ needs the same number of targets.

Deregistration delay

  • When you deregister a target, its state becomes draining. It gets no new requests. The requests that are running may finish.
  • When the deregistration delay ends, the load balancer closes what is left and the target is gone. The default is 300 s.
  • Set it a little above your longest request. With 300 s for an API that answers in one second, every deploy and every scale-in waits five minutes for nothing.
  • The application must stay up during the delay. An Auto Scaling group waits for it before it terminates an instance. A deploy script that stops the application itself must deregister and wait first.
  • On SIGTERM the application should finish its running requests and then exit.
  • In Kubernetes a pod gets SIGTERM at the moment its deregistration starts. A short preStop sleep covers the gap (Day 13).

Timeouts and the three error codes

  • 502 Bad Gateway: the load balancer reached for a target and got no valid answer. The connection was refused, reset, or closed in the middle. Deploys and keep-alive settings cause most of them.
  • 503 Service Unavailable: there is no target to send to. The target group is empty, or every target is draining or still initial.
  • 504 Gateway Timeout: the target did not answer within the idle timeout, or the connection to it was not made within 10 s. A slow application, or a security group that drops the packets.
  • The idle timeout is 60 s by default. The keep-alive timeout of the application must be longer. If it is shorter, the load balancer reuses a connection at the moment the application closes it: a 502.
  • Two metrics tell you who made the error. HTTPCode_ELB_5XX_Count: the load balancer. HTTPCode_Target_5XX_Count: your application.
  • In the access log, target_status_code is - when the target never answered.

TLS and SNI

  • An HTTPS listener ends TLS at the load balancer. The certificate comes from ACM, costs nothing and renews itself.
  • A listener has one default certificate and up to 25 more. The client names the host in the TLS handshake (SNI), and the load balancer picks the certificate that matches. One listener serves many domains.
  • The security policy fixes the TLS versions and ciphers. Use a TLS 1.3 policy, such as ELBSecurityPolicy-TLS13-1-2-2021-06, unless old clients force you lower.
  • From load balancer to target you choose HTTP or HTTPS. With HTTPS the ALB encrypts and does not validate the target's certificate.
  • Mutual TLS: the ALB can verify client certificates against a trust store, or pass them to the target in a header.
  • On an NLB, a TLS listener ends TLS. A TCP listener passes it through unchanged, for a target that must do the handshake itself.

Network Load Balancer

  • Layer 4: TCP, UDP and TLS. It does not read HTTP, so there are no rules by host or path. A listener is a port that forwards to one target group.
  • One static address per AZ, and it can be an Elastic IP. Customers can put it in a firewall list.
  • It takes very high rates and sudden jumps without warming, and adds less latency than an ALB.
  • It chooses a target per connection, by a hash of the flow. The connection stays there for its whole life. Long-lived connections do not move when you add targets.
  • The target sees the client's address. Its security group must allow the clients, not only the load balancer.
  • The idle timeout for TCP is 350 s. After that the NLB forgets the flow without telling anybody, and the next packet gets a reset. Set TCP keep-alive below it.
  • An endpoint service for PrivateLink needs an NLB (Day 3).

Gateway Load Balancer

  • Layer 3. It takes every IP packet, of any protocol, sends it through a fleet of appliances and gets it back.
  • A route table sends the traffic to a Gateway Load Balancer endpoint. The packets reach the appliance in a GENEVE tunnel on port 6081, unchanged inside.
  • One flow always goes to the same appliance, in both directions. A stateful firewall needs that.
  • Health checks take a failed appliance out, and an Auto Scaling group replaces it.
  • It is for inspection, not for applications. Day 2 has the routing.

The Auto Scaling group

  • Three numbers: minimum, maximum, desired. The group has one job: keep the desired number of healthy instances running, spread evenly over its AZs.
  • A launch template says what to launch: AMI, type, role, security groups, user data. Launch configurations are the old form; do not use them.
  • The group replaces an instance that fails its health check. The health check grace period gives a new instance time to start before failures count.
  • With a target group attached, the group registers each new instance and deregisters each one before it terminates it.
  • On scale-in, the default termination policy first keeps the AZs balanced, then removes instances with the oldest launch template. Scale-in protection keeps one instance out of it.
  • All of this assumes that instances can be thrown away. Nothing that matters is stored on them.

Dynamic scaling: target tracking and step

  • Target tracking: you name a metric and a value, such as average CPU at 50%. The policy makes two alarms. Above the target for 3 minutes: scale out. Well below it for 15 minutes: scale in. Out is fast, in is slow.
  • The metric must fall when you add instances, in proportion. Average CPU and requests per target do. Latency and the total request count do not.
  • For workers on a queue, publish the backlog per instance as a custom metric and track that.
  • Step scaling: you write the alarm and the steps: 10% over, add 2; 30% over, add 6. More control, and more to tune. Simple scaling is the old form, with a cooldown after every change.
  • Instance warm-up is the time until a new instance counts in the metric. Without it, the policy sees the same high average and launches again.
  • Turn on detailed monitoring. With 5-minute metrics, every decision is late.
  • A policy never goes below the minimum or above the maximum. A maximum set too low is an outage that waits for a busy day.

Scheduled and predictive scaling

  • A scheduled action sets minimum, maximum or desired at a time you give, once or by a cron expression. For events with a date.
  • Predictive scaling learns the daily and weekly pattern from the history of the group. It needs at least 24 hours of data and uses up to 14 days.
  • It forecasts the next 48 hours and launches capacity before each hour needs it, earlier by a buffer time that you set.
  • Start in forecast only mode. Compare the forecast with what happened. Then let it scale.
  • It only adds capacity. Keep a target tracking policy next to it, for the jump that was in no forecast and for scaling in.
  • It pays off when the load has a rhythm and the instances are slow to start.

Lifecycle hooks

  • A hook holds an instance at launch (Pending:Wait) or before termination (Terminating:Wait) until you say that it may go on.
  • At launch: install software, fetch configuration, warm a cache. Until the hook is completed, the instance is not registered with the load balancer. The instance can complete its own hook at the end of user data.
  • At termination: finish the job in progress, upload logs, leave a cluster.
  • You end the wait with complete-lifecycle-action, as CONTINUE or ABANDON. At launch, ABANDON terminates the instance. At termination, both go on to terminate.
  • The timeout is 1 hour by default, and ABANDON is the default result. A heartbeat extends the wait, up to 48 hours.
  • The hook sends an event to EventBridge, so a Lambda function or an SSM Automation can do the work.
  • A Spot interruption gives 2 minutes. No hook can hold the instance longer.

Warm pools

  • A warm pool is a set of instances that have already done their first boot. They wait stopped (you pay for the volumes), hibernated, or running.
  • A scale-out takes from the pool first. A stopped instance is in service in seconds, where a new one takes minutes.
  • Lifecycle hooks run when an instance enters the pool, and again when it leaves it.
  • With a reuse policy, a scale-in returns instances to the pool instead of terminating them.
  • By default the pool holds the difference between maximum and desired. Set a smaller prepared capacity.
  • A warm pool does not work with a mixed instances policy or with Spot.
  • Try the cheaper fix first: a baked AMI (Day 4).

Mixed instances and Spot

  • One group can use several instance types and both purchase options.
  • You set an On-Demand base, and above it the share of On-Demand and Spot.
  • List many types of similar size, across families and generations. Or give attributes (vCPUs, memory) and let EC2 choose the types.
  • The Spot allocation strategy price-capacity-optimized takes the pools with the most spare capacity at a low price. That gives fewer interruptions than the lowest price alone.
  • An interruption comes with 2 minutes notice. Capacity Rebalancing launches a replacement earlier, when EC2 signals that an instance is at risk.
  • When sizes differ, give each type a weight, and the group counts capacity in units instead of instances.
  • With targets of different size, use least outstanding requests on the target group.

Instance refresh

  • An instance refresh replaces the instances of a group after the launch template changed: a new AMI, a new type, new user data.
  • Minimum healthy percentage (default 90) is the share of the desired capacity that must stay in service. It fixes the batch size.
  • Maximum healthy percentage (up to 200) lets the group launch new instances before it terminates old ones, so capacity never falls.
  • After each batch it waits for the health checks and the instance warm-up.
  • Checkpoints stop the refresh at a percentage, so you can look. Auto rollback returns to the old template when the refresh fails or a CloudWatch alarm fires.
  • Skip matching leaves the instances that already have the new configuration.
  • Every replaced instance goes through the deregistration delay and the lifecycle hooks, as in any scale-in.

Global Accelerator

  • Global Accelerator gives you two static anycast IPv4 addresses. AWS announces them from its edge locations all over the world.
  • A client's packets enter the AWS network at the nearest edge and travel on the AWS backbone to an endpoint: an ALB, an NLB, an instance or an Elastic IP, in one Region or several.
  • It works at layer 4, for TCP and UDP. It does not cache and does not read HTTP. CloudFront is for HTTP content (Day 20).
  • It checks the health of the endpoints and moves traffic to another Region in under a minute. The failover does not wait for a DNS TTL.
  • A traffic dial per Region and a weight per endpoint let you move traffic by percentage.
  • Choose it for fixed addresses, for protocols that are not HTTP, and for fast failover between Regions.

Hands-on lab

Interview questions

A deploy causes 502 errors for 30 seconds. Which settings are involved?

A 502 means the load balancer sent a request to a target and got no valid answer, so a target was registered and not serving. I look at four things. First, how the deploy takes an instance out: if it stops the application without deregistering the target, the load balancer keeps sending until health checks fail. Second, the health check interval and unhealthy threshold, because their product is how long that lasts; 30 seconds fits an application that was back before two checks at a 30-second interval had failed, or checks every 15 seconds with a threshold of 2. Third, the deregistration delay: it must be longer than the longest request, and the application must stay up until it ends. Fourth, the way in: the new target must pass the healthy threshold on a health check that is true only when the application can really serve. The fix is to deregister, wait, stop, start, register and wait for healthy, which an instance refresh or CodeDeploy does for me. I also check the keep-alive timeout of the application against the idle timeout of the ALB, because that gives stray 502s that people blame on deploys.

502, 503 and 504 from an ALB: what does each one tell you?

All three are made by the load balancer, not by my application, and the metric HTTPCode_ELB_5XX_Count counts them separately from the target's own errors. A 502 says a target was chosen and the connection to it was refused, reset or closed before a full answer came: an application that stopped while registered, or closed an idle connection that the load balancer then reused. A 503 says there was no target to choose: an empty target group, targets in an AZ that is not enabled, or all of them replaced at once. A 504 says a target was chosen and did not answer in time: the request ran longer than the idle timeout of 60 seconds, or the connection could not be made within 10 seconds, which is often a security group. So 502 sends me to deploys and keep-alive settings, 503 to registration and batch size, and 504 to slow code and network rules.

When do you choose an NLB over an ALB?

The ALB is my default for HTTP, because it routes by host and path, ends TLS with certificates chosen by SNI, can authenticate users and works with WAF. I choose an NLB when one of five things is true. The protocol is not HTTP: plain TCP, UDP, or TLS that the target must end itself. The clients need fixed addresses for their firewalls. The load is very high or jumps suddenly, which an NLB takes without scaling first. The target must see the real client address at the network level. Or I am publishing a service through PrivateLink, which needs an NLB. I accept what comes with it: no routing by content, a target chosen per connection and not per request, cross-zone off by default, and an idle timeout of 350 seconds that drops quiet connections without a notice. When I need both fixed addresses and layer 7 rules, I put an NLB in front of an ALB.

What is cross-zone load balancing, and when would you turn it off?

DNS spreads clients over the load balancer nodes, one or more per AZ. Without cross-zone, a node sends only to targets in its own AZ, so if one AZ has two targets and another has eight, the two get four times the load each. With cross-zone, every node sends to every target and the load is even. On an ALB it is on and free. On an NLB it is off by default, and turning it on adds data transfer charges between AZs. I turn it off, or leave it off, when I want each AZ to stand alone: for zonal shift, where I move traffic away from an AZ that has a problem, and to avoid the transfer cost. The condition is that I then keep the same capacity in every AZ, which the Auto Scaling group does when it is balanced.

How does target tracking work, and how do you choose the metric?

I give a metric and a value, and the policy keeps the metric near that value by changing the desired capacity. It makes two CloudWatch alarms: one fires after three minutes above the target and scales out, the other after fifteen minutes well below it and scales in. The metric must be an average per instance that falls in proportion when I add instances. CPU is the usual start for CPU-bound services. Requests per target is better for a web fleet, because it has no ceiling: CPU cannot read above 100%, so after a large jump a CPU policy adds too few instances and needs several rounds. For queue workers I publish the backlog per instance. I do not use latency, because it does not fall in proportion and depends on things that more instances do not fix. I set the instance warm-up to the real start time, turn on detailed monitoring, and choose a target low enough that the fleet survives the time until new instances help.

How do you design a health check for a load balancer?

The health check answers one question: can this process serve a request now? So it is a cheap endpoint that returns 200 when the application has started, its configuration is loaded and its pools exist. I do not let it call the database or other services. If it does, a slow database makes every target unhealthy in the same minute, and the load balancer then has nothing useful to do; a failure of one dependency has become a failure of the whole site. The state of dependencies goes to a second endpoint that monitoring reads. For the numbers, a 10-second interval with 2 or 3 as thresholds finds a dead target in 20 to 30 seconds without reacting to one slow answer. I set the Auto Scaling group's health check type to ELB, so that it replaces what the load balancer rejects, and the grace period longer than the start time, so that it does not kill instances that are still booting.

The fleet needs eight minutes to add capacity after a traffic jump. How do you shorten that?

I split the eight minutes into detection, launch and readiness. Detection: target tracking needs three one-minute datapoints, and with basic monitoring the data is five minutes old, so detailed monitoring comes first; a step policy on a faster alarm can react sooner. Launch and readiness is usually the largest part. A baked AMI removes the installation at boot. A warm pool of stopped instances brings the start down to seconds. A lower healthy threshold and a shorter health check interval bring the target into service sooner, and slow start is off unless the application needs it. Then I ask whether the capacity can be there before the load: predictive scaling for a daily curve, a scheduled action for a known event. Last, headroom: a lower target value means the fleet can take a bigger jump while it waits. I check that the maximum size, the vCPU quota and the load balancer itself allow the new size.

What are lifecycle hooks for, and what happens when one times out?

A hook makes the Auto Scaling group wait at a transition so that I can do work. At launch the instance stays in Pending:Wait: I install or configure, and only when I complete the hook is it registered with the load balancer. At termination it stays in Terminating:Wait: a worker finishes its job, logs are uploaded, a node leaves its cluster. I complete the hook with CONTINUE or ABANDON. If nobody completes it, the heartbeat timeout ends the wait, one hour by default, with the default result, which is ABANDON. At launch that terminates the instance and the group tries again; at termination the instance is terminated either way. So a broken launch hook gives a group that launches and kills instances every hour, and a broken termination hook gives a scale-in that takes an hour per instance. I set a timeout that matches the work, and send heartbeats when a job is long.

How do you roll out a new AMI to 200 instances without losing capacity?

With an instance refresh on the Auto Scaling group. I make a new launch template version with the new AMI and start the refresh with a minimum healthy percentage of 100 and a maximum of, for example, 110. The group then launches 20 new instances, waits until they pass the load balancer health check and the warm-up, and only then removes 20 old ones, which drain for the deregistration delay. I add a checkpoint at a small percentage with a wait, so that the first batch runs with real traffic for a while, and I turn on auto rollback with a CloudWatch alarm on the error rate, so that a bad image stops the refresh and brings back the old template. Before I start I check that the maximum size and the vCPU quota allow 220 instances. The deregistration delay and the warm-up decide how long the whole thing takes, so I make them fit the application and not the defaults.

How do you run a fleet on Spot without outages?

Spot is for work that can lose an instance at any time, so the service must be stateless and behind a load balancer or a queue. I use a mixed instances policy: an On-Demand base that can carry the minimum acceptable load, and Spot above it. I allow many instance types across families, sizes and generations, in all AZs, because each combination is a separate capacity pool and one pool can be empty. The allocation strategy is price-capacity-optimized, which avoids the pools that are most likely to be interrupted. I turn on Capacity Rebalancing, so that a replacement starts when EC2 signals a risk, before the two-minute notice. On the notice, the instance is deregistered and drains, so the deregistration delay must be well under two minutes. I also plan for the case where no Spot capacity exists: the group must be allowed to grow on On-Demand.

Global Accelerator, CloudFront, or Route 53 latency routing: which one for a service in two Regions?

They work at different layers. Route 53 latency routing answers a DNS query with the nearest Region. It is cheap and simple; failover waits for health checks and for the TTL in every resolver and client, and some clients keep an address much longer. CloudFront is an HTTP proxy with a cache at the edge: the right choice when the content can be cached or when I need its features, such as edge functions and origin failover. Global Accelerator gives two fixed anycast addresses, takes TCP and UDP into the AWS network at the nearest edge, and sends each connection to the nearest healthy Region. Its failover takes well under a minute and does not depend on DNS. So for a cacheable web application I use CloudFront, for a non-HTTP protocol, clients that need fixed addresses, or strict failover time I use Global Accelerator, and for the simple case I start with Route 53.
