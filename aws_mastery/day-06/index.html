S3 and Storage

The fleet from yesterday is stateless, so its data lives somewhere else. Most of it lives in S3. S3 looks simple: a bucket, a key, an object. Inside it is a request pipeline with seven places where a request can be denied, a set of storage classes with very different bills, and features such as versioning, replication and Object Lock that quietly change what a delete means. The centre of the page is one request: a bucket policy allows it, and S3 still says AccessDenied. Which layer said no? Around S3 sit the file and transfer services: EFS, FSx, Storage Gateway, DataSync and AWS Backup.

The diagram

The whole picture. A signed request reaches the S3 endpoint for the bucket's Region. S3 authenticates it and then walks the authorisation layers; every one must allow and none may deny. The object is encrypted with the method chosen for it, written as a new version if versioning is on, placed in a storage class that lifecycle rules may change later, perhaps locked, perhaps replicated to another Region, and an event is published. Around the bucket are the ways bytes get in and the file services for workloads that need a file system rather than an object store.

How it works inside

What S3 is, and is not

  • An object store: a key maps to bytes plus metadata. There are no directories; the / in a key is a character that the console and LIST treat as a delimiter.
  • A bucket name is globally unique and the bucket lives in one Region. Objects never leave that Region unless you replicate or copy them.
  • Writes are atomic per object and reads are strongly consistent since 2020: a GET after a PUT returns the new object. There is no partial update; you replace the whole object.
  • Durability of 99.999999999% comes from storing every object on several devices in at least three AZs. Availability is 99.99% for Standard, lower for the IA and One Zone classes.
  • Objects are up to 5 TB. One PUT is up to 5 GB. Anything larger is a multipart upload.
  • There are general purpose buckets, directory buckets (S3 Express One Zone: single-digit millisecond latency, one AZ, a different namespace) and table buckets for Iceberg tables.

Performance and prefixes

  • Each prefix gives at least 3,500 PUT/COPY/POST/DELETE and 5,500 GET/HEAD requests per second. S3 adds partitions over time as load grows; a sudden jump on one prefix returns 503 SlowDown until it has.
  • A prefix is any string before the key, not only up to a /. Keys that start with a date all share a few prefixes; add a hash or an id early in the key to spread them.
  • Large downloads: use ranged GETs in parallel. Large uploads: multipart with parts of 8 to 100 MB, which the CLI and SDKs do for you.
  • First-byte latency is 100 to 200 ms. For many small objects that latency dominates; batch or pack them, or use S3 Express One Zone.
  • Retry on 503 with backoff and jitter. The SDKs do; your own HTTP client must.
  • Clients in a VPC reach S3 through a gateway endpoint (free, a route) or an interface endpoint (PrivateLink, hourly cost, reachable from on-premises). Day 2 covers both.

The access control layers

  • Block Public Access is a switch at the account and bucket level. With it on, a policy or ACL that would grant public access is ignored or rejected. Leave it on everywhere; serve public content through CloudFront.
  • Bucket policy: a resource policy, up to 20 KB, the place for cross-account grants, TLS-only conditions (aws:SecureTransport), VPC-endpoint conditions and deny-everything-else rules.
  • IAM identity policy: for callers in the same account, either the identity policy or the bucket policy may allow. Cross-account, both must allow.
  • ACLs are legacy. With Object Ownership = Bucket owner enforced they are disabled, every object belongs to the bucket owner, and the "I own the bucket but cannot read the object" problem disappears.
  • Access Points: a named endpoint with its own policy and optional VPC restriction, so that one bucket with many teams does not need one giant bucket policy. Multi-Region Access Points route to the nearest replicated bucket.
  • VPC endpoint policy and KMS key policy are two more places a request can die. Then S3 Object Lambda can rewrite what a GET returns.

Encryption

  • Every new object is encrypted. SSE-S3 (AES-256, keys S3 manages) is the default and free.
  • SSE-KMS uses a KMS key: the key policy becomes a second gate, CloudTrail shows every use, and you can revoke access by changing the key policy. Each PUT and GET calls KMS unless S3 Bucket Keys are on, which cuts calls and cost by about 99%.
  • DSSE-KMS encrypts twice for rules that demand two layers. SSE-C: you send the key with every request over TLS and S3 keeps nothing.
  • Client-side: encrypt before upload with the Encryption SDK; S3 never sees plaintext.
  • A bucket's default encryption applies to objects that arrive without a header. A bucket policy can deny PUTs that do not ask for KMS.
  • Enforce TLS with a Deny on aws:SecureTransport = false. Enforce a minimum TLS version with s3:TlsVersion.

Versioning and what a delete means

  • Versioning is off, enabled or suspended; once enabled a bucket can never go back to off.
  • Every PUT writes a new version with a new version id. A DELETE without a version id writes a delete marker and hides the object; the data is still there and still billed.
  • To really delete, delete the specific version id. To restore, delete the delete marker.
  • MFA Delete requires the root user's MFA to change the versioning state or delete a version. Rarely used; Object Lock is the modern answer.
  • Lifecycle has separate actions for noncurrent versions: transition them after N days, expire them after N days or keep only the newest N. Without these, a versioned bucket grows forever.
  • Replication and Object Lock both require versioning.

Storage classes

  • Standard: frequent access, no retrieval fee, no minimum duration.
  • Standard-IA and One Zone-IA: about half the storage price, a retrieval fee per GB, a 30-day minimum and a 128 KB minimum object size. One Zone is one AZ: for data you can recreate.
  • Glacier Instant Retrieval: milliseconds, 90-day minimum, higher retrieval fee. For quarterly access.
  • Glacier Flexible Retrieval: minutes to hours, 90-day minimum. Deep Archive: 12 to 48 hours, 180-day minimum, the cheapest. Both need a RestoreObject call before a GET.
  • Intelligent-Tiering: a small monitoring fee per object and no retrieval fees; S3 moves objects between tiers by access. The right default when you do not know the pattern. Objects under 128 KB are never moved and are not charged the fee.
  • Express One Zone: for latency-critical, small-object, high-request workloads in one AZ, with a per-request price far below Standard.

Lifecycle rules

  • A rule has a filter (prefix, tags, object size) and actions: transition current versions, transition noncurrent versions, expire current, expire noncurrent, remove delete markers, abort incomplete multipart uploads.
  • Rules run once a day (UTC midnight); a transition happens the day after the object reaches the age, and the bill changes when the transition completes.
  • Transitions go down only: Standard → IA → Glacier classes. To move an object back up, copy it.
  • Transitions cost a per-request fee. Moving millions of tiny objects to Glacier can cost more than leaving them, and each Glacier object carries 32 KB plus 8 KB of overhead.
  • Minimum durations are charged early: delete an IA object after 10 days and you pay for 30.
  • Always add abort incomplete multipart uploads after 7 days. Half-finished uploads are invisible and billed.

Replication

  • Cross-Region (CRR) or Same-Region (SRR), to one or more destination buckets, in the same or another account. Both buckets need versioning and S3 needs a role.
  • Only new objects replicate. Existing ones need S3 Batch Replication.
  • By default delete markers do not replicate, so a delete at the source leaves the copy. You can turn marker replication on. Version deletes never replicate.
  • Replication is asynchronous and usually completes within minutes. Replication Time Control gives an SLA of 15 minutes for 99.99% of objects, with metrics and events for the rest.
  • Objects encrypted with SSE-KMS replicate only if you say so, and the destination key is a different key in the destination Region.
  • Replicas can land in a different storage class and under a different owner (owner override) for a separate audit account.

Object Lock

  • WORM: write once, read many. Enabled at bucket creation (or by support later), needs versioning, and locks versions, not keys. A new PUT still creates a new version.
  • Retention period: a date until which the version cannot be deleted or overwritten. Set a default on the bucket or per object.
  • Governance mode: users with s3:BypassGovernanceRetention can still remove it. For protection against mistakes.
  • Compliance mode: nobody, not even the root user, can shorten it, and the bucket cannot be deleted while a locked version exists. For regulation, and for ransomware-proof backups.
  • Legal hold: an on/off flag with no date, independent of retention.
  • Test compliance mode with a retention of one day before you commit to one of ten years.

Events, inventory and batch

  • Event notifications to SQS, SNS or Lambda: one destination per event type and prefix/suffix filter, and overlapping filters are rejected. Delivery is at-least-once, usually within seconds.
  • Sending to EventBridge is a single switch: every event, including the ones the classic path lacks (lifecycle transitions, restores, replication, tagging), with content-based rules and many targets.
  • S3 Inventory gives a daily or weekly CSV/Parquet listing of every object with its size, class, encryption and replication status. Cheaper than LIST for millions of objects.
  • S3 Batch Operations runs one action over an inventory or a manifest: copy, tag, restore, invoke Lambda, set retention, replicate.
  • Storage Lens shows usage and activity over the whole organisation, with free and paid metrics, and finds incomplete uploads and cold data.
  • Requester pays makes the caller pay for requests and transfer, for public datasets.

Presigned URLs and uploads from browsers

  • A presigned URL is a normal S3 URL with your credentials' signature and an expiry. Whoever holds it can do that one operation on that one key until the expiry.
  • It can live up to 7 days when signed with IAM user keys, and only until the session expires when signed with a role's temporary credentials. A Lambda signing with its role gives URLs that die with its credentials, sometimes within an hour.
  • The signer must have the permission; the URL cannot grant more than the signer has, and a bucket policy Deny still applies.
  • Presigned POST lets a browser form upload with conditions on size, content type and key prefix.
  • Browsers need a CORS configuration on the bucket before they can PUT to it.
  • For a mobile app: the backend signs, the device uploads straight to S3, and an event tells the backend when the object is there.

EFS

  • A managed NFS v4 file system; thousands of instances, containers and Lambda functions can mount it at once. Grows and shrinks on its own, petabyte scale.
  • A mount target per AZ, with an ENI and a security group that allows port 2049. Mount through the AZ's own target to avoid cross-AZ charges and latency.
  • Regional (three AZs) or One Zone (cheaper, one AZ). Classes: Standard and Infrequent Access, with lifecycle policies between them.
  • Throughput modes: Elastic (pay for what you use, the default), Provisioned, or Bursting (tied to size, credits run out).
  • Access points fix a POSIX user and a root directory per application. IAM policies on the file system can require TLS and deny root.
  • Latency is in milliseconds per operation; a workload that opens thousands of small files is slow on any network file system.

FSx, Storage Gateway, DataSync, Transfer, Backup

  • FSx for Windows: SMB, Active Directory, DFS, Multi-AZ. FSx for Lustre: HPC and ML scratch at hundreds of GB/s, linked to an S3 bucket. FSx for NetApp ONTAP: NFS, SMB and iSCSI together, snapshots, dedup, SnapMirror from on-premises NetApp. FSx for OpenZFS: NFS with ZFS snapshots and clones.
  • Storage Gateway runs on-premises: S3 File Gateway (NFS/SMB share backed by S3, with a local cache), Volume Gateway (iSCSI, cached or stored, snapshots to EBS), Tape Gateway (a virtual tape library for backup software, tapes in Glacier).
  • DataSync: an agent that copies file systems, S3, EFS, FSx and other clouds, with checksums, scheduling and bandwidth limits. For migrations and recurring sync, not for a live mount.
  • Transfer Family: managed SFTP, FTPS, FTP and AS2 endpoints in front of S3 or EFS, for partners who send files.
  • AWS Backup: one plan, one vault, one policy across EBS, EFS, RDS, Aurora, DynamoDB, S3, FSx, EC2 and more, with cross-Region and cross-account copies and vault lock for immutability.
  • Snow family: physical devices when the network is too slow; Day 28.

Hands-on lab

Goal: build a locked-down versioned bucket, prove that a delete does not delete, make the owner lose and regain access to an object, trace a denied request in CloudTrail, add lifecycle and event rules, and mount EFS from two instances. About 45 minutes.

Cost: a few cents: a handful of objects, a KMS key ($1 a month, delete it at the end), a CloudTrail data-event trail for an hour, and two t4g.nano instances for the EFS part.

Interview questions

A bucket policy allows access but the request is still denied. Name four possible reasons.

S3 is only one voter and any explicit Deny wins, so I go looking for the Deny or the missing Allow in another layer. One: the caller is in another account, and cross-account access needs both the bucket policy and the caller's own IAM policy to allow the action; the bucket policy alone is not enough. Two: an SCP or a permission boundary on the caller denies S3, or limits it to certain Regions or buckets. Three: the object is encrypted with SSE-KMS and the caller cannot use the key, because the key policy does not list it; the S3 call fails with AccessDenied although the S3 permissions are fine. Four: the request arrives through a VPC endpoint with a policy that does not allow this bucket, or the bucket policy has a condition on aws:SourceVpce and the request came another way. I would add two more: Block Public Access overrides a policy that grants to everyone, and if ACLs are still enabled the object may belong to another account that uploaded it, so even the bucket owner cannot read it. Since the 403 does not say which layer refused, I turn on CloudTrail data events, repeat the call and read the error and the neighbouring KMS event.

Bucket policy, IAM policy, ACL or Access Point: when do you use each?

For callers inside my own account I prefer IAM identity policies, because permissions then live with the identity and I can read what a role can do in one place. The bucket policy is for things that belong to the bucket: cross-account grants, denying plain HTTP, requiring a VPC endpoint, requiring encryption, and a service principal such as CloudTrail or a CloudFront origin access control. ACLs I disable with Bucket owner enforced; the only place they still appear is the log delivery group of some older services, and that is being replaced by policies too. Access Points come in when one bucket serves many teams or applications: each gets its own endpoint with its own policy, optionally reachable only from one VPC, and the bucket policy delegates to them with one statement. That keeps the bucket policy under its 20 KB limit and lets each team change its own policy without touching the others.

How do you give a mobile app access to upload files without giving it AWS credentials?

The app never holds AWS credentials. It authenticates to my backend, with Cognito or my own login, and asks for permission to upload one file. The backend, which has a role with s3:PutObject on a prefix, generates a presigned URL or a presigned POST for a key it chooses, such as uploads/{userId}/{uuid}, with a short expiry of a few minutes and, with a presigned POST, conditions on content length and content type. The device PUTs straight to S3 over that URL, so the bytes never pass through my servers. The bucket has a CORS rule if a browser is involved, Block Public Access on, and an event notification on uploads/ that tells the backend, through SQS or EventBridge, that the object exists; the backend validates it and moves or records it. Reads work the same way in reverse, or through CloudFront with signed URLs when many users read the same files. If the backend is a Lambda, I remember that its URLs die when its role credentials expire, so I keep the expiry short on purpose.

Versioning is on. A developer deletes a prefix with 10 million objects by mistake. What happened, and how do you recover?

Nothing was lost. Each delete without a version id wrote a delete marker on top of the current version; the data is still there and still billed. Recovery is to remove the delete markers. For ten million keys I do not script a loop. I generate an S3 Inventory or list the versions for the prefix, filter to the delete markers that are the latest version, and run an S3 Batch Operations job, or a short script over the list, that deletes those marker version ids. The objects reappear as they were. Afterwards I ask how the developer had s3:DeleteObject on production at all, and I consider two protections: a bucket policy that denies s3:DeleteObjectVersion to everyone except a break-glass role, so that versions can only be hidden and never destroyed, and Object Lock for the data that must survive even a malicious actor. If versioning had been off, the answer would have been the replica in the other Region, or AWS Backup, or an apology.

Design the storage for 50 TB of application logs that are read heavily for a week, occasionally for 90 days, and kept for 7 years.

The lifecycle rule writes itself from the access pattern. Logs land in Standard, where the week of heavy reading has no retrieval fee. After 30 days, the earliest allowed, they move to Standard-IA: half the price and the occasional read costs a cent a gigabyte. After 90 days they move to Glacier Deep Archive, at about a dollar per terabyte per month, and expire after 7 years. I key the objects by source and time with a hash or source id early in the key, so that the write rate spreads over prefixes, and I compress and batch them, because logs are small and the IA and Glacier classes bill a minimum of 128 KB and add 40 KB per object in Glacier. If the retention is a legal requirement I enable Object Lock in compliance mode with a 7-year default retention and keep a replica in another Region. The rule also aborts incomplete multipart uploads after 7 days. For queries I point Athena at the Standard and IA data and accept that anything older needs a restore first. Over 7 years that is roughly 2.5 PB in Deep Archive, about $30,000 a year, against about $700,000 a year if it all stayed in Standard.

When would you choose Intelligent-Tiering over writing lifecycle rules yourself?

When I cannot predict access per object. A data lake where some partitions are hot for months and others are never read again, user uploads where a few files become popular, or a bucket shared by many teams with different habits. Intelligent-Tiering watches each object and moves it to the infrequent tier after 30 days without access and to the archive instant tier after 90, and back to frequent the moment it is read, with no retrieval fee and no early-deletion fee. The price is a monitoring fee per object, which is nothing for large objects and a real cost for millions of tiny ones; objects under 128 KB are excluded and simply stay at the frequent price. I write my own rules when the pattern is known and time-based, as with logs, because then IA and Glacier are cheaper than the tiers and I can choose Deep Archive, which Intelligent-Tiering only reaches through the optional asynchronous archive tiers that bring back restore latency.

Explain how S3 cross-Region replication behaves on deletes and on existing data, and when you would use Replication Time Control.

Replication copies new objects, their metadata and tags to the destination after they are written, asynchronously, usually within minutes. Three things surprise people. Objects that existed before the rule do not replicate, so the first step on an existing bucket is a Batch Replication job. A delete without a version id writes a delete marker, and markers are not replicated unless I turn that on, so by default the replica keeps the object; a delete of a specific version is never replicated, which protects the replica from a destructive mistake. And SSE-KMS objects replicate only when the rule says so, using a different key in the destination Region. I turn on Replication Time Control when the replica is part of a recovery objective: it gives a 15-minute SLA for 99.99% of objects, metrics for the replication latency and the bytes pending, and an event when an object misses the window, which is what lets me put a number on the data I could lose in a Regional failover.

Your batch job gets 503 SlowDown errors from S3. What is happening and what do you do?

S3 partitions a bucket by key prefix and each partition serves about 3,500 writes and 5,500 reads a second. S3 splits partitions as load grows, but it takes time, and a job that starts at full speed on one prefix exceeds the current partition and gets 503s until the split has happened. First I make sure the client retries with exponential backoff and jitter, which the SDKs do by default and which turns the errors into a slower start rather than failures. Then I look at the keys: if they share a long prefix such as a date, I add a few characters of hash or an id early in the key so that the load spreads over many partitions. I ramp the job up over minutes instead of seconds. For a known future load I can ask AWS Support to pre-partition the prefix. And I check whether the job is doing more requests than it needs, such as a HEAD before every GET or a LIST per object.

S3, EFS or FSx for a fleet of web servers that need shared uploaded files?

I ask whether the application needs a file system or only thinks it does. If it writes a file and later reads the whole file, S3 is right: it is far cheaper, needs no mount, scales without limits, and the servers stay stateless; a small change in the code, or a library that maps a path to a bucket, usually does it. If the application uses POSIX semantics, such as appending, locking, renaming or listing directories at speed, or is third-party software I cannot change, I use EFS: NFS from every instance, a mount target in each AZ, Elastic throughput, access points for per-application roots, and a lifecycle policy to the infrequent access class. If the servers are Windows and the application wants SMB and Active Directory permissions, FSx for Windows. I would warn that EFS costs about 13 times S3 per gigabyte and that a workload opening thousands of small files is slow on any network file system, so the thumbnail directory with a million files belongs in S3 either way.

How do you protect backups in S3 against ransomware that has taken over the account?

I assume the attacker has the credentials of an administrator in the production account, so permissions alone are not a defence. First, versioning plus Object Lock in compliance mode on the backup bucket, with a retention equal to the backup retention: nobody, not even root, can delete a locked version early, and the bucket cannot be deleted while one exists. Second, a copy in a separate account that production cannot assume into, written by replication or by AWS Backup cross-account copy with a vault lock; the attacker's account is then not the one that holds the only copy. Third, the backup account's own Block Public Access and SCPs that deny disabling versioning, changing lock settings or deleting the bucket. Fourth, detection: CloudTrail to a locked bucket in the security account, GuardDuty S3 protection, and alarms on mass deletes and on changes to replication or lifecycle, because a lifecycle rule that expires everything after one day is the quiet way to destroy a bucket. Last, I test a restore, because a backup that was never restored is a hope, not a backup.
