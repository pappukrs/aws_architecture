Messaging and orchestration

A queue between two services buys you three things: the producer never waits for the consumer, a burst becomes a backlog instead of an outage, and a consumer that dies loses nothing. It costs you one thing, and most teams discover it in production: the message that was processed twice. SQS promises at-least-once delivery, and so does every other system on this page once you read the small print; the consumer that charges a card and then crashes before deleting the message will charge it again. This page is about building on that promise instead of fighting it. First the queue: SQS standard against FIFO, the visibility timeout, long polling, dead-letter queues and redrive. Then the fan-out and routing layer: SNS with filter policies, EventBridge with buses, rules, Pipes and the Scheduler. Then the orchestrators: Step Functions standard against express, retries, and the saga pattern for a process that must undo itself. Then the streams and the rest: Kinesis against MSK, Amazon MQ for protocols you did not choose, and AppSync for clients that want to be told. The centre of the page is the interview question: a message is processed twice. Is that a bug? How do you make the consumer safe?

Model: four sources of a second delivery. The producer retries a SendMessage whose response was lost, about one call in 20,000 on a normal day, and each retry is a new message with a new id on a standard queue; a FIFO queue drops it when the producer sends a deduplication id. The queue itself, on standard, re-delivers a message on rare internal retries, taken as one in 100,000. The visibility timeout expires before the work is done: if the work takes longer than the timeout every message is redelivered, and all of its retries fail the same way until maxReceiveCount sends it, already processed, to the DLQ; if the work's slow tail (taken as 3× the typical time) crosses the timeout, 2% of messages are redelivered. The consumer fails after the side effect and before the delete at the rate you pick, and that message comes back after the timeout. A consumer with no idempotency turns every duplicate into a duplicate side effect; a claim with a conditional write catches all of them except the ones whose claim and act are not atomic, taken as 2% of the consumer-failure duplicates when the claim is written after the act; an idempotent operation catches all of them. FIFO exactly-once processing removes the producer and queue duplicates; it does nothing about the visibility and consumer ones.

How it works inside

SQS standard: a lease, not a lock

  • A queue is stored redundantly across AZs. SendMessage writes a copy to several servers and acknowledges; ReceiveMessage samples a subset of those servers, which is why a receive on a nearly empty queue can return nothing while a message exists (the docs call it short polling's sampling) and why order is best-effort: a message that landed on a server that was not sampled comes later.
  • Receiving does not remove. The message becomes invisible for the visibility timeout (30 s by default, up to 12 hours), and the consumer must call DeleteMessage with the receipt handle before the timeout, or the message reappears for another consumer. ChangeMessageVisibility extends the lease for long work; a Lambda event source mapping does this for you up to the function's timeout.
  • Throughput is effectively unlimited per queue, with no provisioning. In flight at once: 120,000 messages (received, not deleted); beyond that receives return nothing. Message size 256 KB by default, raisable to 1 MiB; bigger payloads go to S3 with a pointer (the extended client library does it).
  • Long polling (WaitTimeSeconds up to 20) makes a receive wait until a message arrives and queries every server, so it returns fewer false empties and costs a twentieth as much when the queue is idle. There is no reason to short-poll a production queue.

SQS FIFO: order and dedup, per group

  • Every message carries a MessageGroupId. Messages in one group are delivered in order and, crucially, one at a time: while a message from group A is in flight, no other message of group A is delivered to anyone. Groups are the unit of parallelism; a queue with one group is single-threaded.
  • MessageDeduplicationId (or a SHA-256 of the body with content-based deduplication) makes a second send with the same id within 5 minutes a no-op. This is producer-side dedup: it removes a retried send, not a redelivered message.
  • Throughput: 300 messages a second per API action without batching, 3,000 with batches of 10; high throughput mode partitions by group and reaches tens of thousands a second, 70,000 with batching in the largest Regions. 20,000 in flight.
  • "Exactly-once processing" means a message is delivered once and stays unavailable until the visibility timeout passes; if your consumer fails to delete it in time it comes back, in order, and blocks its group. A poison message in a FIFO group stops the group until the DLQ takes it.

Dead-letter queues and redrive

  • A redrive policy on the source queue names a DLQ and a maxReceiveCount (1–1,000). Each receive increments ApproximateReceiveCount; past the limit, SQS moves the message to the DLQ instead of making it visible again. The DLQ must be the same type (standard or FIFO) and in the same account and Region.
  • The DLQ's retention clock is the original send time, not the move time: a 4-day retention with a message that spent 3 days in the source leaves one day to look at it. Give DLQs the full 14 days.
  • A redrive (StartMessageMoveTask) sends DLQ messages back to the source, or to any queue, at a rate you choose. It is for after the fix. Redriving into an unfixed consumer is a loop with extra steps.
  • A Lambda consumer without ReportBatchItemFailures makes the whole batch fail when one message fails, so nine good messages are retried with the bad one and arrive in the DLQ together. Turn partial batch responses on, always.

SNS: one publish, many copies

  • A topic takes a publish and delivers a copy to each subscription: SQS queues, Lambda functions, HTTP endpoints, email, SMS, mobile push, Firehose. Delivery to SQS and Lambda is free and reliable; HTTP endpoints get a retry policy of your choosing (up to about an hour by default, 23 days configurable) and then a DLQ.
  • A filter policy per subscription selects messages by attributes or, since 2022, by fields of the JSON body: exact match, prefix, numeric ranges, anything-but, exists. The topic does the routing so the subscriber receives only what it asked for and pays nothing for the rest.
  • Raw message delivery hands the subscriber the payload as sent instead of the SNS envelope; without it, a queue consumer parses JSON inside JSON. FIFO topics deliver in order to FIFO queues only, with the same group and dedup semantics as the queue.
  • No retention: a subscriber that is unreachable gets retries and then nothing. The reliable pattern is SNS → SQS → consumer: the queue holds the message for the consumer that is down; the topic only copies it.

EventBridge: a bus with rules

  • An event bus receives events as JSON with a source, detail-type and detail. The default bus carries events from AWS services (an EC2 state change, a CodePipeline stage, a GuardDuty finding); custom buses carry yours; partner buses carry SaaS events. Rules match on any field with patterns (equals, prefix, numeric, exists, anything-but, wildcards) and send to up to five targets each, with input transformation.
  • Delivery is at-least-once with a retry policy (up to 24 hours and 185 attempts by default) and a DLQ per target. Latency is typically about half a second; it is not a queue for a tight loop. Throughput defaults to thousands of PutEvents a second in the big Regions, raisable.
  • Archive and replay: an archive records events matching a pattern for a retention you set, and a replay sends them back through the rules for a time window, to the rules you name. That is the recovery tool after a bad deploy of a consumer.
  • Pipes connect one source (SQS, Kinesis, DynamoDB Streams, MSK, MQ) to one target with optional filtering and an enrichment step (Lambda, Step Functions, API), replacing the glue function. The Scheduler runs one-off and recurring schedules (cron, rate, at) with a flexible window and time zone, invoking over 270 services directly, at a million schedules an account.

Step Functions: Standard and Express

  • A state machine is a JSON definition (Amazon States Language) of states: Task (call a service or a function), Choice, Parallel, Map, Wait, Pass, Succeed, Fail. The state's output is the next state's input; the data flowing through is the execution's memory, up to 256 KB. Over 220 service integrations call APIs directly, without a Lambda in between.
  • Standard: an execution runs up to one year, every state transition is recorded durably, the execution is exactly-once (a second StartExecution with the same name within 90 days is rejected), and you pay $0.025 per 1,000 transitions. For long-lived, human-in-the-loop, auditable processes.
  • Express: up to five minutes, at-least-once (asynchronous) or at-most-once (synchronous StartSyncExecution), history to CloudWatch Logs, priced per request and duration, $1 per million plus about $0.00001667 per GB-second. For high-volume, short, idempotent work: event processing, API orchestration, the body of a Map.
  • Integration patterns: request-response (call and continue), .sync (call and wait for the job: a Batch job, a Glue run, an ECS task, a child workflow), and .waitForTaskToken (pause until something calls SendTaskSuccess with the token: a human approval, an external system). Distributed Map runs up to 10,000 child executions over an S3 listing or a JSON array.

Retries, catches and the saga

  • A Task state's Retry lists error names (States.TaskFailed, States.Timeout, Lambda.ServiceException, your own), an interval, a backoff rate, a maximum of attempts and, since 2023, jitter and a cap. Retry transient errors; do not retry a validation error 20 times.
  • A Catch routes an error to another state with the error in the input. That is how a workflow fails gracefully: catch, record, compensate, then end in a Fail state with a cause someone can read.
  • The saga pattern: a sequence of steps, each with a compensating step that undoes it (reserve stock / release stock, charge card / refund, create shipment / cancel shipment). When step N fails, the Catch runs the compensations for steps N−1 down to 1. Each step and each compensation must be idempotent, because the workflow may run them again after a retry.
  • A task running in Lambda has its own timeout and Lambda's own retries for asynchronous invocations; set TimeoutSeconds on the Task state and HeartbeatSeconds on long callbacks so a hung step becomes a States.Timeout instead of a year-long wait.

Kinesis Data Streams

  • A stream is a set of shards; a record goes to the shard chosen by the hash of its partition key and gets a sequence number. Each shard accepts 1 MB/s or 1,000 records a second and serves 2 MB/s to all consumers together, or 2 MB/s per consumer with enhanced fan-out (push over HTTP/2, up to 20 consumers). Records up to 1 MB; retention 24 hours by default, up to 365 days.
  • Reading is by iterator: a consumer asks for records from a position (trim horizon, latest, a sequence number, a timestamp) and keeps its own checkpoint (the KCL stores it in DynamoDB; a Lambda event source mapping keeps it for you). Reading deletes nothing; two consumers see the same records.
  • On-demand mode scales shards for you and bills per GB; provisioned bills per shard-hour and needs resharding (split and merge) as traffic changes. A hot partition key is a hot shard: WriteProvisionedThroughputExceeded on one shard while the others idle.
  • Order is per shard. A Lambda consumer runs one invocation per shard at a time (or up to 10 with parallelization factor, ordered per key), and a failing batch blocks the shard until it succeeds, the record expires, or the retry and bisect settings give up: a poison record stalls the shard, and IteratorAge is the alarm.

MSK and Amazon MQ

  • MSK runs Apache Kafka: brokers across AZs, topics split into partitions, each a replicated ordered log; producers choose a partition by key; consumer groups share partitions among members and commit offsets. Retention is by time or size per topic, as long as you pay for disk. Provisioned clusters (you pick brokers and storage; Express brokers simplify it) or MSK Serverless (per partition-hour and GB). Connect for sinks and sources, Schema Registry via Glue.
  • Kafka is for when you have the ecosystem (Flink, Debezium, Connect, a team that speaks it), need retention of weeks to forever, topics with hundreds of partitions, or hundreds of MB/s. For most AWS-native work Kinesis is the same shape with nothing to operate; the choice is usually about the team, not the technology.
  • Amazon MQ is a managed ActiveMQ or RabbitMQ broker in your VPC: AMQP, JMS/OpenWire, MQTT, STOMP, the protocols an existing application already speaks. Active/standby across AZs for ActiveMQ (failover is a reconnect, tens of seconds), a 3-node cluster for RabbitMQ. You size the broker and it has a ceiling.
  • MQ is the migration answer, not the greenfield one: it moves a JMS application to AWS without a rewrite. A new system that wants a queue wants SQS; one that wants a broker's routing wants EventBridge or SNS.

AppSync: the server calls the client

  • A managed GraphQL API: a schema, resolvers (JavaScript or VTL, single or pipeline) that map fields to data sources (DynamoDB, Lambda, RDS via the Data API, OpenSearch, HTTP, EventBridge), authorisation by API key, IAM, Cognito, OIDC or a Lambda authoriser, per field. Caching per resolver.
  • Subscriptions: a client subscribes over WebSocket to a mutation; when the mutation runs, AppSync pushes the result to every subscribed client, filtered server-side. That is how a dashboard, a chat or an order tracker gets live data without polling and without you running a WebSocket fleet. The Events API does the same for plain pub/sub channels without a GraphQL schema.
  • Limits to know: 256 KB per request and response, a 30-second resolver timeout, and subscriptions deliver what the mutation returned, so the mutation's selection set must include what the subscriber needs.
  • Pricing is per operation ($4 per million queries and mutations), per real-time update and per connection-minute. For a server-to-server API with no live clients, API Gateway and Lambda are cheaper and simpler.

Consumers: Lambda or a worker fleet

  • A Lambda event source mapping polls the queue for you, invokes the function with a batch (up to 10 messages for FIFO; up to 10,000 with a batching window of up to 5 minutes for standard), deletes the messages the function reported as processed, and scales from 5 concurrent pollers by up to 300 a minute, capped by maximum concurrency on the mapping (2–1,000) and the account's concurrency. Set the queue's visibility timeout to six times the function timeout, or a slow function's batch is redelivered while it is still running.
  • A worker on ECS or EC2 runs a loop: long-poll, process, delete, with a thread pool. It is the answer when the work is long (more than 15 minutes), needs a warm connection pool or a large model in memory, or when the consumer is a legacy process. Scale the service on ApproximateNumberOfMessagesVisible divided by the task count (backlog per task), not on CPU, which is idle while waiting.
  • The order of operations is the whole story: receive, claim the business key, act, delete. Delete first and a crash loses the message; act before claiming and a crash duplicates the act; claim after acting and a crash in between does both.
  • Backpressure is free: a consumer that is slow leaves messages in the queue, and the age metric tells you. A consumer that must not fall behind needs more concurrency or a faster handler, never a bigger queue.

Idempotency: the consumer's promise

  • An operation is idempotent when running it twice has the effect of running it once. Naturally idempotent: set a value, upsert a row by key, delete by key, put an object. Not: increment, append, insert without a unique key, send an email, charge a card.
  • For the second kind, an idempotency key turns the operation into the first kind: a business id (order 4711's payment) that is stored with the result the first time, so a second run with the same key finds the record and returns the stored result. A conditional write (DynamoDB attribute_not_exists, a unique index) makes the claim atomic across concurrent duplicates; a TTL on the record bounds the table.
  • Pass the key downstream: payment providers, email APIs and your own services accept an Idempotency-Key header for exactly this reason. Lambda Powertools has an idempotency decorator that does the DynamoDB dance for you, including the in-progress state and expiry.
  • Choose the key from the business, not from the transport: the SQS message id changes when the producer retries, so a dedup on it misses the most common duplicate.

Which one, in a sentence

  • SQS: work for one of N identical workers, with a buffer. SNS: tell everyone who asked, now, cheaply, at any scale. EventBridge: route events by content across teams and accounts, with AWS and SaaS events included, and replay. Step Functions: a process with steps, retries, branches, waits and a history someone will read. Scheduler: at a time or on a schedule.
  • Kinesis: an ordered log of records many readers consume at their own pace, AWS-native. MSK: the same when you have Kafka. Amazon MQ: a broker for an application that already speaks AMQP or JMS. AppSync: push data to browsers and phones.
  • The patterns that combine them: SNS → SQS (fan-out with buffering per consumer), EventBridge → SQS → Lambda (routing with a buffer and a DLQ), SQS → Pipe → Step Functions (a queue that starts a workflow per message), Kinesis → Lambda (ordered processing per key), DynamoDB Streams → Pipe → EventBridge (changes as events).
  • What they all share: at-least-once delivery, per-key order at best, a retry policy that ends in a DLQ, and the need for a consumer that does not mind seeing a message twice.

Hands-on lab

Goal: build a standard queue with a dead-letter queue, make a message come back by letting the visibility timeout expire, watch it land in the DLQ and redrive it; measure what short polling costs; see FIFO deduplication and group locking; run a Lambda consumer that claims every message with a conditional write and skips the duplicate; fan out through an SNS topic with a filter policy; route through an EventBridge bus and schedule a message; and run a Step Functions saga with a retry and a compensation. CloudShell in ap-south-1; everything is in the free tier or within a few cents.

Cost: effectively nothing. SQS, SNS, EventBridge, Lambda and DynamoDB here stay inside the free tier; Step Functions Standard is 4,000 free transitions a month and this lab uses about 60. Delete at the end anyway so the account stays readable.

  1. Queues. A DLQ with 14 days of retention, a source queue with long polling, a 10-second visibility timeout and a redrive policy of three receives. Send five messages. 
    export AWS_DEFAULT_REGION=ap-south-1

DLQ=$(aws sqs create-queue --queue-name day11-dlq --attributes MessageRetentionPeriod=1209600 --query QueueUrl --output text)
DLQARN=$(aws sqs get-queue-attributes --queue-url $DLQ --attribute-names QueueArn --query Attributes.QueueArn --output text)
Q=$(aws sqs create-queue --queue-name day11-orders --attributes "{\"ReceiveMessageWaitTimeSeconds\":\"20\",\"VisibilityTimeout\":\"10\",\"RedrivePolicy\":\"{\\\"deadLetterTargetArn\\\":\\\"$DLQARN\\\",\\\"maxReceiveCount\\\":\\\"3\\\"}\"}" --query QueueUrl --output text)

  2. The lease. Receive one message and do not delete it. Receive again at once: it is invisible. Wait 10 seconds and receive again: it is back, with ApproximateReceiveCount 2. Do that twice more and it goes to the DLQ, never deleted, fully "processed" each time.

  4. FIFO. Content-based deduplication drops the second identical send within five minutes. Two groups: a message in flight for group A does not stop group B, but it does stop the rest of A. 
    F=$(aws sqs create-queue --queue-name day11-orders.fifo --attributes FifoQueue=true,ContentBasedDeduplication=true,VisibilityTimeout=30 --query QueueUrl --output text)
aws sqs send-message --queue-url $F --message-group-id cust-A --message-body '{"orderId":"o-100","step":"created"}' --query '[MessageId,SequenceNumber]' --output text

aws sqs send-message --queue-url $F --message-group-id cust-A --message-body '{"orderId":"o-100","step":"paid"}' --output text
aws sqs send-message --queue-url $F --message-group-id cust-B --message-body '{"orderId":"o-200","step":"created"}' --output text
aws sqs get-queue-attributes --queue-url $F --attribute-names ApproximateNumberOfMessages    # 3, not 4
aws sqs receive-message --queue-url $F --max-number-of-messages 10 --attribute-names MessageGroupId --query 'Messages[*].[Attributes.MessageGroupId,Body]' --output text
aws sqs receive-message --queue-url $F --max-number-of-messages 10 --attribute-names MessageGroupId --query 'Messages[*].[Attributes.MessageGroupId,Body]' --output text
    The first receive returns the head of A and the head of B; the second returns nothing for 30 seconds even though "paid" is waiting, because A is locked while "created" is in flight. Every message with the same group id through one consumer: that is the FIFO throughput ceiling, and why the group id must be the entity, not the tenant.

import json, os, time, boto3
ddb = boto3.client("dynamodb"); TABLE = os.environ["TABLE"]
def handler(event, context):
    failures = []
    for r in event["Records"]:
        body = json.loads(r["body"]); key = body["orderId"]
        try:
            ddb.put_item(TableName=TABLE, Item={"pk": {"S": key}, "ttl": {"N": str(int(time.time()) + 86400)}},
                         ConditionExpression="attribute_not_exists(pk)")          # the claim
        except ddb.exceptions.ConditionalCheckFailedException:
            print("DUPLICATE skipped", key, r["messageId"]); continue
        try:
            if body.get("amount") == 666: raise RuntimeError("payment provider down")
            print("CHARGED", key, body.get("amount"), r["messageId"])             # the act
        except Exception as e:
            ddb.delete_item(TableName=TABLE, Key={"pk": {"S": key}})              # release the claim so a retry can act
            print("FAILED", key, e); failures.append({"itemIdentifier": r["messageId"]})
    return {"batchItemFailures": failures}
P

Interview questions

A message is processed twice. Is that a bug? How do you make the consumer safe?

It is not a bug in the queue; it is the contract. SQS standard, SNS, EventBridge, Kinesis, Kafka and Express workflows all promise at-least-once delivery, and a second delivery has four ordinary causes: the producer's SendMessage timed out after the queue stored the message and the SDK retried it as a new message; the visibility timeout expired before the consumer finished, so the message became visible again while the first consumer was still working; the consumer did the work and then crashed, was deployed over or hit its timeout before calling DeleteMessage; and, rarely, the queue itself redelivers on an internal retry. FIFO's exactly-once processing removes only the first of those, inside a five-minute window, and only when the producer sends a deduplication id. The bug is a consumer that is not safe to run twice. I make it safe in this order. Every message carries a business key, the order id or payment id, never the SQS message id, because the message id changes on the producer's retry. The consumer claims the key before acting, with a conditional write to DynamoDB on attribute_not_exists or a unique index, so of two concurrent deliveries exactly one wins the claim and the other sees the failure and skips. The act itself is made idempotent where the downstream allows it: an upsert instead of an insert, a set instead of an increment, and the key passed to the payment provider as its idempotency key so even a retried call cannot charge twice. If the act fails, the claim is released so a retry can act; if it succeeds, the result is stored with the claim so a late duplicate can return the same answer. The message is deleted only after the work is durable, and the visibility timeout is set above the slowest honest run, six times the Lambda timeout, with an extension for long work. A dead-letter queue with a small maxReceiveCount stops a poison message after a few tries, and partial batch responses keep nine good messages out of the DLQ when one is bad. Then I say the sentence the interviewer is waiting for: exactly-once is a property of the pair, at-least-once delivery plus an idempotent consumer, and the queue sells the first half only.

Standard or FIFO? What does FIFO actually give you, and what does it cost?

FIFO gives two things: order within a message group, and producer-side deduplication for five minutes on a deduplication id or a hash of the body. It does not give a consumer that runs once; a message that is not deleted before its visibility timeout comes back, in order, and blocks its group while it does. The cost is throughput and parallelism. A group is delivered one message at a time, so the number of groups in flight is the number of consumers that can work, and a queue with one group id is a single-threaded system at 300 messages a second per API action, 3,000 batched, or more in high throughput mode which partitions by group. So I ask what needs ordering. Usually it is per entity: the events of one order, one device, one customer must be in sequence, and events of different entities do not care. Then the group id is the entity id, there are thousands of groups, and FIFO is nearly as parallel as standard. If the answer is "everything must be in global order" I ask why, because that is one consumer forever, and the usual real answer is that the consumer wants the latest state, which an idempotent upsert with a version number gives on a standard queue. I take FIFO for per-key order and for producer dedup when the producer cannot carry an idempotency key; I take standard for everything else, since its throughput is unlimited, its price is lower, and the consumer has to be idempotent either way.

How do you set the visibility timeout, and what happens when you get it wrong?

The visibility timeout is the lease: how long a received message stays hidden from other consumers. Too short and a message is redelivered while the first consumer is still on it, so every message is processed twice and, because neither attempt deletes in time, each lands in the DLQ after maxReceiveCount tries with its work done several times. The symptom is ApproximateReceiveCount above one on every message and duplicate side effects spaced exactly one timeout apart. Too long and a message whose consumer crashed waits the whole timeout before anyone else sees it: with twelve hours, a crash at 09:00 is a message processed at 21:00. So I set it just above the slowest honest run. For a Lambda consumer the rule is six times the function timeout, because the event source mapping may hold a batch through retries before invoking. For a worker, I extend the lease with ChangeMessageVisibility as the work progresses, a heartbeat, so the queue default can stay short and a crash is noticed quickly. And I never rely on the timeout for correctness: the consumer is idempotent regardless, because a timeout tuned for today's p99 is wrong on the day the database is slow.

Design the dead-letter strategy for a payment consumer.

A DLQ is for the message that cannot be processed, not for the one that failed once. The source queue gets a redrive policy with maxReceiveCount of three to five: enough for a transient error to clear, few enough that a poison message does not hammer the database for an hour. The Lambda consumer reports partial batch failures so only the failing record is retried. The DLQ has fourteen days of retention, because its clock is the original send time, and a CloudWatch alarm on ApproximateNumberOfMessagesVisible greater than zero that pages, because for payments a message in the DLQ is a customer waiting. Nobody consumes the DLQ automatically; a human reads the message, finds the cause (a schema change, a provider outage, a bug), fixes it, and redrives with StartMessageMoveTask back to the source at a limited rate, which works because the consumer is idempotent and will skip the ones that in fact succeeded. For a FIFO payment queue I keep maxReceiveCount low, two or three, because a poison message blocks its whole group until it leaves. Two things I add: the consumer never throws on a validation error, since a malformed message will never succeed and should go to a parking queue with a reason on the first try; and the DLQ itself has no redrive policy and no consumer that could loop it back.

SNS, EventBridge or Kinesis for "order placed"?

It depends on who needs it and what they do with it. If a handful of known subscribers need every event now and each should have its own buffer, SNS fanning out to one SQS queue per subscriber is the simplest and nearly free, with filter policies so the refund team is not sent the charges. If many teams, possibly in other accounts, will subscribe over time without the publisher knowing, and some of them want only orders over a hundred dollars from one Region, EventBridge: content-based rules, cross-account buses, input transforms, AWS and SaaS events on the same bus, an archive to replay the last two hours after a bad deploy, and a schema registry. It costs a dollar per million and adds about half a second, which for an event is nothing. If the readers need the events in order per customer, at tens of thousands a second, with the ability to reprocess a week of history or to feed an analytics pipeline, Kinesis: it is a log, readers keep their own position, nothing is deleted by reading, and order is per shard. The usual production answer is two of them: the order service publishes one event to EventBridge; a rule delivers it to a Kinesis stream for analytics and to SQS queues for the services that act on it; and if the team already runs Kafka, MSK takes the stream's role.

Step Functions Standard or Express? When is each the wrong answer?

Standard is a durable, exactly-once execution that can run a year, with every transition recorded and visible, priced per transition at twenty-five dollars a million. Express is a five-minute, high-volume, at-least-once run priced per request and duration, a dollar a million plus duration, with history in logs. Standard is wrong for the hot path: an event processed a thousand times a second through five states is a hundred and twenty-five dollars an hour in transitions, and Express does it for a few dollars. Express is wrong for anything that must not run twice without idempotent steps, anything over five minutes, anything with a human in it, and anything you will need to audit state by state. The split that works: Standard for the business process, order fulfilment, onboarding, approvals, with its saga and callbacks; Express for the work inside it, called as a nested workflow or as the body of a Map, and for event transforms and API compositions. Synchronous Express, started with StartSyncExecution, is the one exactly-once-ish variant: at-most-once, the caller gets the result or an error and decides about the retry. And the question behind the question: for a chain of two Lambdas with no retries or branches, neither; call the function.

Implement a saga for an order: reserve stock, charge, ship. What makes it hard?

The shape is simple: a Standard workflow with a Task per step and a Catch on each that routes to the compensations in reverse order, release stock, refund, cancel shipment, then a Fail state with a cause. The hard parts are the edges. First, a step can fail from the workflow's point of view and succeed from the service's: the charge times out after the provider accepted it. So the charge carries the order id as an idempotency key, and the compensation is a refund by that key, which is a no-op if nothing was charged; or a query step reads the real state before compensating. Second, retries: a step is retried on transient errors with backoff and a cap, which means the step runs more than once, so every step and every compensation must be idempotent. Third, partial compensation failure: the refund itself can fail, so compensations get their own retries, and the terminal state records what was and was not undone for a human, since a saga guarantees eventual consistency and not atomicity. Fourth, timeouts: TimeoutSeconds on each task so a hung provider becomes a caught error rather than a year of waiting, and a heartbeat for callback steps. Fifth, concurrency: two sagas for the same order must not interleave, so the start is guarded by the execution name being the order id, which Standard rejects as a duplicate for ninety days. What I would not do is chain the services with synchronous calls and try/catch in code: the first deploy mid-process loses the state, and nobody can see where order 4711 is.

The queue has a million messages and Lambda is draining it slowly. What do you check?

Age first, then concurrency, then the function. ApproximateAgeOfOldestMessage tells me whether this is a burst draining or a backlog growing; depth alone does not. Then Lambda's ConcurrentExecutions for the consumer against the ceilings: the event source mapping's maximum concurrency, the function's reserved concurrency, and the account's concurrency that an API may be eating. If it is flat at a round number, that is the cap. If it is at the cap and the function is fast, raise the cap or give the consumer its own account. If the concurrency is low and not capped, the mapping is still scaling, three hundred a minute from five, or the function is being throttled and the batch returned to the queue, visible in Throttles. Then the function: duration, errors, and whether a failing batch is being retried whole because partial batch responses are off, which multiplies the work by ten. Then the queue's own limits: 120,000 in flight on standard, and on FIFO the number of distinct message groups, since one group is one invocation at a time. The fixes, in order of cheapness: partial batch responses, a bigger batch with a batching window so one invocation does more, more memory for a CPU-bound handler, more groups for FIFO, a higher concurrency cap, and, if the work is steady all day, a container fleet that is cheaper than a million invocations an hour.

Why is the SQS bill higher than the compute bill?

Because SQS bills requests, not messages, and the requests you did not think about outnumber the ones you did. Every message is at least three requests, send, receive, delete, and each 64 KB of a large message is a request of its own. Then the empty receives: a worker fleet short-polling an idle queue with fifty threads makes about a thousand empty receives a second, billed at forty cents a million, which is about a thousand dollars a month for nothing. The fixes are mechanical. Set ReceiveMessageWaitTimeSeconds to twenty on the queue itself, so every client long-polls whether its author knew about it or not, and the idle cost drops twenty-fold. Batch: receive ten, delete ten in one call, send ten in one call, which cuts the per-message requests from three to a fraction. Use the Lambda event source mapping or a small number of pollers rather than a thread per container. Check NumberOfEmptyReceives on every queue, and read Cost Explorer by usage type, which separates requests from payload. One more: a VPC endpoint for SQS is a few dollars a month plus per gigabyte and replaces NAT gateway charges for consumers in private subnets, which is often the bigger line.

Kinesis or MSK? And when is SQS the better answer than either?

Both are logs: ordered per shard or partition, retained for a time you set, read by any number of consumers that keep their own position. Kinesis is the AWS-native one with nothing to operate: on-demand or shards, Lambda and Firehose and Flink integrations, retention to a year, and limits per shard that you scale by resharding. MSK is Kafka: the ecosystem of Connect, Debezium, Schema Registry, Flink and client libraries in every language, retention as long as the disk holds, hundreds of partitions per topic and hundreds of megabytes a second, and a team that knows how to run consumer groups, rebalances and compaction. I pick MSK when the organisation already speaks Kafka, needs the ecosystem, keeps data for weeks, or runs at a scale where the broker-hour pricing beats per-shard or per-gigabyte; I pick Kinesis when the consumers are Lambda and Firehose and nobody wants to think about brokers. SQS is the better answer whenever the consumers are competing workers rather than independent readers, order does not matter beyond a key, replay is not needed, and the traffic is bursty: a queue absorbs a spike without resharding, bills per request rather than per hour, and a consumer that is slow simply leaves a backlog rather than falling behind an iterator that expires. Most "streams" in a business application are queues that wanted a buffer.

We have a RabbitMQ cluster on EC2. Amazon MQ, or something else?

The question is whether the application needs RabbitMQ or merely uses it. If the code is written against AMQP with exchanges, routing keys and bindings, and the team wants to move to AWS without touching that code, Amazon MQ for RabbitMQ is the lift: a managed three-node cluster across AZs, patching and backups done, the same client libraries, and a known ceiling because it is still a broker you size. I would move it there first and measure. If the application is a set of producers and worker pools that happen to use a queue, I would migrate queue by queue to SQS and SNS during the move: no broker to size, no ceiling, per-request pricing, and no 03:00 page when memory fills and producers block. What stays on MQ for good is the protocol work: IoT devices on MQTT, a JMS application from a vendor, a STOMP client in a factory. What I would warn about: Amazon MQ failover for ActiveMQ is a reconnect of tens of seconds and the client must retry; RabbitMQ quorum queues versus classic ones change the durability story; and a broker in your VPC means security groups, endpoints and a bill per hour even at zero messages.

A dashboard needs live order updates in the browser. How?

The server has to push, so the choice is between running the WebSocket layer and renting it. AppSync rents it: a GraphQL schema with a subscription on the order-updated mutation, clients connect over WebSocket, and when the mutation runs, from the order service or from a Lambda triggered by the queue, AppSync fans the result out to every subscribed client with server-side filtering so a user sees only their orders. The Events API does the same with plain channels when GraphQL is more than you want. It is priced per update and per connection-minute, scales to many connections without a fleet, and authorises per field with Cognito or IAM. The alternative is API Gateway WebSocket APIs with a connection table in DynamoDB and a function that posts to each connection id, which is more code and the same price shape, or a container fleet with sticky connections behind an NLB, which is for when you need a protocol AppSync does not speak. The piece people forget is the plumbing behind: the order event lands on EventBridge or a queue, a consumer runs the AppSync mutation, and that consumer is idempotent, so a redelivered event does not flash the same update twice on the screen, or it carries a version number so the client discards the stale one.

EventBridge rule is not firing. Walk through the debugging.

First the bus: a custom rule on a custom bus does not see events sent to the default bus, so I check EventBusName on the PutEvents call. Second the shape: I create a catch-all rule on that bus with a CloudWatch Logs target, send one event, and read the event as EventBridge saw it, because most patterns fail on a field nested one level deeper than expected, a number sent as a string, or a detail-type with different capitalisation; then I run test-event-pattern with the logged event and my pattern until it returns true. Third the metrics: TriggeredRules for the rule, Invocations and FailedInvocations for the target; a rule that triggers but fails to invoke is a permissions problem, a missing resource policy on the queue or topic, or a missing role for an API destination or a state machine. Fourth the target's own view: a Lambda target shows an invocation in its logs or does not; an SQS target shows a message or a policy denial in CloudTrail. Fifth, throttling: ThrottledRules if the target's rate limit or the account's PutEvents quota is hit. And at the end I leave two things behind: the catch-all logging rule stays in dev, and every target gets a dead-letter queue so the next failure is a message in a queue and not a silence.
