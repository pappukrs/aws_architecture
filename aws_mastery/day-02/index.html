VPC Internals

The architecture track taught you which boxes to draw: subnet, route table, NAT gateway, security group. Today you follow one packet through those boxes. At each hop you see what is checked, what is rewritten and what is remembered. Then you break the path in six ways and learn to tell the breaks apart from a Flow Log record and a Reachability Analyzer result.

The diagram

Full picture: one HTTPS request from an instance in a private subnet, and its reply. Read the left lane downwards, then the right lane upwards. The request passes the security group, the subnet's network ACL and a route lookup. Then the NAT gateway rewrites the source address, and the internet gateway rewrites it again. The reply comes back through the same two gateways in reverse. Two things remember the connection: the security group and the NAT gateway (dashed boxes). The network ACLs and the route tables remember nothing. The monospace lines show the packet's addresses on each stretch.

Which route wins?

  

    
One route table, with routes that overlap on purpose. Pick a destination address, or type one, and say which target the packet goes to before you read the table.

    

    
Other

    

    

    
The order of the rules: the longest matching prefix wins. Only when two routes have the same destination does the type decide: a static route beats a prefix-list route, and both beat a propagated route. Among propagated routes, Direct Connect BGP beats VPN static, which beats VPN BGP. The S3 prefix list holds many ranges; one example range is shown.

  


  
How it works inside

  

    

      
IP planning and secondary CIDRs

      
    
        
  • A VPC CIDR and a subnet CIDR must each be between /16 and /28. You cannot resize either one later.
    • 
        
  • When a VPC runs out of addresses, you add a secondary CIDR and create new subnets in it. A local route for it appears in every route table.
    • 
        
  • There are rules. If the primary CIDR is in 10.0.0.0/8, you cannot add a block from 172.16.0.0/12 or 192.168.0.0/16. You can add another 10.x block or one from 100.64.0.0/10.
    • 
        
  • The new block cannot be the same as, or larger than, the destination of a route that already exists in any route table of the VPC.
    • 
        
  • You cannot remove the primary CIDR. You can remove a secondary one.
    • 
        
  • Plan so that no two VPCs overlap, in any account or Region. Overlap blocks peering, and it cannot be fixed without rebuilding.
    • 
      

    

    

      
IPv6 and dual-stack

      
    
        
  • An Amazon-provided IPv6 block for a VPC is a /56. A subnet usually gets a /64. You do not choose the range.
    • 
        
  • Every IPv6 address is globally unique, so it is public. There is no private range and no address translation.
    • 
        
  • What makes an IPv6 subnet private is only its route: ::/0 to an egress-only internet gateway instead of the internet gateway.
    • 
        
  • IPv4 and IPv6 are separate everywhere: separate routes, separate security group rules (::/0), separate network ACL rules. Opening one does not open the other.
    • 
        
  • An IPv6-only subnet reaches IPv4-only services with DNS64 on the subnet and a route for 64:ff9b::/96 to a NAT gateway, which does NAT64.
    • 
      

    

    

      
Network interfaces (ENIs)

      
    
        
  • The private IP, the security groups, the MAC address and the source/destination check belong to the ENI, not to the instance.
    • 
        
  • An ENI stays in its subnet, so it stays in one AZ. A secondary ENI can move to another instance in the same AZ and takes its addresses and security groups with it. The primary ENI cannot be detached.
    • 
        
  • Source/destination check drops packets that are not from or to the ENI's own addresses. Turn it off on anything that forwards traffic: a NAT instance, a firewall, a router.
    • 
        
  • AWS services create requester-managed ENIs in your subnets: NAT gateways, load balancers, interface endpoints, Lambda. They use your addresses and appear in your Flow Logs.
    • 
        
  • An auto-assigned public IPv4 address is released when the instance stops. An Elastic IP stays.
    • 
      

    

    

      
Route priority

      
    
        
  • The router uses the most specific route that matches the destination. This is longest prefix match.
    • 
        
  • If two routes have the same destination, a static route beats a propagated one. A prefix-list route sits between them.
    • 
        
  • The local route covers the VPC CIDR. You may add a more specific route, but its destination must be the whole CIDR of one subnet. This is how you send traffic between two subnets through a firewall.
    • 
        
  • A subnet uses exactly one route table. With no explicit association it uses the main route table. Editing a table that is not associated changes nothing.
    • 
        
  • A route table can also be associated with the internet gateway. It then steers traffic that enters the VPC, for example to a firewall endpoint.
    • 
      

    

    

      
Prefix lists

      
    
        
  • A prefix list is a named set of CIDR blocks. You use its ID in security group rules and in routes. Change the list once and every rule that uses it follows.
    • 
        
  • A customer-managed list has a maximum size that you set. In a security group or route table it counts as that maximum, not as the number of entries in use. A list sized for 20 entries costs 20 rules.
    • 
        
  • An AWS-managed list has a fixed weight. S3 and DynamoDB weigh 1. The CloudFront origin-facing list weighs 55, so one rule with it uses 55 of the 60 rules a security group has by default.
    • 
        
  • The S3 and DynamoDB lists are also what a gateway endpoint puts into your route tables (architecture Day 24).
    • 
      

    

    

      
Security group references

      
    
        
  • A rule can name another security group as its source. It then allows traffic from the private IP addresses of the network interfaces that have that group.
    • 
        
  • It copies no rules from the other group, and it counts as one rule however many instances are in that group.
    • 
        
  • It matches private addresses only. If the client calls the server's public IP, the packet arrives with a public source address and the rule does not match.
    • 
        
  • It works inside a VPC and across a peering connection in the same Region. Across a transit gateway it works for inbound rules only, and only when security group referencing is enabled on the gateway.
    • 
        
  • It does not work when the traffic between the two instances is routed through a middlebox. Use CIDR blocks there.
    • 
      

    

    

      
Stateful in practice: connection tracking

      
    
        
  • A security group lets a reply through because it tracks the connection, not because a rule matches.
    • 
        
  • Not every flow is tracked. If a rule allows TCP or UDP from 0.0.0.0/0 and the other direction allows all traffic to 0.0.0.0/0 on all ports, the flow is untracked. Flows through a NAT gateway, a Network Load Balancer or an interface endpoint are always tracked.
    • 
        
  • Remove a rule, and a tracked connection keeps working until it ends or times out. An untracked one is cut at once.
    • 
        
  • An idle tracked TCP connection is forgotten after a timeout. The default is 5 days, and 350 seconds on the newest (Nitro v6) instance types. You can set it per ENI.
    • 
        
  • Each instance type can track a limited number of connections. Past that limit, packets are dropped.
    • 
      

    

    

      
Stateless in practice: ephemeral ports

      
    
        
  • A network ACL judges every packet alone, in both directions. A reply needs its own rule (architecture Day 5).
    • 
        
  • The rule must cover the port the client chose. Many Linux kernels use 32768–61000. Windows Server 2008 and later use 49152–65535. NAT gateways, load balancers and Lambda use 1024–65535. In practice you allow 1024–65535.
    • 
        
  • The rule must also match the reply's source address. Behind a NAT gateway that is still the internet host, not the NAT gateway.
    • 
        
  • A network ACL is read when a packet enters or leaves the subnet. Traffic between two hosts in one subnet never meets it.
    • 
        
  • Neither a network ACL nor a security group can block DNS queries to the Amazon resolver. A network ACL also cannot block the instance metadata service.
    • 
      

    

    

      
NAT gateway and egress-only gateway

      
    
        
  • A NAT gateway maps many private sources to one address by giving each connection its own source port. That is why its limit is per destination: 55,000 connections at once to one destination address, port and protocol, for each of its addresses.
    • 
        
  • It handles TCP, UDP and ICMP only. It has no security group. It closes a connection that is idle for 350 seconds without telling either side.
    • 
        
  • A standard NAT gateway lives in one subnet, so in one AZ (architecture Day 4). The newer regional mode spans the AZs you use and needs no public subnet.
    • 
        
  • An egress-only internet gateway is the IPv6 answer. It is stateful, it allows connections that start inside and blocks those that start outside, and it translates nothing.
    • 
      

    

    

      
Network Firewall and Gateway Load Balancer

      
    
        
  • AWS Network Firewall puts a firewall endpoint in a subnet of its own in each AZ. It inspects only what your route tables send through that endpoint.
    • 
        
  • It has two engines. The stateless engine reads each packet alone and can pass it, drop it or hand it on. The stateful engine reads the flow, takes Suricata-compatible rules and domain lists, and writes logs.
    • 
        
  • A Gateway Load Balancer does the same job for third-party appliances. It works at layer 3, takes every packet on every port and sends it to an appliance inside a GENEVE tunnel on port 6081. A Gateway Load Balancer endpoint is the route target.
    • 
        
  • Both need to see both directions of a flow. Update the route tables for the request and for the reply.
    • 
      

    

    

      
Reachability Analyzer

      
    
        
  • It builds a model from your configuration and checks whether a path exists. It sends no packets, so it works even when the instance is stopped, and it cannot see the operating system's firewall.
    • 
        
  • A reachable result lists every hop: security group rule, network ACL rule, route. An unreachable result gives an explanation code and the component that blocks.
    • 
        
  • It reports the first blocker it finds. Fix it and run again; there may be another one behind it.
    • 
        
  • It analyses IPv4 only. Source and destination must be in the same Region.
    • 
        
  • You pay for each analysis you run.
    • 
      

    

    

      
Flow Logs

      
    
        
  • A flow log records metadata per network interface: addresses, ports, protocol, packets, bytes, and ACCEPT or REJECT. It has no payload.
    • 
        
  • ACCEPT and REJECT are the verdict of the security group and the network ACL together. The record does not say which of the two rejected. The direction pattern tells you.
    • 
        
  • One connection gives two records, one per direction. Records are aggregated over an interval, so they arrive minutes later. This is not a live view.
    • 
        
  • Not logged: DNS to the Amazon resolver, the instance metadata service, the Amazon Time Sync Service, DHCP.
    • 
        
  • The default format hides NAT. Add pkt-srcaddr and pkt-dstaddr to see the original addresses, and tcp-flags, flow-direction and traffic-path to see who started a connection and where it left the VPC.
    •

How it fails in production

  

    

      
SymptomCauseHow you find itFix

      

        Launches fail in one subnet. Auto Scaling cannot add instances, new pods or tasks stay pending, the error is InsufficientFreeAddressesInSubnet.
        The subnet has no free addresses. Every ENI takes one: instances, pods, Lambda, endpoints, load balancers.
        aws ec2 describe-subnets and read AvailableIpAddressCount. Alarm on it before it reaches zero.
        You cannot resize a subnet. Add a secondary CIDR to the VPC, create larger subnets in it and move the workload. Delete unused ENIs.
      

      

        Some new connections to one external API time out at peak. Existing connections are fine. Other destinations are fine.
        NAT port exhaustion: more than 55,000 connections at once to the same destination address and port through one NAT address.
        CloudWatch metric ErrorPortAllocation above zero on the NAT gateway. Check ActiveConnectionCount too.
        Reuse connections (keep-alive, pooling). Add secondary addresses to the NAT gateway. Spread subnets over more NAT gateways. For AWS services, use an endpoint and skip the NAT gateway.
      

      

        A connection that was idle for some minutes fails on its next use with “connection reset by peer”.
        The NAT gateway dropped it after 350 seconds of silence. It sends no FIN, so both ends still think it is open.
        CloudWatch metric IdleTimeoutCount rises. The application log shows resets on the first query after a quiet period.
        TCP keepalive below 350 seconds, or a connection pool that tests and retires idle connections.
      

      

        Connections hang after a network ACL change. Nothing is refused; calls simply time out.
        The reply is dropped. The inbound rule for ephemeral ports is missing, too narrow in ports, or limited to the VPC CIDR.
        Flow Logs: ACCEPT for the request, then REJECT for the reply with the two addresses swapped. Reachability Analyzer: SUBNET_ACL_RESTRICTION.
        Allow TCP 1024–65535 inbound from the addresses you call. Do the same check on the NAT gateway's subnet.
      

      

        Traffic through a firewall works for some flows and not for others, often depending on the AZ.
        Asymmetric routing. The request passes the firewall in one AZ and the reply returns through another AZ, or around the firewall. The stateful engine sees half a flow and drops it.
        Flow Logs on the firewall endpoint ENIs: one direction on one ENI, the other direction elsewhere. The firewall's own flow and alert logs.
        Route both directions through the same endpoint, in the AZ of the workload. Behind a transit gateway, turn on appliance mode for the inspection VPC attachment (Day 3).
      

      

        A peering request to a partner VPC cannot be created, or two networks cannot be routed to each other.
        Overlapping CIDR blocks. Peering is refused if any block of one VPC overlaps any block of the other, even blocks you do not plan to use.
        aws ec2 describe-vpcs and compare every entry in CidrBlockAssociationSet on both sides.
        Expose the one service through PrivateLink (Day 3), or use a private NAT gateway with a small routable range on each side. Long term: one address plan, enforced with IPAM.
      

      

        You removed a security group rule during an incident and the session is still alive.
        The connection is tracked. A tracked connection keeps flowing until it ends or its idle timeout passes.
        The rule is gone, yet Flow Logs still show ACCEPT for that address and port.
        Add a network ACL deny for the address. It is stateless and cuts the connection at once. Or replace the security groups on the ENI.
      

      

        A busy proxy or gateway instance drops packets while CPU and bandwidth look fine.
        The instance has reached the number of connections it can track.
        On the instance, ethtool -S eth0 shows conntrack_allowance_exceeded rising.
        A larger instance type or more instances. A shorter idle timeout on the ENI. Or rules that leave the flow untracked.

Hands-on lab

  

    
Goal: build a small VPC, prove a path with Reachability Analyzer, break one route, read the explanation, then read real Flow Log records. About 40 minutes.

    
Cost: about $0.30. Three analyses at $0.10 each are most of it. The t3.micro instance and its public IPv4 address add a cent or two for an hour, and the log data is a few kilobytes. Use a sandbox account, and run the cleanup step at the end.

    
    
      
  1. Choose a Region and build the network: a VPC, one subnet, an internet gateway and a route table with a default route.

    export AWS_DEFAULT_REGION=ap-south-1

VPC=$(aws ec2 create-vpc --cidr-block 10.20.0.0/16 \
  --tag-specifications 'ResourceType=vpc,Tags=[{Key=Name,Value=mastery-day02}]' \
  --query Vpc.VpcId --output text)
SUBNET=$(aws ec2 create-subnet --vpc-id $VPC --cidr-block 10.20.1.0/24 \
  --query Subnet.SubnetId --output text)
IGW=$(aws ec2 create-internet-gateway \
  --query InternetGateway.InternetGatewayId --output text)
aws ec2 attach-internet-gateway --internet-gateway-id $IGW --vpc-id $VPC
RTB=$(aws ec2 create-route-table --vpc-id $VPC \
  --query RouteTable.RouteTableId --output text)
aws ec2 create-route --route-table-id $RTB \
  --destination-cidr-block 0.0.0.0/0 --gateway-id $IGW
ASSOC=$(aws ec2 associate-route-table --route-table-id $RTB --subnet-id $SUBNET \
  --query AssociationId --output text)
    
      
    2. 
      
  2. Launch one instance with a public IPv4 address. It gets the VPC's default security group: all outbound allowed, nothing inbound from outside. No key pair is needed; you will not log in.

    INSTANCE=$(aws ec2 run-instances \
  --image-id resolve:ssm:/aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64 \
  --instance-type t3.micro \
  --network-interfaces "DeviceIndex=0,SubnetId=$SUBNET,AssociatePublicIpAddress=true" \
  --tag-specifications 'ResourceType=instance,Tags=[{Key=Name,Value=mastery-day02}]' \
  --query 'Instances[0].InstanceId' --output text)
aws ec2 wait instance-running --instance-ids $INSTANCE
    
      
    3. 
      
  3. Turn on Flow Logs for the VPC, delivered to CloudWatch Logs with a 1-minute interval. The service needs a role it can assume.

    aws logs create-log-group --log-group-name /mastery/day02/flow

cat > trust.json <<'EOF'
{"Version":"2012-10-17","Statement":[{"Effect":"Allow",
  "Principal":{"Service":"vpc-flow-logs.amazonaws.com"},"Action":"sts:AssumeRole"}]}
EOF
cat > perms.json <<'EOF'
{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Action":[
  "logs:CreateLogGroup","logs:CreateLogStream","logs:PutLogEvents",
  "logs:DescribeLogGroups","logs:DescribeLogStreams"],"Resource":"*"}]}
EOF
ROLE_ARN=$(aws iam create-role --role-name mastery-day02-flowlogs \
  --assume-role-policy-document file://trust.json --query Role.Arn --output text)
aws iam put-role-policy --role-name mastery-day02-flowlogs \
  --policy-name publish --policy-document file://perms.json
sleep 15   # give IAM time to make the new role usable

FLOWLOG=$(aws ec2 create-flow-logs --resource-type VPC --resource-ids $VPC \
  --traffic-type ALL --log-destination-type cloud-watch-logs \
  --log-group-name /mastery/day02/flow --deliver-logs-permission-arn $ROLE_ARN \
  --max-aggregation-interval 60 --query 'FlowLogIds[0]' --output text)
    
      
    4. 
      
  4. Create a Reachability Analyzer path from the instance to the internet gateway and analyse it. Repeat the last command until status is succeeded.

    NIP=$(aws ec2 create-network-insights-path --source $INSTANCE --destination $IGW \
  --protocol tcp --destination-port 443 \
  --query NetworkInsightsPath.NetworkInsightsPathId --output text)

NIA1=$(aws ec2 start-network-insights-analysis --network-insights-path-id $NIP \
  --query NetworkInsightsAnalysis.NetworkInsightsAnalysisId --output text)
aws ec2 describe-network-insights-analyses --network-insights-analysis-ids $NIA1 \
  --query 'NetworkInsightsAnalyses[0].{status:Status,found:NetworkPathFound,hops:ForwardPathComponents[].Component.Id,why:Explanations[].ExplanationCode}'
    
        Expect found: true. Read hops: the network interface, the security group, the network ACL, the route table and the internet gateway appear in the order the packet meets them.
      
    5. 
      
  5. Break the route and analyse the same path again. No packet is sent; only the configuration changed.

    aws ec2 delete-route --route-table-id $RTB --destination-cidr-block 0.0.0.0/0

NIA2=$(aws ec2 start-network-insights-analysis --network-insights-path-id $NIP \
  --query NetworkInsightsAnalysis.NetworkInsightsAnalysisId --output text)
aws ec2 describe-network-insights-analyses --network-insights-analysis-ids $NIA2 \

Interview questions

  
An instance cannot reach the internet. List the six things you check, in order.
(1) The route: which route table the subnet really uses, explicit or main, and whether it has 0.0.0.0/0 to an internet gateway or a NAT gateway. (2) The target of that route: the internet gateway is attached, or the NAT gateway is available and sits in a subnet whose own route table points to the internet gateway. (3) The public address: the instance has a public IPv4 address if it goes straight to the internet gateway, or the NAT gateway has its Elastic IP. (4) The security group's outbound rules for the destination port. (5) The network ACLs in both directions, including inbound ephemeral ports for the reply, on the instance's subnet and on the NAT gateway's subnet. (6) DNS and the host: the name resolves, and no proxy setting or operating-system firewall is in the way. I confirm with Reachability Analyzer for the configuration and Flow Logs for the real traffic.

  
The security group allows all outbound traffic and the network ACL allows outbound 443. HTTPS calls still hang. Why, and what do the Flow Logs show?
The network ACL is stateless, so the reply needs an inbound rule of its own. The reply arrives on the client's ephemeral port, from the server's address. Without an inbound allow for TCP 1024–65535 from that address, it is dropped. The flow log on the instance's network interface shows ACCEPT for the outgoing record and REJECT for the incoming one. A security group would never produce that pair, because it lets the reply of a tracked connection through.

  
A route table has 10.0.0.0/8 to a transit gateway, 10.50.0.0/16 to a peering connection, the same 10.50.0.0/16 propagated from a virtual private gateway, and a propagated 10.50.8.0/24. Where do packets for 10.50.1.9 and 10.50.8.4 go?
10.50.1.9 goes to the peering connection. The longest match is the /16, two routes have it, and a static route beats a propagated one. 10.50.8.4 goes to the virtual private gateway. The /24 is the longest match, and prefix length is compared first; static against propagated matters only when the destinations are identical.

  
During an incident you remove the inbound SSH rule from a security group. The attacker's session stays open. Why, and how do you cut it now?
The session is a tracked connection. Removing the rule stops new connections, but a tracked one continues until it closes or its idle timeout passes, which can be days. To cut it at once, add a network ACL deny for the attacker's address on that subnet. It is stateless and applies to the next packet. If the rule had allowed SSH from 0.0.0.0/0 and outbound was open to everything, the flow would have been untracked and removing the rule would have cut it immediately.

  
A service behind a NAT gateway calls one payment API very often. At peak, some new connections time out. What do you check, and what are the fixes?
I check the NAT gateway's ErrorPortAllocation metric. Above zero means it could not allocate a source port: more than 55,000 connections at once to the same destination address and port through one NAT address. Fixes, in order of preference: reuse connections with keep-alive and a pool, so fewer exist; add secondary IP addresses to the NAT gateway, each adds 55,000; split the subnets over more NAT gateways. I also look at IdleTimeoutCount, because idle connections that are never closed hold ports.

  
Why does IPv6 need no NAT gateway, and what keeps an IPv6 instance private?
NAT exists for IPv4 because private addresses are not routable and public ones are scarce. Every IPv6 address in a VPC is globally unique and routable, so nothing needs translating. Privacy comes from routing instead: the private subnet sends ::/0 to an egress-only internet gateway. It is stateful, lets connections out and their replies back, and refuses connections that start from the internet. Security groups still apply and need their own IPv6 rules.

  
Your VPC is 10.0.0.0/16 and nearly full. What are your options, and what can you not do?
I cannot resize the VPC CIDR or any subnet. I can associate a secondary CIDR, up to five blocks by default, and create new subnets there. Because the primary block is in 10.0.0.0/8, the new block must also be a 10.x range, a 100.64.0.0/10 range or a public range; 172.16.0.0/12 and 192.168.0.0/16 are refused. It must not overlap any peered VPC, and it must not be the same as or larger than the destination of an existing route. I also look for waste first: unused ENIs, oversized subnets that sit empty, and workloads that could move to IPv6.

  
What does a Flow Log record not tell you?
It has no payload, only addresses, ports, protocol, counters and ACCEPT or REJECT. It does not say whether the security group or the network ACL rejected; I work that out from which direction was rejected. It is the verdict of those two only, so a packet lost to a missing route or at the internet gateway still shows as accepted. It leaves out DNS to the Amazon resolver, the metadata service, time sync and DHCP. It is aggregated and delayed by minutes. And in the default format it shows the NAT gateway's address, not the original one, unless I add pkt-srcaddr and pkt-dstaddr.

  
When do you add Network Firewall on top of security groups and network ACLs, and what must be true of the routing?
When the rule cannot be written as address and port: allow outbound HTTPS only to a list of domain names, detect known attack patterns, or log which rule matched each flow. Also when many VPCs need one inspection point. The firewall inspects only what the route tables send through its endpoint, so I change the routes for both directions: the workload subnet's default route to the endpoint, and a route table on the internet gateway that sends return traffic for that subnet to the same endpoint. Both directions must pass the same endpoint, or the stateful engine sees half a flow.

  
A security group rule names another security group as its source. When does that work, and when does it fail?
It allows traffic from the private IP addresses of the network interfaces that have the named group. It works inside one VPC and across a peering connection in the same Region. Across a transit gateway it works only for inbound rules and only with security group referencing enabled. It fails across an inter-Region peering connection, when the client uses the server's public IP address, and when the traffic is routed through a middlebox appliance. In those cases I use CIDR blocks or a prefix list.
