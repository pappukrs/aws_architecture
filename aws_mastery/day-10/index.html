Caching and purpose-built databases

A cache is the cheapest way to make a database look fast, and the most common way to make one fall over. At a 99% hit ratio the database behind the cache is sized for one request in a hundred; the day the cache node restarts, it gets all hundred. This page is about that day. First the cache itself: ElastiCache with Redis OSS or Valkey against Memcached, cluster mode and hash slots, replicas and failover, memory, eviction policies, lazy loading against write-through, TTLs and the stampede. Then the stores built for one shape of data, where a cache is still the same problem: MemoryDB when the cache is the database, OpenSearch for search and logs, DocumentDB for JSON, Neptune for graphs, Keyspaces for wide rows, Timestream for time series, and Redshift for the warehouse. The centre of the page is the interview question: the cache node restarts and the database falls over. Why, and how do you prevent it?

The diagram

The whole picture. The application connects over TCP to a cache that lives in its own subnets. With Redis OSS or Valkey and cluster mode disabled, one shard holds every key: a primary that takes writes and replicas in other AZs that take reads, with a primary endpoint whose DNS flips at failover and a reader endpoint over the replicas. With cluster mode enabled, the 16,384 hash slots are split across shards, each a primary with replicas, behind a configuration endpoint; keys with the same hash tag stay together and a command across slots fails. Memcached is simpler and more fragile: nodes without replication, the client decides which node holds which key. The patterns box is what the application does: lazy loading fills the cache on misses with a TTL, write-through fills it on writes, and the memory settings decide what happens when it is full. The database on the left sees only the misses, which is the whole point and the whole danger. MemoryDB on the right is the same API with a durable transaction log, a database rather than a cache. Model: on a normal day the database sees reads × (1 − hit ratio). When a node restarts, the keys it held are gone: all of them for a single node or a cluster-mode-disabled primary without a replica, a third for one shard of three, a quarter for one Memcached node of four; with a Multi-AZ replica the keys survive on the replica and the cost is a window of about 30 seconds while DNS and the clients move. During the storm, requests concentrate on the hottest third of the working set, so request coalescing caps the database load at that many distinct keys a second. A database pushed past its capacity without a breaker thrashes: its effective throughput is taken as half of its capacity, which is why the refill takes so long. The refill time is the cold keys divided by what the database actually delivers, times 1.5 for duplicate fetches when there is no coalescing.

Lazy loading or write-through: what the cache saves and costs

Lazy loading fills the cache on a miss; write-through fills it on every write. The first caches what is read and goes stale for up to a TTL; the second is always fresh and doubles every write, and it caches what is written whether or not anyone reads it. Pick the pattern, the traffic and the TTL. With lazy loading every active key is re-read from the database once per TTL, so the misses are the active keys divided by the TTL, capped at the read rate for each group; the keys in memory are the ones read within one TTL. With write-through alone the cache holds only keys written within the TTL, and reads of anything else miss. With both, the keys are as for lazy loading, the values are fresh, and the cache takes the writes as well. Each key costs its value plus about 100 bytes of overhead; a node's usable memory is 75% of its RAM, the rest reserved for replication and snapshots. Node prices are us-east-1 Redis OSS on-demand (Valkey is about 20% less); serverless is $0.125 per GB-hour of data plus $0.0034 per million ECPUs, one ECPU per KB of each command. The database reads avoided are priced as DynamoDB eventually consistent reads at $0.125 per million request units, as a floor; against RDS the saving is an instance size.

How it works inside

What ElastiCache is

  • A managed in-memory key-value store in your VPC: you choose an engine (Redis OSS, its fork Valkey, or Memcached), a node type, a subnet group and a security group, and get an endpoint. The data lives in RAM, so reads and writes are sub-millisecond and the price is per GB of memory, not per GB of disk.
  • Two deployment forms. Node-based: you pick node sizes and counts and pay per node-hour. Serverless: you pick an engine, AWS runs the shards, and you pay per GB-hour stored and per ECPU consumed; it scales within about a minute and starts around $90 a month for a 1 GB cache that is barely used.
  • Valkey is the engine to pick for anything new: the same commands and wire protocol as Redis OSS 7.2, lower prices, and it is where AWS and the Linux Foundation put their development.
  • What it is not: durable. A node restart loses its memory, snapshots are periodic, replication is asynchronous. Anything that must survive a restart goes to MemoryDB or a database.

Redis / Valkey against Memcached

  • Memcached is a multi-threaded cache of strings, up to 1 MB each by default: no replication, no persistence, no failover, no data structures. The client hashes each key to a node, so a cluster of four nodes is four independent caches, and losing one loses a quarter of the keys until the client remaps them. Auto discovery tells the client the node list.
  • Redis OSS / Valkey is single-threaded for commands (I/O threads since 6.0 help with the network), with data structures: hashes, lists, sets, sorted sets, streams, HyperLogLog, geo, bitmaps, plus Lua scripts, pub/sub and transactions. It replicates to replicas, snapshots to S3, and fails over.
  • Choose Memcached only for a pure cache of large flat values where you want to use every core of a big node and can tolerate losing a node's keys. Choose Redis or Valkey for everything else: sessions, leaderboards, rate limits, queues, locks, and any cache you would rather not lose at once.
  • Neither is a database. Memcached cannot be, and Redis in ElastiCache is tuned as a cache: appendonly is not available, and a cluster restart from a snapshot is minutes old.

Cluster mode disabled or enabled

  • Disabled: one shard, one primary, up to five read replicas, all 16,384 hash slots on the one primary. Writes scale to one node's memory and one core; reads scale by replicas through the reader endpoint. Simple clients, every command works, the dataset must fit one node.
  • Enabled: the slots are split across up to 500 shards, each a primary with up to five replicas. The client talks to the configuration endpoint, learns the slot map, and sends each command to the shard that owns CRC16(key) mod 16384; a wrong guess gets a MOVED redirect. Writes and memory scale with shards; online resharding moves slots without downtime.
  • Multi-key commands, transactions and Lua scripts need every key on one shard: put the part you want hashed in braces, {user:42}:cart and {user:42}:profile, and the slot is computed from user:42 only. Otherwise: CROSSSLOT Keys in request don't hash to the same slot.
  • Turn cluster mode on from the start if the dataset might ever exceed one node or the write rate one core; the switch later is a migration, and the client library must be cluster-aware.

Replication and failover

  • Replicas receive the primary's write stream asynchronously. ReplicationLag is normally milliseconds, and a read from a replica can return a value a moment old; a failover promotes the replica with the most data, and the writes still in flight to the old primary are lost.
  • Multi-AZ with automatic failover needs at least one replica in another AZ. When the primary fails its health checks, a replica is promoted and the primary endpoint's DNS is repointed; clients that cache DNS or hold dead connections keep failing until they reconnect, which is why a client with a short DNS TTL and a reconnect-on-error policy matters as much as the setting.
  • Failover typically completes in under a minute for cluster mode disabled; cluster mode enabled is faster because the slot map changes and cluster-aware clients follow it without DNS. aws elasticache test-failover rehearses it; every production cluster should have had one.
  • Without a replica, a node failure or a maintenance replacement is a cold cache: a new node, empty, with the same endpoint. That is the day of the question at the top of the page.

Memory, eviction, reserved memory

  • maxmemory is set by the node type. When the data reaches it, maxmemory-policy decides: allkeys-lru evicts the least recently used key of any kind, the right choice for a pure cache; volatile-lru, volatile-ttl and volatile-lfu evict only keys that have a TTL, so a cache with keys without TTLs fills up and then errors; noeviction (the default in some parameter groups) returns OOM command not allowed on writes.
  • Evictions above zero means the cache is smaller than the working set; the hit ratio falls and the database warms up. Either grow the node, add shards, shorten TTLs, or shrink the values.
  • reserved-memory-percent, 25% by default, keeps RAM free for the fork that a snapshot (BGSAVE) and a full replica sync need: the forked child shares pages copy-on-write, and under heavy writes the copies can double memory. Set it to zero and the node swaps, then gets replaced. SwapUsage above a few MB is the symptom.
  • Big keys and big values hurt twice: a 10 MB hash blocks the single thread while it is serialised, and a DEL of it blocks too (use UNLINK). Values over a few hundred KB belong elsewhere.

Caching patterns

  • Lazy loading (cache-aside): read the cache; on a miss read the database and write the cache with a TTL. Only requested data is cached, a node failure is a performance problem not a correctness one, and the price is a stale window of up to a TTL after every write, plus a miss penalty of two round trips.
  • Write-through: every write to the database also writes the cache. Reads of written data are always fresh and never miss; the price is a write penalty, memory spent on data nobody reads, and a cache that is empty after a restart until something is written again. In practice it is combined with lazy loading and a TTL, so the cache self-heals.
  • Write-behind: write the cache and let a worker write the database later. Fast and dangerous: a lost node loses the writes. ElastiCache does not do this for you; MemoryDB's log is the honest version.
  • The details that decide the production experience: a TTL with jitter so a batch of keys does not expire in the same second; negative caching of "not found" for a short TTL, because the database lookup that returns nothing is the one scripts hammer; versioned keys (user:42:v7) instead of invalidation when the schema changes; and the fallback decision: on a cache error, does the application read the database, or fail?

The stampede

  • One hot key expires. Every request in the next few milliseconds misses, and each one reads the database and writes the cache: a thousand identical queries for one value. Multiply by a cold node and it is every key at once. The names: cache stampede, thundering herd, dog-piling.
  • Request coalescing (single flight): the first miss for a key takes a short lock (SET key:lock 1 NX PX 2000) and reads the database; the others wait for the value or serve the stale one. One database read per key per expiry.
  • Stale-while-revalidate: store the value with a logical expiry inside it and a physical TTL well beyond; past the logical expiry, serve the stale value and refresh it in the background. The database sees a trickle, and a database outage degrades to stale data instead of errors.
  • Probabilistic early expiration: each read refreshes the value early with a probability that rises as the TTL nears, so hot keys never expire at all. And the blunt protection that always works: a rate limit or circuit breaker on the database client, so excess misses fail fast instead of queueing on the one resource that cannot shed load.

Snapshots, backups, maintenance

  • A snapshot is an RDB file written to S3: a point-in-time copy made by a forked child, daily on a schedule or on demand, kept up to 35 days, and the only way to seed a new cluster with data. It is minutes to hours old; it is not a durability story.
  • Take snapshots from a replica, not the primary: the fork costs memory and CPU on the node that does it. On small nodes without enough reserved memory, a snapshot is itself a cause of the restart.
  • Every cluster has a weekly maintenance window; engine patches and node replacements happen inside it, and a cluster without a replica goes cold then. Choose the window, subscribe to the ElastiCache events (ElastiCache:NodeReplacementScheduled, FailoverComplete) through SNS, and plan for it as you would for a deploy.
  • Scaling: vertical (node type) is online for replication groups with a replica, with a failover; horizontal is replicas for reads, shards for writes and memory, both online. Serverless does all of this without you, within a minute, with a configurable maximum.

MemoryDB

  • The Redis / Valkey API as a durable database: every write is appended to a Multi-AZ transaction log before it is acknowledged, replicas read from the log, and a failover loses nothing. Snapshots to S3 come from the log. Reads are microseconds, writes single-digit milliseconds because of the log round trip.
  • Shards and replicas like cluster mode enabled: up to 500 shards, five replicas each, online scaling. Vector search is built in, which makes it a candidate for a durable vector store with sub-millisecond lookups.
  • The price is roughly two to three times ElastiCache for the same memory, plus $0.20 per GB written. That is the price of not needing a database behind it; a session store, a game state, a feature store, a leaderboard that must be right, or a queue of jobs that must not vanish can run on MemoryDB alone.
  • Decision: ElastiCache when the data has another home and losing the cache is a performance incident; MemoryDB when the data has no other home. DAX when the home is DynamoDB and you want no application change.

OpenSearch

  • A distributed inverted index: documents go into an index, which is split into primary shards, each copied to replica shards on other nodes; a query fans out to one copy of every shard and merges the results. Full-text relevance, aggregations, geo, and k-NN vector search in one engine; it is the backbone of log analytics and site search.
  • Sizing is about shards: aim for 10–50 GB per shard, few shards per index, and keep the shard count per node in the hundreds, because every shard costs heap. JVMMemoryPressure above 75% sustained means garbage collection is eating the node; above 95% it stops indexing. Disk at 85% stops shard allocation, at 95% the index goes read-only (flood stage).
  • Managed domains: dedicated master nodes (three) for anything serious, data nodes across three AZs, UltraWarm and cold storage for old log indices on S3, Index State Management to roll and delete indices by age. OpenSearch Serverless removes the sizing and charges per OCU-hour, with a floor of two OCUs for indexing and two for search in production.
  • It is not a system of record: writes are near-real-time (refresh interval, 1 s by default), there are no transactions, and a cluster block turns a logging pipeline into a backlog. Data arrives by Firehose, Logstash, Data Prepper, or a DynamoDB zero-ETL integration.

DocumentDB and Keyspaces

  • DocumentDB is a MongoDB-compatible API (currently up to the 5.0 wire protocol) on an Aurora-style architecture: one writer, up to 15 readers, storage that grows to 128 TiB and replicates six ways across three AZs, point-in-time recovery, and global clusters. Documents up to 16 MB, flexible schema, indexes on nested fields. It is the pick when a team writes MongoDB queries and you want Aurora's operations; not every MongoDB feature exists, so test the application's query log against the compatibility list first. Elastic clusters shard the writes across several nodes when one writer is not enough.
  • Keyspaces is a Cassandra-compatible API (CQL) run like DynamoDB: no nodes, per-request or provisioned capacity, unlimited table size, point-in-time recovery, and a row up to 1 MB. Partition key plus clustering columns, the same hot-partition rules as Day 9, lightweight transactions for conditional writes. It is for teams with Cassandra data models and drivers who want to stop running Cassandra, and for time-ordered wide rows per partition.
  • Both are "same API, AWS operations". The question to ask is whether the API is the point. If the application is new, DynamoDB usually wins against Keyspaces and against DocumentDB for known access patterns, and Aurora PostgreSQL with jsonb wins against DocumentDB when the documents are queried in ad hoc ways.

Neptune

  • A graph database: vertices and edges with properties, queried in Gremlin or openCypher (property graph) or SPARQL (RDF). Aurora-style storage, one writer, up to 15 readers, 128 TiB, global database. Neptune Analytics loads a graph into memory for algorithms like PageRank and community detection; Serverless scales the compute by NCU.
  • It wins when the question is traversal: who is within three hops, what is connected to this and that, which path exists. In SQL that is a self-join per hop whose cost explodes; in a graph each hop follows pointers. Fraud rings, identity resolution, knowledge graphs, recommendations, network topology, access control with inheritance.
  • It loses when the question is a lookup or a scan: a friends list is a DynamoDB adjacency list (PK = user, SK = FRIEND#id) at a fraction of the cost. Model the queries first; one or two hops over known keys is not a graph workload.
  • The floor is high: a db.r6g.large writer and reader is about $500 a month before storage and I/O, and Serverless has a 1 NCU minimum per instance. Bulk loads come from S3 in CSV or RDF; it is not an analytics engine for a billion-edge graph without Neptune Analytics.

Timestream

  • Timestream for LiveAnalytics: serverless time-series storage with SQL and time functions. Records carry a timestamp, dimensions (device, Region) and measures; writes land in a memory store (retention from an hour to a year) and age into a magnetic store (up to 200 years) automatically, with a price per GB-hour in memory, per GB-month on magnetic, and per GB scanned by queries. Late-arriving data within the memory retention is accepted. Scheduled queries pre-aggregate for dashboards.
  • Timestream for InfluxDB: managed InfluxDB on instances, for teams with the InfluxDB API, Flux and Telegraf already in place.
  • It wins for metrics and telemetry queried by series and time range with aggregates; it loses for anything queried by key, where DynamoDB with a device-plus-time key is cheaper, and for heavy analytics over everything, which is an S3 and Athena or Redshift job. Watch the query cost: a dashboard that scans a year of raw data every refresh is priced by the terabyte.

Redshift

  • A columnar, massively parallel data warehouse: a leader node plans a query, compute nodes each scan their slice of the columns, compressed, with sort keys and distribution styles deciding how much each node reads and whether a join needs a shuffle. Aggregates over billions of rows in seconds; single-row lookups in hundreds of milliseconds, which is why it is never behind a web request.
  • RA3 nodes separate compute from managed storage on S3 with a local SSD cache, so you size compute for the queries and pay $0.024 per GB-month for data. Serverless charges per RPU-second with an 8 RPU base; concurrency scaling adds transient clusters for queue spikes, an hour a day free; Spectrum queries S3 directly, data sharing gives other clusters and accounts live read access, and zero-ETL from Aurora and DynamoDB replicates tables in without a pipeline.
  • The lake question of Day 22 in one line: Athena when the data is in S3 and queries are occasional, Redshift when the same analysts run many queries a day over the same curated tables and want sub-second dashboards, and both when the lake is the source and Redshift is the serving layer.
  • Operations that bite: VACUUM and ANALYZE (mostly automatic now), workload management queues and query timeouts, disk full on DC2 nodes, and the cost of a cluster running 24 hours for a 9-to-5 team; pause it, or go serverless.

  6. The stampede, and the lock that stops it. Fifty threads miss the same key at the same moment. Without coalescing, every thread reads DynamoDB; with a SET NX lock, one does and the others wait for the value. 
    cat > stampede.py <<'PY'
import boto3, json, os, redis, sys, threading, time
r = redis.Redis(host=os.environ['PRI'], port=6379, ssl=True)
t = boto3.resource('dynamodb').Table('day10-products')
LOCK = sys.argv[1] == 'lock'; db_reads = 0; lk = threading.Lock()
def read_db(pid):
    global db_reads
    with lk: db_reads += 1
    time.sleep(0.05)                                   # a 50 ms query
    return t.get_item(Key={'id': pid})['Item']
def get(pid):
    key = f'product:{pid}'
    v = r.get(key)
    if v: return json.loads(v)
    if LOCK:
        if r.set(key + ':lock', 1, nx=True, px=2000):   # single flight
            item = read_db(pid); r.set(key, json.dumps(item, default=str), ex=300); r.delete(key + ':lock'); return item
        for _ in range(100):                             # the others wait for the value
            time.sleep(0.01); v = r.get(key)
            if v: return json.loads(v)
    item = read_db(pid); r.set(key, json.dumps(item, default=str), ex=300); return item
r.delete('product:p7', 'product:p7:lock')
th = [threading.Thread(target=get, args=('p7',)) for _ in range(50)]
t0 = time.time(); [x.start() for x in th]; [x.join() for x in th]
print(f'{sys.argv[1]}: 50 concurrent misses → {db_reads} DynamoDB reads in {time.time()-t0:.2f} s')

Interview questions

The cache node restarts and the database falls over. Why, and how do you prevent it?

The why is arithmetic. A cache with a 99% hit ratio lets you run a database sized for one read in a hundred, and that is exactly what most teams do, because the cheap database is the point of the cache. When the node restarts it comes back empty, and for the next minutes every read is a miss: the database sees a hundred times its normal load. It cannot shed it: connections fill, queries queue, latency climbs, clients time out and retry, which adds more load, and the cache refills slowly because each miss now takes seconds instead of milliseconds, so the storm lasts longer than the working set would suggest. It is not the cache that failed; it is the database that was never sized for its miss rate. Prevention is in layers. First, the cache should not go cold: a replica in another AZ with Multi-AZ automatic failover means a restart promotes a warm replica in under a minute, and a cluster-mode cluster loses a shard's share, not everything. Second, the application must not amplify a miss: request coalescing so that one database read serves every concurrent miss for the same key, TTLs with jitter so keys never expire together, and stale-while-revalidate so a stale value is served while one refresh runs in the background. Third, the database must be protected from the storm that gets through: a rate limit or circuit breaker on the database client at the capacity you measured, so excess misses fail fast and the database keeps serving, and a database with enough headroom for the miss rate you decided to accept, say ten times normal rather than a hundred. Fourth, warm the cache on purpose after a replacement, from a snapshot or a list of hot keys, and rehearse with a test failover and a load test that starts flushed. And the honest conclusion: if the business cannot survive the cache being lost, it is not a cache but a database, and it should be MemoryDB or DAX, which fail over warm. I would end by saying the monitoring: alarm on hit ratio, evictions and swap, because a cache that is slowly shrinking is the same outage in slow motion.

Redis or Memcached? Give the real reasons, not the feature list.

Memcached is a multi-threaded cache of strings with no replication, no persistence and no failover; the client hashes keys across nodes, so a node loss costs that node's keys, and a change in the node list reshuffles keys unless the client uses consistent hashing. It is simple and it uses every core, which is why it remains the answer for one case: a large flat cache of big values, where the loss of a node is a brief dip in hit ratio and throughput per node matters more than anything else. Redis OSS or Valkey is single-threaded for commands, which caps one shard at one core, but it replicates, snapshots, fails over, and has data structures: sorted sets for leaderboards, hashes for objects, streams for queues, atomic counters with expiry for rate limits, Lua for compound operations. Those features turn it from a cache into the shared state of a stateless fleet. So the real question is whether losing the node is acceptable and whether you need anything but GET and SET. For almost every team the answer is Redis or Valkey with cluster mode enabled and a replica per shard, and Valkey specifically because it is the engine AWS prices lower and develops. I would say what neither is: a database. ElastiCache Redis has no append-only log and its snapshot is minutes old; if the data has no other home, MemoryDB.

Cluster mode enabled or disabled? What changes for the application?

Cluster mode disabled is one shard: one primary with all 16,384 slots, up to five replicas for reads, a primary endpoint and a reader endpoint. The dataset must fit one node's memory and the writes one core; every command works; any client works. Cluster mode enabled splits the slots over up to 500 shards, each a primary with replicas, behind a configuration endpoint; the client fetches the slot map and routes each key with CRC16 modulo 16384, following MOVED redirects when the map changes. Writes and memory scale with shards, resharding is online, and a shard failure affects a fraction of the keys. The application pays in three places: the client library must be cluster-aware; multi-key commands, transactions and scripts need every key on one shard, which means hash tags like {user:42} in the key names, and that is a change to every key format in the codebase; and operations like SCAN or FLUSHALL become per-shard. My rule is to enable cluster mode from the first day for anything that could grow, because the migration later is a key-naming project under pressure, and to keep it disabled only for small caches with legacy clients. Serverless is cluster mode enabled underneath, so the same hash-tag discipline applies there.

Lazy loading or write-through? When does each one hurt?

Lazy loading reads the cache, on a miss reads the database and writes the value with a TTL. It caches what is read, so memory is spent only on live keys, and it tolerates a cache failure as a performance problem. It hurts in two ways: every miss costs two round trips plus the database read, which under a cold cache is the storm; and a write to the database does not touch the cache, so a value is stale for up to a TTL unless the write path invalidates it. Write-through writes the cache on every database write. Reads of recently written data never miss and are never stale; it hurts because every write costs twice, because memory is spent on data nobody reads, and because after a node loss the cache is empty until something is written, which for a read-heavy catalogue could be forever. In practice I use both: write-through or delete-on-write for freshness, lazy loading with a jittered TTL as the safety net that repopulates after any loss and bounds the staleness of anything the write path missed. The TTL is a product decision, not a technical one: how old may this value be? Sessions can be seconds stale, prices cannot, an avatar can be a day. And on the write side I would say the thing that is not a pattern but a decision: what the application does when the cache is down. Read through to the database with a breaker, or fail the request; whichever it is, it is decided in code before the day it matters.

Evictions started appearing on a cache that has run for a year. What do you do?

Evictions mean the node is full and the policy is removing keys to make room, so the hit ratio is about to fall and the database is about to take the difference. I look at three things in order. Memory: DatabaseMemoryUsagePercentage at the ceiling, and whether the growth is the working set or garbage; redis-cli --bigkeys and --memkeys tell me what is large, and a scan of TTLs tells me whether keys are being written without an expiry, which is the usual cause of a cache that fills slowly over a year. Policy: allkeys-lru is right for a cache, and if it is volatile-lru and some keys lack TTLs the node will fill and then error instead of evicting. Reserved memory: 25% should be there, or the next snapshot will swap. Then the fix depends on what I found. Keys without TTLs get them, with jitter. A larger working set gets a bigger node or another shard, scaled online with a replica in place. Values that are too large get trimmed or moved to S3 with a pointer. And I alarm on Evictions above zero and on hit ratio below the design value, because this is exactly the signal that arrived before the outage and nobody was watching.

Latency went up; CPU on the cache node is 9%. Where is the time going?

Redis executes commands on one thread, so CPUUtilization across a sixteen-core node hides a saturated core; EngineCPUUtilization is the metric, and at 9% overall it is probably near 100%. Then SLOWLOG GET: the usual suspects are KEYS with a pattern, SMEMBERS or HGETALL on a structure with a million members, a Lua script that loops, or a DEL of a huge key that blocks while it frees memory, for which UNLINK exists. The fix is to replace the command, then to spread the load: replicas for reads through the reader endpoint, shards for writes. If the engine CPU is low too, I look at the network and the client: TLS handshakes from an application that opens a connection per request, which shows as NewConnections; a cross-AZ hop on every call; a pool too small so requests queue in the client; or a big value that saturates the node's network bandwidth. And I check for a snapshot or a replica sync in progress, because the fork costs CPU and memory on the node that does it, which is why snapshots belong on a replica.

ElastiCache, DAX or MemoryDB for a session store?

I start with what a lost session costs. If a user being logged out during a cache failover is an acceptable incident, ElastiCache Valkey with a replica and Multi-AZ failover is the cheapest answer, and the session has a TTL anyway. If a session holds state that must not vanish, a half-finished checkout, a game in progress, a shopping cart that the product promises to keep, then losing a node must lose nothing, and that is MemoryDB: the same API, every write in a Multi-AZ transaction log before it is acknowledged, failover without data loss, at two to three times the price of ElastiCache and with single-digit millisecond writes instead of sub-millisecond. DAX is the answer only when the session already lives in DynamoDB and the goal is read latency with no code change; it is a read-through, write-through cache for one store, eventual reads only. In many systems the right split is two stores: DynamoDB as the durable session record with a TTL, and ElastiCache as a read cache in front for the hot path, which is also the setup where the cache can be lost without consequence. What I avoid is the half-measure: an ElastiCache cluster treated as durable because it has a replica, since replication is asynchronous and a failover drops the last writes.

Design the OpenSearch domain for 2 TB a day of logs kept for 90 days.

I size by shards and by tiers. Daily indices, so retention is a delete and the hot tier holds a known number of days. 2 TB a day of raw logs is about 2 TB indexed with compression and field choices, maybe more with replicas: with one replica that is 4 TB a day on disk. Shards of 30 to 50 GB: 40 to 60 primary shards per daily index, spread over the data nodes. Hot for seven days is about 28 TB with replicas, on instances with enough heap for that shard count, which puts me at a dozen or more r-family data nodes with gp3 volumes, across three AZs, plus three dedicated master nodes. Days 8 to 90 go to UltraWarm, which stores them on S3 behind a cache and costs a fraction, and an Index State Management policy does the rollover, the move and the delete. Ingestion comes through Firehose or OpenSearch Ingestion with a buffer in front so a cluster block becomes a backlog, not a loss. Mappings matter more than nodes: explicit mappings, no dynamic field explosion, keywords where nobody searches text, and no indexing of the raw message twice. Then the alarms: ClusterStatus, JVMMemoryPressure above 75%, FreeStorageSpace, ClusterIndexWritesBlocked, and the ingest backlog. If the team would rather not size at all and the volume is this large and steady, Serverless with a time-series collection is a defensible answer; at small volumes it is not, because of the OCU floor, and at that point I would ask whether CloudWatch Logs Insights and S3 with Athena do the job without a cluster.

A team wants DocumentDB because "the data is JSON". Argue.

JSON is a format, not a workload, so I ask what they do with it. If the access patterns are known and the documents are read and written by key, DynamoDB stores JSON as items, scales further, costs less, and has no instances. If the documents are queried in ad hoc ways across nested fields and the team thinks in SQL, Aurora PostgreSQL with jsonb and GIN indexes gives joins, transactions and reporting for free. DocumentDB earns its place in one case: the team has a MongoDB application and its drivers, aggregation pipelines and query habits, and wants Aurora-style operations, readers, PITR and global clusters without running MongoDB. Even then I would run the real query log against the compatibility list, because the API is MongoDB 5.0 and not every operator or index type is there, and I would compare with MongoDB Atlas on AWS if they need the latest features. What I would not accept is "we might need flexible schema later": every store here has that, and the cost of picking a document database for a key-value workload is paid every month in instance hours.

Redshift, Athena or Aurora for the analytics team?

It depends on three numbers: data size, query frequency and who is waiting. Under a hundred gigabytes with a handful of people, an Aurora read replica with the right indexes answers reporting queries without a second system, and that is where most companies should start. When the data is in S3 anyway and the queries are occasional, Athena: no cluster, pay per terabyte scanned, columnar Parquet and partitioning make that cheap, and nobody is on call for it. Redshift is for the warehouse pattern: terabytes to petabytes, the same analysts running many queries a day over curated tables, dashboards that expect sub-second responses from result caching and materialised views, and data arriving continuously through zero-ETL from Aurora and DynamoDB or through Glue. RA3 separates compute from managed storage so the cluster is sized for the queries, Serverless charges per RPU-second for a team that works office hours, Spectrum reaches the lake for the long tail, and data sharing lets other teams query without copies. The decision I give in interviews: lake first, Athena on it, and Redshift as the serving layer when the query load and latency expectations justify a cluster that someone tunes. Day 22 goes deeper.

Build a rate limiter for 100 requests per minute per API key, across 200 containers.

The counter must be shared and atomic, which is Redis or Valkey. The simple version is a fixed window: INCR on a key like rl:{apikey}:2026-10-11T14:05 and EXPIRE it on first use, or a Lua script or MULTI to do both; if the count exceeds 100, reject. One round trip, microseconds of engine time, and the hash tag keeps the key on one shard. Its flaw is the window edge: 100 at 14:05:59 and 100 at 14:06:00. A sliding window fixes it with a sorted set per key: ZADD the timestamp, ZREMRANGEBYSCORE older than a minute, ZCARD for the count, EXPIRE, in one script; more memory but exact. A token bucket, stored as a hash of tokens and last-refill time and updated by a script, gives bursts with a steady rate. Then the operational side. The limiter is in the hot path of every request, so the cache client has a short timeout and a decision for when the cache is down: fail open and log, since a rate limiter outage should not be an API outage. The keys expire on their own, so memory is bounded by the number of active API keys. The hot key risk is one abusive key hammering one shard, which at a few thousand operations a second is fine for Valkey; at hundreds of thousands I would count locally per container for a second and sync. And I would say why not DynamoDB: the atomic counter works but each check is a write unit and single-digit milliseconds, which at this rate is both slower and dearer than the cache.

Serverless ElastiCache or nodes?

Serverless removes the sizing: I pick an engine, it runs the shards, scales within about a minute as the data and the request rate grow, is Multi-AZ by default, and bills per GB-hour of data plus per ECPU, with a maximum I set. It wins for caches that are small, spiky, new, or owned by a team with no one to tune node types, and for development accounts where a node pair would idle. It loses on steady large caches: at a few hundred gigabytes the GB-hour price plus ECPUs costs more than reserved r7g nodes with replicas, and a flash crowd that goes from zero to ten times in seconds throttles briefly because scaling is smooth, not instant. Nodes give control: the node type, the shard count, the parameter group, a scheduled scale-up before a known peak, and reserved pricing. Serverless is cluster mode enabled underneath, so the client must be cluster-aware and the keys need hash tags for multi-key operations. My default is serverless for a new cache under about 50 GB and nodes with reserved pricing once the usage is steady and measured, in either case with a replica, a Multi-AZ setting, and the alarms from the diagram.
