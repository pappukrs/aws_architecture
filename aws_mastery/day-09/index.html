DynamoDB in depth

Yesterday's databases scale by a bigger instance. DynamoDB scales by cutting the table into partitions and spreading them over a fleet you never see. That one decision explains everything else on this page: why the partition key is the design, why one hot key throttles while the table is idle, why a filter expression does not make a Scan cheaper, why a global secondary index is eventually consistent and a local one is not, why a transaction costs double, and why the bill is either per request or per provisioned unit-hour. The centre of the page is the interview question: design the keys for "orders by customer" and "orders by status" in one table. Around it: partitions and replicas, item collections, single-table design, GSI against LSI, on-demand against provisioned, hot partitions and adaptive capacity, conditional writes and transactions, Streams, TTL, DAX, global tables, backups and point-in-time recovery.

The diagram

The whole picture. The application signs every request and sends it to the regional endpoint, directly, through a gateway VPC endpoint from private subnets, or through a DAX cache cluster. Request routers authenticate it, hash the partition key, and send it to the partition that owns that key. A partition holds up to 10 GB and serves 3,000 read units and 1,000 write units a second; it is stored three times in three AZs with one leader that takes writes and strongly consistent reads. Items with the same partition key form an item collection, sorted by the sort key, and a Query reads one collection in that order. A global secondary index is a second table with its own partitions and keys, fed asynchronously, so it is eventually consistent; a local secondary index lives inside the partition and can be read strongly. Capacity is either per request or per provisioned unit, and in both modes the per-partition ceiling is what you hit first. Streams carry every change for 24 hours to Lambda or Kinesis. TTL, point-in-time recovery, backups and export live on the right; a global table replica and the metrics that matter are bottom left. Bottom right is the design to know by heart: one table that answers "orders by customer" and "orders by status" without a Scan and without a hot key.

Scan or Query: what one access pattern costs

Every read is billed by the bytes DynamoDB evaluates, rounded up to 4 KB, halved if eventually consistent. A Query evaluates one item collection; a Scan evaluates the table, and a filter expression is applied afterwards, so it changes what you get back and not what you pay. On-demand or provisioned: the bill

On-demand charges per request. Provisioned charges per unit-hour whether you use it or not; auto scaling tries to keep the provisioned level at about 70% of what you consume, but it reacts in minutes, so a spike needs a minimum that is already high enough, and a scheduled scale-up before a known peak. The answer is a utilisation: what fraction of the capacity you pay for is used. Shape the traffic, choose the minimum you would dare to run, and read the numbers.

How it works inside

What DynamoDB is

  • A regional key-value and document store run as a shared service: no instance, no connection, no VPC. Every operation is an HTTPS request signed with SigV4, authorised by IAM, answered in single-digit milliseconds at any table size, because every operation except Scan touches one partition by key.
  • A table holds items (up to 400 KB each, names included) made of attributes (string, number, binary, bool, null, list, map, sets). The only schema is the key: a partition key, or a partition key plus a sort key. Everything else varies per item.
  • The API is small: GetItem, PutItem, UpdateItem, DeleteItem, Query, Scan, the batch and transaction forms, and PartiQL on top of the same operations. There are no joins, no aggregates and no ad hoc queries; you design the table around the access patterns, not around the entities.
  • Two prices: per request (on-demand) or per provisioned unit-hour, plus storage. Compare RDS: there you buy an instance and the engine decides how to use it; here you buy throughput and the design decides whether you can use it.
  • Everything is encrypted at rest (AWS owned key by default, AWS managed or your own KMS key) and in transit. The SDK retries throttles and 5xx errors with backoff, so a sick table shows up first as latency, then as errors.

Partitions and replicas

  • The table is split into partitions by the hash of the partition key. Each partition holds up to 10 GB and serves at most 3,000 RCU and 1,000 WCU per second. Table size is unlimited because the partition count is.
  • Each partition is stored on three replicas in three AZs; one is the leader. A write goes to the leader and is acknowledged when two of three replicas have it, which is why a write is durable the moment it returns. An eventually consistent read is served by any replica, so it may miss a write from the last few hundred milliseconds; a strongly consistent read goes to the leader.
  • Partition count is the larger of what size needs (10 GB each) and what throughput needs (3,000 RCU and 1,000 WCU each). A table provisioned at 10,000 WCU has at least ten partitions; after a split, partitions do not merge back.
  • Request routers sit in front: they authenticate, consult partition metadata, and forward. Your SDK talks to a regional endpoint; the gateway VPC endpoint is a route-table entry for private subnets, not a network interface.
  • Throughput is per partition, not per table. Whatever you provision or whatever on-demand would allow, one partition key goes to one leader, and that leader does 1,000 writes a second. This is the fact behind every hot-partition story.

Keys and item collections

  • Partition key alone: a plain key-value store, one item per key, GetItem only. Partition key + sort key: items with the same partition key form an item collection, stored together and sorted by the sort key's bytes. The pair must be unique.
  • Query reads one item collection: partition key equal to a value, optionally a sort-key condition (=, <, between, begins_with), forwards or backwards, up to 1 MB per page. Sorting, ranges and "latest N" come from the sort key; there is no other way to sort.
  • Choose the partition key for distribution: many values, evenly accessed. Choose the sort key for the order and range you need: ISO timestamps sort chronologically, zero-padded numbers sort numerically, COUNTRY#CITY#STREET gives hierarchical begins_with, a KSUID or ULID gives time-ordered unique ids.
  • Generic key names (PK, SK) with typed prefixes in the values (CUSTOMER#42, ORDER#2026-10-03T14:05#B7) let several entity types share a table and an index without colliding. The prefix is the type.
  • Limits that bite: partition key value 2,048 bytes, sort key 1,024 bytes, and with an LSI every item collection is capped at 10 GB including the index.

Single-table design

  • Start from the access patterns, written down as a list: "orders for a customer, newest first", "open orders older than an hour", "an order and its line items in one read". Then choose keys so that each pattern is one Query or GetItem. Entities come last.
  • An aggregate shares a partition key: the order header has SK = ORDER#…, its lines SK = ORDER#…#LINE#1, so one Query returns the whole order. A customer's profile sits in the same collection as their orders.
  • Adjacency list for many-to-many: write the relationship as items on both sides (PK = CUSTOMER#42, SK = PRODUCT#7) and add a GSI that swaps PK and SK (an inverted index) for the reverse lookup.
  • Gains: one round trip per aggregate, one capacity setting, one stream, one backup, one set of alarms. Costs: the table is hard to read without the pattern list, every GSI is shared by every entity, and analytics needs an export. It is a tactic for a known workload, not a rule; separate tables when entities have different lifecycles, capacity modes, retention or owners.
  • Three rules of thumb: pre-join what you read together, denormalise what you read often, and never design for a query you have not listed; DynamoDB will not rescue an unplanned one, and that is the trade you made for the scaling.

GSI against LSI

  • A global secondary index is a second table DynamoDB maintains for you: its own partition and sort keys from any attributes, its own partitions, its own capacity in provisioned mode. It is fed from the base table's write asynchronously, usually within a second, so it is eventually consistent only; ConsistentRead on a GSI is an error.
  • GSIs are sparse: an item without the index key attribute is simply not in the index. Set GSI1PK only on open orders and the index is the list of open orders.
  • Projection decides what the index stores: KEYS_ONLY, INCLUDE named attributes, or ALL. A query that needs an attribute not projected cannot fetch it from a GSI; you read the base table afterwards. More projection costs storage and write units on every update of a projected attribute.
  • Up to 20 GSIs per table by default, created or deleted at any time; a backfill reads the whole table. In provisioned mode a GSI needs its own WCU and a throttled GSI throttles writes to the base table, the most common way a "harmless" index takes production down.
  • A local secondary index keeps the partition key and gives an alternative sort key. It lives inside the base partition, so it supports strongly consistent reads and shares the table's capacity; non-projected attributes are fetched from the base item on the fly. Up to 5, only at table creation, and it caps every item collection at 10 GB. Choose an LSI only when you need strong consistency on the alternative order; otherwise a GSI.

Capacity units and the two modes

  • One RCU is one strongly consistent read of up to 4 KB per second, or two eventually consistent reads, or half a transactional read. One WCU is one write of up to 1 KB per second, or half a transactional write. Writes round up per item: a 1.1 KB item costs 2 WCU; a 400 KB item costs 400. Query and Scan sum the items evaluated and round once.
  • Provisioned: you set RCU and WCU on the table and on each GSI. Auto scaling (Application Auto Scaling) changes them on a target utilisation, 70% by default: scale-out needs two consecutive minutes above target and takes minutes to apply, scale-in waits fifteen minutes below. Decreases are limited to 27 a day. Burst: up to 300 seconds of unused capacity is banked for spikes. Reserved capacity for one or three years takes 54% or 77% off the baseline.
  • On-demand: no settings; you pay per read and write request unit. A table serves up to twice its previous 30-minute peak at once and grows beyond that by adding partitions, during which some requests throttle. A new table starts at 4,000 WCU and 12,000 RCU. You can set a maximum to cap the bill and a warm throughput to pre-grow the partitions before a launch.
  • Per unit, on-demand costs about 3.5× the provisioned price, so provisioned wins whenever more than about 29% of what you pay for is used; at a 70% auto scaling target that is most steady workloads. On-demand wins when the traffic is spiky or unpredictable, so that the minimum you would need is most of the peak; when the table is small; and when nobody wants to own auto scaling. Switch between modes once per 24 hours.
  • Account and table quotas: 40,000 RCU and 40,000 WCU per table by default, 80,000 per account per Region for provisioned; raise them with a ticket before a launch, not during it.

Hot partitions and adaptive capacity

  • The table is provisioned for 10,000 WCU and consuming 800, and writes are throttled. That is a hot partition: the key the writes go to lives on one partition, and that partition's leader stops at 1,000 WCU.
  • Adaptive capacity is on by default and instant: a hot partition can use more than its even share of the table's provisioned capacity, up to the per-partition ceiling. Split for heat then divides a hot partition by key range over minutes. Neither helps when the heat is a single key or a single item, or when a timestamp sort key sends every new write to the tail of one collection.
  • Classic causes: a date or a status as the partition key; a tenant that is a quarter of the traffic; a counter item every request updates; a configuration item every request reads (3,000 RCU is the ceiling for reads of one item); a GSI whose key has five values.
  • Find it with CloudWatch Contributor Insights for DynamoDB (most accessed and most throttled keys), and the fact that ThrottledRequests rises while ConsumedWriteCapacityUnits is far below provisioned.
  • Fix it in the design: write sharding (append a suffix 0–N to the hot key, query all N in parallel and merge), calculated suffixes when the reader knows the shard, spread counters over many items, cache reads of hot items (DAX or in-process), and never make a low-cardinality attribute a key without a shard.

Consistency, conditional writes, transactions

  • Reads are eventually consistent by default; ConsistentRead=true gives strong consistency on tables and LSIs, at double the RCU, never on GSIs or through DAX. Writes are atomic per item: a PutItem replaces the item, an UpdateItem changes attributes in place with SET, REMOVE, ADD (atomic counters, set unions) and DELETE.
  • A ConditionExpression makes a write succeed only if the condition holds on the current item: attribute_not_exists(PK) for insert-if-absent, version = :v for optimistic locking, stock >= :n for a reservation. A failed condition costs one write unit and returns ConditionalCheckFailedException; ask for the item back with ReturnValuesOnConditionCheckFailure.
  • TransactWriteItems: up to 100 Put, Update, Delete and ConditionCheck actions across tables in one Region, all or nothing, 4 MB total, at twice the write units. TransactGetItems: up to 100 items read as one snapshot. A conflict with another transaction or a failed condition cancels the whole thing with the reason per item; a ClientRequestToken makes a retry within 10 minutes idempotent.
  • Batches are not transactions: BatchWriteItem (25 puts or deletes, 16 MB) and BatchGetItem (100 items, 16 MB) can succeed partially and return UnprocessedItems you must retry.
  • Retries are the trap: an ADD count :1 retried after a timeout increments twice. Make writes idempotent with a condition on a version or request id, or use a transaction with a token.

Streams and change data capture

  • DynamoDB Streams is an ordered change log of the table: every insert, update and delete appears exactly once, in order per partition key, kept for 24 hours. The view decides the payload: KEYS_ONLY, NEW_IMAGE, OLD_IMAGE or NEW_AND_OLD_IMAGES. Shards follow partitions and split with them.
  • Lambda consumes it through an event source mapping: reads are free; you set batch size and batching window, a filter so only the events you want invoke the function, bisect on error to isolate a poison record, a retry limit, an on-failure destination (SQS or SNS), a parallelisation factor up to 10 per shard, and tumbling windows for aggregates. A stuck batch shows as a rising IteratorAge.
  • Kinesis Data Streams for DynamoDB writes the same changes to a Kinesis stream: retention up to a year, many consumers, Firehose to S3; but order is not guaranteed and duplicates can occur, so consumers dedupe on the sequence number and ApproximateCreationDateTime.
  • Uses: materialised views and aggregates, search indexes in OpenSearch, replication to another store, audit trails, triggers ("order created → send email"). TTL deletes arrive in the stream with userIdentity.principalId = dynamodb.amazonaws.com, so a consumer can tell expiry from a user delete.
  • At most two consumers should read a shard directly (Lambda counts as one); fan out through Kinesis or EventBridge Pipes when more need it.

TTL, backups, recovery, export

  • TTL: name a numeric attribute holding an epoch-seconds time; items past it are deleted by a background process, typically within a few days, for free and visible in the stream. Expired items that are not yet gone still come back from reads, so filter on the attribute if it matters.
  • On-demand backups are full, instant, consume no capacity and cost $0.10 per GB-month until you delete them. Point-in-time recovery keeps a continuous backup for 35 days at $0.20 per GB-month and restores to any second. Either restore creates a new table in minutes to hours, scaling with size.
  • A restore brings the data and the GSIs. It does not bring auto scaling settings, TTL, Streams, PITR itself, tags, IAM policies, CloudWatch alarms or the table's name. Script the re-creation and rehearse it; the day you need it is not the day to discover this.
  • AWS Backup copies to another account and Region and locks the vault. Export to S3 from the PITR data, full or incremental, in DynamoDB JSON or Ion, uses no table capacity and is how analytics gets the data: Athena over the export, not a Scan. Import from S3 creates a new table from such files without consuming write units.
  • Deletion protection is a flag on the table; turn it on in production. A DeleteTable on a table with PITR keeps a final restorable snapshot for 35 days only if you create a backup first; it does not do that on its own.

DAX

  • DynamoDB Accelerator is a managed in-memory cache cluster in your VPC with the same API: change the client's endpoint, keep the code. Reads that hit the cache return in microseconds; a cluster serves millions of requests a second.
  • Two caches: the item cache for GetItem and BatchGetItem, keyed by primary key, 5-minute TTL by default; and the query cache for Query and Scan, keyed by the exact request parameters. Writes are write-through: DAX writes to DynamoDB, then updates the item cache; the query cache is not invalidated by writes and simply ages out.
  • Only eventually consistent reads are served from the cache; a strongly consistent read passes through to DynamoDB untouched, and transactions are not cached.
  • A cluster is one primary and up to ten read replicas across AZs; it is cold after a restart and its failover takes minutes. It costs per node-hour (about $0.04 for a dax.t3.small, $0.27 for a dax.r5.large).
  • Use it for read-heavy, read-mostly workloads with hot items, where it removes RCUs and hot-key throttling at once. Skip it for write-heavy tables, strongly consistent reads, or when an in-process cache with a short TTL already does the job.

Global tables

  • A global table is one table replicated to other Regions, every replica accepting writes. Replication runs through Streams, typically in under a second; the current version (2019.11.21) adds and removes Regions without downtime.
  • Conflicts are resolved last writer wins by timestamp. Transactions and conditional writes are evaluated against the local replica only, so two Regions can both "successfully" reserve the last unit of stock. Route writes for a key to one Region, or accept the window.
  • Each replica is a full table with its own capacity and storage; writes are billed as replicated write units (about 1.5× a plain write, per Region). Replicas must use the same mode, and provisioned replicas need auto scaling.
  • The newer multi-Region strong consistency option makes writes synchronous across three Regions (one may be a witness) at higher write latency, for the workloads that cannot tolerate the window.
  • What it gives you: active-active applications, and disaster recovery with an RPO of seconds and an RTO of a DNS change. What it does not: a cheap backup (it costs twice the table) or cross-Region atomicity.

Access control and security

  • There are no database users. IAM decides per API action and per table or index ARN; a policy on the table alone does not cover its GSIs (table/Orders/index/*).
  • Fine-grained access: the condition key dynamodb:LeadingKeys restricts a caller to items whose partition key equals their identity (a Cognito user id), and dynamodb:Attributes restricts which attributes they may read or write. This is how a mobile app talks to a table directly.
  • Resource-based policies on tables and streams allow cross-account access without assuming a role, like a bucket policy; the table owner can use them to block public access.
  • Encryption at rest is always on; a customer managed KMS key gives you the audit trail and the ability to revoke, at a KMS cost per request that the cache inside DynamoDB keeps small. In transit is TLS; the gateway VPC endpoint keeps traffic off NAT and its endpoint policy limits which tables the VPC may reach.
  • CloudTrail records the control plane always and the data plane (every GetItem) if you enable data events, which is expensive on a busy table. Table class Standard-IA is a cost setting, not a security one: 60% cheaper storage, 25% dearer requests.

Seeing inside

  • CloudWatch per table and per GSI: ConsumedReadCapacityUnits and ConsumedWriteCapacityUnits against the provisioned ones, ReadThrottleEvents, WriteThrottleEvents, ThrottledRequests by operation, SuccessfulRequestLatency (watch p99 per operation), SystemErrors (theirs), UserErrors (yours, account-wide), ConditionalCheckFailedRequests, TransactionConflict, ReturnedItemCount, TimeToLiveDeletedItemCount, ReplicationLatency for global tables, OnlineIndexPercentageProgress for a backfill.
  • Contributor Insights for DynamoDB: the most accessed and most throttled keys per table and index, the only way to see a hot key from outside.
  • On the consumer side, Lambda's IteratorAge is the stream's lag; an age that climbs while invocations fail is a poison record.
  • ReturnConsumedCapacity on any request returns the units it cost, per table and per index; put it in a debug log and you can price an access pattern before it ships. ScannedCount against Count on a Query or Scan shows what a filter threw away.
  • Alarms worth having: throttle events over zero, p99 latency, consumed over 80% of provisioned, IteratorAge, and a Budgets alarm on the table's cost for on-demand tables.

Interview questions

Design the keys for "orders by customer" and "orders by status" in one table.

I start from the two patterns and what each needs: a customer's orders, usually newest first, sometimes in a date range; and the orders in a given status, usually open ones, oldest first so they get worked. The first pattern decides the table key. Partition key CUSTOMER#<id>: millions of values, evenly spread, and everything about one customer lands in one item collection. Sort key ORDER#<ISO timestamp>#<orderId>: it sorts chronologically, begins_with(SK, "ORDER#") selects only orders, a between on the timestamp gives a date range, and ScanIndexForward=false gives newest first. The customer's profile goes in the same collection with SK = PROFILE, so one Query returns the customer and their orders. The second pattern cannot be served by the table key, so it is a GSI, and the naive version is the trap: GSI1PK = STATUS#OPEN is a key with a handful of values, every new order is OPEN, so every insert hits one GSI partition and the index throttles at a thousand writes a second, which throttles the table. So I shard it: GSI1PK = STATUS#OPEN#<0–9> with the suffix computed from the order id, GSI1SK = timestamp. Reading open orders is ten parallel Queries merged by time; the fan-out is cheap and the write path is spread ten ways. Two refinements. The index is sparse: when an order reaches a terminal state I remove GSI1PK rather than set it to DELIVERED, so the index holds only live orders and stays small. And if the reader needs read-after-write on status, I say so: the GSI is eventually consistent, so the screen that just changed a status reads the order back from the base table by its key. I would also state the thing I am not doing: no Scan with a filter, because it reads the whole table and the filter runs after the read; and no status as the table's partition key, because a hot key is a hot key in any capacity mode.

Explain partitions. Why does a table provisioned for 10,000 WCU throttle at 800?

DynamoDB stores a table as partitions, each a chunk of about 10 GB that serves at most 3,000 read units and 1,000 write units a second, replicated three times across three AZs with one leader that takes the writes. The partition key is hashed to pick the partition, so every write to one key goes to one leader, and that leader does 1,000 writes a second and not one more. The table's 10,000 WCU is spread over at least ten partitions; it is a sum, not a pool. So if 800 writes a second all carry the same partition key, a date, a status, a big tenant, a counter, they go to one partition that is at its ceiling while the other nine idle. On-demand does not change this, because the ceiling is physical, per partition. Adaptive capacity helps when the heat is spread across keys that happen to share a partition: the hot partition borrows from the table's unused capacity instantly, and over minutes DynamoDB splits it by key range. It cannot help when the heat is a single key, and it cannot help when a timestamp sort key sends every new write to the tail of one collection, because no range split separates the newest writes from each other. I find it with Contributor Insights, which lists the most-accessed and most-throttled keys, and with the metric pair: throttle events up while consumed capacity is far below provisioned. I fix it in the key design: write sharding with a suffix, counters spread over many items, caching for a hot read item, and never a low-cardinality attribute as a partition key.

GSI or LSI: when would you choose each, and what are the traps?

A GSI is a second table that DynamoDB maintains for me: any attributes as its keys, its own partitions, its own capacity in provisioned mode, fed asynchronously from the base table's writes, so it is eventually consistent only, and I can add or drop it at any time at the cost of a backfill. An LSI keeps the table's partition key and gives a different sort key, lives inside the base partition, shares the table's capacity, and because it is in the same partition it can be read strongly consistently. The LSI costs are heavy: five at most, only at table creation, and it caps every item collection in the table at 10 GB, index included, which is a limit that arrives in production years later as a write failure on one key. So I choose an LSI only when I need a second sort order within a partition key and the read must see the latest write; everything else is a GSI, which is most things: inverted lookups, status lists, time ranges across keys. The GSI traps: it is sparse, so an item without the key attribute or with the wrong type is silently absent, which is a feature when I want it and a bug when I did not; its projection decides what a query can return, and anything not projected means a second read of the base table; a projection of ALL doubles storage and the write cost of every update; and in provisioned mode a GSI that is under-provisioned or has a hot key throttles writes to the base table, which is the way an innocent index takes down a service. I provision GSIs like the table, shard their keys when the cardinality is low, and I keep the number small because every entity in a single-table design shares the same twenty.

On-demand or provisioned: how do you decide, and what is the maths?

On-demand charges per request: after the 2024 price cut, $0.625 per million writes and $0.125 per million reads. Provisioned charges per unit-hour whether used or not: $0.00065 per WCU-hour, which is 3,600 writes, so $0.18 per million at full utilisation. That makes on-demand about three and a half times dearer per unit, so the break-even is utilisation: provisioned wins whenever more than about 29% of what I pay for is actually used. Auto scaling targets 70% and tracks a business-hours curve well, so for a steady or daily-shaped load provisioned is two to three times cheaper, and reserved capacity on the baseline takes another half off. On-demand wins when the traffic is spiky or unpredictable, because then the minimum I would have to run to avoid throttling for minutes at each spike is most of the peak and the utilisation collapses; when the table is small enough that the difference is pocket money; and for anything new, where I do not yet know the shape. The other half of the decision is operational. On-demand has no settings to get wrong, no scaling lag, and it is what I start every new table on. Its two limits are that it serves at most twice the previous half-hour's peak instantly, so a flash crowd beyond that throttles for minutes unless I set warm throughput beforehand, and that per-request pricing can run away on a bad access pattern, so I set the on-demand maximum and a budget alarm. Provisioned has the scaling lag, needs the GSIs sized too, and needs someone to own the auto scaling policy, but it is predictable and cheaper when the load is. Switching is once a day, so I change mode on a calm day, not during an incident. In interviews I give the one-line version: start on-demand, measure for a month with Cost Explorer, and move the flat tables to provisioned with reserved capacity.

How does DynamoDB replicate a write, and where exactly is a strongly consistent read not available?

A write arrives at a request router, which hashes the partition key and sends it to the leader replica of that partition. The leader writes it and forwards it to the two other replicas in the other two AZs; once one of them acknowledges, two of three have it, the leader returns success. The write is durable across two AZs at that moment; the third replica catches up within milliseconds. A strongly consistent read goes to the leader and therefore sees every acknowledged write; an eventually consistent read goes to any of the three, and if it lands on the one still catching up, it sees the previous version, which is why the documented staleness is "usually within a second" and in practice milliseconds. Strong reads cost twice the units because the leader is one node and the other two share the eventual reads. Where strong is not available: on a global secondary index, because the index is updated asynchronously after the base write, through a separate propagation path, so there is no leader that has promised anything; through DAX, because the cache serves what it has and a request for a strongly consistent read bypasses the cache altogether; and across Regions in a global table, where replication is asynchronous and last writer wins, unless the table uses the strongly consistent multi-Region option, which makes writes wait for other Regions. On an LSI strong reads work, because the index lives in the same partition as the item. So the design rule: any read that must see its own write goes to the base table or an LSI with ConsistentRead, and the GSIs serve the lists where a second of lag is fine.

Implement "reserve one unit of stock and create the order" so that it survives retries and concurrency.

Two items must change together: the stock item's count must go down only if it is positive, and the order item must appear exactly once. A read-then-write is wrong because two buyers read "one left" at the same moment. So it is a TransactWriteItems with two actions: an Update on PRODUCT#sku with SET available = available - :one and the condition available >= :one, and a Put of the order with the condition attribute_not_exists(PK). The transaction is all or nothing; if either condition fails I get a TransactionCanceledException with a reason per action, so I can tell the user "sold out" or detect a duplicate. For retries, the order id is generated by the client before the first attempt, so a retry sends the same item, and I pass that id as the ClientRequestToken: within ten minutes DynamoDB returns the original result for the same token without applying anything again, and if the token has expired, the attribute_not_exists condition catches the duplicate. For concurrency, two transactions touching the stock item conflict; one wins, the other is cancelled with a TransactionConflict reason and the SDK retries it, and then its condition decides. It costs four write units instead of two, which is the price of not selling the same unit twice. What I would not do: an atomic counter with ADD -1 and no condition, because a retried timeout decrements twice and the count goes negative; or two separate writes with a compensating delete, which leaves a window where the order exists and the stock does not. And I would say what the transaction cannot do: it is one Region, and in a global table the other Region evaluates its own copy, so a sellable inventory lives in one home Region.

When is single-table design the right call, and when is it not?

Single-table design means storing several entity types in one table with generic keys and prefixed values, laid out so that each access pattern is one Query. It is right when the access patterns are known and few, when some of them read an aggregate, an order with its lines, a customer with their orders, that would otherwise be several round trips, and when the operational wins matter: one capacity setting, one stream, one backup, one set of alarms, and in provisioned mode one pool of capacity shared across entities, which is cheaper than many under-used tables. It also makes Streams-based materialised views simple, since every change is in one stream. It is wrong when the patterns are not known, because every unplanned query becomes a Scan or a new GSI across every entity; when the entities have different lifecycles, retention or capacity modes, say a hot session table and a cold archive, which is simpler as two tables; when different teams own the entities, because a shared table is a shared schema with no enforcement; and when the twenty GSIs are a constraint, because every entity's indexes come out of the same twenty. The honest cost is readability: a single-table layout is unreadable without the access-pattern list, so the list is part of the code, in the repository, with a test per pattern that asserts the Query and the consumed capacity. My rule: design single-table for a bounded service whose patterns I can enumerate on one page, separate tables when the page gets a second sheet, and in both cases keep analytics out of it with an export to S3.

Build a materialised view from Streams. What are the guarantees and what goes wrong?

The stream gives me every change to the table, exactly once, in order per partition key, kept for 24 hours, with the old and new image if I ask for them. A Lambda event source mapping polls the shards, batches records, and invokes the function; the view is a second table or an OpenSearch index that the function updates. The guarantees are narrower than they sound. Order is per key, not across keys, so a view that sums across customers sees updates in any interleaving. Exactly once is for the stream, not for the function: Lambda retries a failed batch, so my function sees records more than once and must be idempotent, which means the view update is a conditional write on a version or on the record's sequence number. And 24 hours is the deadline: a consumer down for a day loses data, so I alarm on IteratorAge with a threshold of minutes. What goes wrong: a poison record that fails the function forever, which without bisect and a retry limit blocks the shard until the records expire; I set BisectBatchOnFunctionError, a maximum retry count, and an on-failure destination to SQS so the bad record is parked and the shard moves on. A hot partition on the source means one shard carries most of the traffic, and the parallelisation factor up to ten per shard is the only lever. A TTL expiry looks like a delete and would remove the row from the view, which is sometimes right and sometimes not; the userIdentity principal tells them apart. For more than two consumers, or for more than a day of retention, I switch the source to Kinesis Data Streams for DynamoDB, and then I lose the ordering and the exactly-once, and dedupe on the sequence number. Rebuilding the view from scratch is not a stream job at all: it is an export to S3 and a batch load, because the stream only has yesterday.

Finance asks why DynamoDB cost $4,000 last month for a table with 50 GB. Where do you look?

Fifty gigabytes is $12 of storage, so the money is in requests, and the first stop is Cost Explorer grouped by usage type: read request units, write request units, or provisioned hours, and by resource if cost allocation tags are on. If it is reads, I compare consumed read units with ReturnedItemCount in CloudWatch: a large read with a small return is a Scan, and a Scan with a filter on a 50 GB table costs about six thousand read units each time, eventually consistent, so a dashboard that refreshes every minute or a nightly job that runs it per tenant explains the figure on its own. The fix is a Query on a key or a GSI, or, for anything analytical, an export to S3 and Athena, which consumes nothing from the table. If it is writes, I look at item size, because a 3 KB item costs three units per write; at the GSIs, because each one with a full projection doubles every write; at transactions, which double again; and at the pattern that updates the same item on every request, a counter or a last-seen timestamp, which is pure write units with no information. If the table is provisioned, I check utilisation: a table provisioned at 5,000 WCU and consuming 300 is $2,400 a month of nothing, and the fix is auto scaling with a sane minimum, or on-demand. If it is global tables, replicated writes are 1.5× per extra Region and the replica's storage is counted again. I would also look for the things people forget: PITR at $0.20 per GB-month is $10 here, old on-demand backups kept forever, and a DAX cluster nobody uses. Then I put ReturnConsumedCapacity into the debug logging of the service, so the next pattern is priced before it ships.

Design the DR and the multi-Region story for a DynamoDB-backed service.

Inside a Region, DynamoDB is already three AZs with synchronous replication, so the single-Region DR question is about mistakes, not hardware: a bad deploy that corrupts items, a script that deletes a table. PITR on every production table gives me any second in the last 35 days; deletion protection stops the accidental DeleteTable; AWS Backup copies to a vault in another account with a lock, for the case where the account itself is compromised. The restore creates a new table and brings data and GSIs but not TTL, Streams, auto scaling, tags or IAM, so the runbook re-applies all of it and the application reads the table name from configuration. I rehearse it quarterly and write down the time, because a 2 TB restore is hours, not minutes. For a second Region, the question is what the application needs. If it is read-mostly DR with a few minutes of RPO, a global table replica gives sub-second replication at the cost of a second table's worth of money, and failover is Route 53 or ARC moving traffic; the application in the other Region is already running against its local replica. If it is active-active, both Regions write their local replica and I design for the semantics: last writer wins, conditional writes evaluated locally, transactions local, so anything with an invariant, inventory, balances, uniqueness, has a home Region per key and the other Region forwards those writes; the rest, sessions, profiles, carts, is fine either way. If an invariant must hold everywhere and the write latency is acceptable, the strongly consistent multi-Region option does it with three Regions. What I avoid is the half-measure of a cross-Region backup copy as the only DR, because restoring it is hours of RTO and up to a day of RPO, which is fine for a data warehouse and not for an order system.

Latency p99 for GetItem went from 4 ms to 60 ms on an on-demand table. Walk through it.

GetItem on a healthy table is single-digit milliseconds, so sixty is not the storage path; something is retrying or queuing. First the throttle metrics: ReadThrottleEvents and ThrottledRequests for GetItem, because the SDK retries a throttled request with exponential backoff and the caller sees the sum of the attempts as latency long before any error. On-demand does not exempt me from the per-partition ceiling of 3,000 read units, so a hot item, the config row that every request reads, throttles at a few thousand reads a second on one key; Contributor Insights shows it in a minute. Second, if traffic jumped past twice the previous peak, the table is adding partitions and throttling meanwhile; the fix for next time is warm throughput. Third, the client side: a Lambda in a VPC without a gateway endpoint goes through NAT, and a NAT under load adds milliseconds and then errors; a new deploy that creates a client per request pays TLS and credential resolution on every call; a JVM at the start of its life pays JIT. Fourth, the AWS side: SystemErrors above zero and a Health Dashboard event. Fifth, strongly consistent reads landing on one leader: if someone flipped ConsistentRead on, the reads that used to spread over three replicas now go to one, and cost double. I would order my checks by the metric that needs no guessing: throttles first, Contributor Insights second, then the client. The fix depends on the cause, but the hot-item case is by far the most common and the answer is a cache: in process for a few seconds, or DAX if there are many hot items, or copying the item under N keys.

A team wants a table per tenant for a thousand tenants. Talk them out of it, or not.

I would ask what they want from it, because the usual answers have better solutions. Isolation: IAM with dynamodb:LeadingKeys on a tenant-prefixed partition key limits a caller to its own items per request, which is stronger than the table boundary because it applies to the data plane. Per-tenant capacity and cost: on-demand bills per request, and cost allocation needs tagging of requests, not tables; one table with tenant in the key and a metrics dimension does the accounting. Per-tenant deletion: a Query by the tenant prefix and a batch delete, or a TTL set on every item of the tenant on offboarding. The costs of a thousand tables are concrete: the Region quota is 2,500 tables; every GSI, alarm, backup policy, TTL setting and stream mapping is per table, so onboarding is a deployment and drift is guaranteed; provisioned mode would need a thousand auto scaling policies and a thousand minimums, which is the most expensive way to buy capacity, and on-demand per table starts cold, so every small tenant throttles at its first spike; and a change to the key design is a thousand migrations. Where a separate table is right: a tenant whose traffic is a large fraction of the total, so that its hot keys are isolated and its capacity reserved; a tenant with contractual data residency or a dedicated KMS key; or a tier with a different retention or backup policy. So the design I would propose is a shared table with tenant-prefixed keys and IAM conditions for the long tail, and a dedicated table for the few that need it, with the application choosing the table from the tenant's configuration so that moving a tenant is a data copy, not a code change.
