Day 4 of 30 · Week 1 — Identity, Networking, Compute, Storage

EC2 in Depth

For three days you built the place where an instance lives. Today you open the instance itself. What is the machine under it, and what does the name m7g.xlarge tell you? Where do its disks really sit, and which of them survive a stop? How does a process on it get credentials, and how does an attacker get the same ones? The centre of the page is one question about storage: the database is slow, so is it the volume, or the instance in front of the volume?

The diagram

Full picture: one instance and everything it depends on. The host runs the Nitro system: a thin hypervisor for CPU and memory, and separate cards for the network, local disks and EBS. The instance was launched from an AMI, which an Image Builder pipeline rebuilds on a schedule. Its EBS volumes are outside the host, in the same AZ, and their snapshots are in S3. The instance store is inside the host, so it stays behind when the instance moves. Inside the instance, the metadata service hands out the role's credentials and user data runs at first boot. The SSM Agent calls out to Systems Manager, so you need no inbound port. A placement group decides how close the hosts of several instances are.

Will the volume keep up?

A database asks its disk for a number of operations per second (IOPS), each of a certain size. Two things limit what it gets: the volume, and the instance in front of the volume. Who gets the role's credentials?

Every process on the instance can ask http://169.254.169.254 for the credentials of the instance role. So can an attacker who makes one of those processes send a request. Set the two metadata options, pick who is asking, and say what happens before you read the result.

The options are HttpTokens (optional or required) and HttpPutResponseHopLimit. The hop limit is the IP time-to-live of the reply that carries the token. Each network hop lowers it by one, and at zero the packet is dropped. A process on the instance itself is zero hops away. A container on a bridge network is one hop away.

How it works inside

Reading an instance type

  • m7g.xlarge is four facts: family m, generation 7, attribute g, size xlarge.
  • Families: M general purpose (4 GiB per vCPU). C compute (2 GiB per vCPU). R and X memory (8 GiB and more per vCPU). I and D local storage. G and P GPUs. T burstable.
  • Attributes: g Graviton, a AMD, i Intel. d has instance store disks. n has more network and EBS bandwidth. b has more EBS performance. z has a high clock speed.
  • Size: each step doubles vCPU and memory, and also raises the network and EBS limits. A small size of the right family can still be the wrong choice because of those limits.
  • Take the newest generation. It is usually both faster and cheaper than the one before.

Nitro

  • Old hosts ran a hypervisor that also emulated the network and the disks in software. That work used CPU that the customer had paid for.
  • Nitro moves that work to dedicated cards: one for VPC networking, one for EBS, one for local NVMe disks. The cards encrypt data in hardware.
  • The Nitro hypervisor that remains only divides CPU and memory. An instance gets almost all of the host's performance. A metal size has no hypervisor at all.
  • A security chip checks the firmware at boot. There is no login to the host, not even for AWS staff.
  • For you this means: EBS volumes and instance store disks appear as NVMe devices, the network uses the ENA driver, and an AMI must have both drivers.
  • Every type released since 2018 is on Nitro. The Xen types (M4, C4, T2) lack many newer features.

Graviton

  • Graviton is the Arm processor that AWS designs. A Graviton type costs about 20% less than the Intel type of the same size, and often does more work per vCPU.
  • On Graviton, one vCPU is one physical core. On Intel and most AMD types, one vCPU is one thread, half a core.
  • The architecture is arm64. You need an arm64 AMI, and arm64 builds of your software and container images.
  • Code in Java, Python, Node.js or Go usually moves without changes. Check native libraries, agents and anything you install as a binary.
  • Managed services hide the difference. RDS, ElastiCache, OpenSearch and Lambda on Graviton need a setting, not a rebuild.
  • For containers, build multi-architecture images so that both kinds of node can pull the same tag.

Burstable instances and CPU credits

  • A T instance has a baseline: a share of each vCPU that it may use all the time. For t3.micro it is 10%, for t3.large 30%.
  • Below the baseline it earns CPU credits. Above it, it spends them. One credit is one vCPU at 100% for one minute.
  • Standard mode: when the credits are gone, the CPU is held at the baseline. The instance looks healthy and is very slow.
  • Unlimited mode: it keeps bursting and you pay for the extra, per vCPU-hour. This is the default for T3 and T4g. A T instance that is busy all day in this mode costs more than an M instance.
  • T is right for workloads that are idle most of the time. For steady load, use M or C.

Placement groups

  • Without a placement group, AWS puts instances on any host with room in the AZ.
  • Cluster: hosts close together in one AZ. The lowest latency, and up to 10 Gbps for a single flow instead of 5. For HPC and tightly coupled systems. One rack or power failure can stop all of them.
  • Spread: each instance on a different rack. At most 7 running instances per AZ in one group. For a small set of nodes that must not fail together, such as a quorum.
  • Partition: you get up to 7 partitions per AZ. No two partitions share a rack. Each can hold many instances. The partition number is in the instance metadata, so Kafka or Cassandra can place replicas in different partitions.
  • A cluster group needs capacity that is next to each other. Launch all instances in one request, with one instance type. Adding one later often fails with InsufficientInstanceCapacity.

AMIs

  • An AMI is three things: one or more snapshots, a block device mapping that says which volumes to create from them, and launch permissions.
  • It also fixes the architecture, the boot mode and the virtualisation type. An x86 AMI does not start on Graviton.
  • An AMI belongs to one Region. Copy it to use it in another. You share it with accounts, with an organisation, or with everyone.
  • For an encrypted AMI, the other account also needs permission to use the KMS key. An AMI encrypted with the default aws/ebs key cannot be shared at all.
  • Deregistering an AMI does not delete its snapshots. You keep paying for them until you delete them.
  • Refer to an AMI through an SSM parameter, not a hard-coded ID. IDs differ per Region and change with every build.
  • The Allowed AMIs setting limits an account to images from owners you trust.

Image Builder: golden images

  • A recipe is a base image plus components: documents with build steps (install, harden) and test steps.
  • A pipeline starts a build instance, runs the components, makes the AMI, starts a test instance from it, and then distributes the AMI to other accounts and Regions.
  • Run the pipeline on a schedule, or when the base image has an update. New instances then start already patched.
  • Lifecycle policies deprecate and delete old images and their snapshots.
  • The trade-off against user data: a baked image starts in seconds and starts the same every time. A script at boot is easy to change, slow to start, and fails when a package repository is down. Bake what is slow and stable. Leave to boot time only what differs per environment.

The metadata service and IMDSv2

  • IMDS is a web server at the link-local address 169.254.169.254. It is reachable only from the instance. It returns the instance ID, the AZ, the user data, and temporary credentials for the instance role.
  • IMDSv1 answers any GET request. An application that can be made to fetch a URL (server-side request forgery) will fetch the credentials for an attacker.
  • IMDSv2 needs a session. First a PUT to /latest/api/token returns a token. Then every GET carries the token in a header.
  • Three things stop an attacker: most SSRF bugs cannot send a PUT or set a header. A PUT that carries X-Forwarded-For is refused. The reply with the token has a hop limit of 1, so it cannot leave the instance.
  • Set HttpTokens=required. Make it the default for the account, and deny launches without it with the condition key ec2:MetadataHttpTokens.
  • Before you enforce it, look at the CloudWatch metric MetadataNoToken. It counts IMDSv1 calls.

User data

  • User data is up to 16 KB of text that you give at launch. On Linux, cloud-init runs it as root, once, at the first boot.
  • It does not run again after a reboot or a stop and start. To change it you must stop the instance, and the change still does not run by itself.
  • The output is in /var/log/cloud-init-output.log. Read it first when an instance comes up without its software.
  • The instance reports running long before the script ends. A load balancer health check, not the instance state, tells you when it is ready.
  • User data is not secret. Every process on the instance can read it from IMDS, and anyone with ec2:DescribeInstanceAttribute can read it from the API. Fetch secrets at boot with the instance role.

EBS volume types

  • gp3: the default SSD. 3,000 IOPS and 125 MiB/s are included at any size. You buy more of each, separately from size, up to 80,000 IOPS and 2,000 MiB/s. Latency is a few milliseconds.
  • io2 Block Express: up to 256,000 IOPS and 4,000 MiB/s. Latency below one millisecond and steady. Durability of 99.999%, a hundred times better than gp3.
  • st1: hard disk. Priced for throughput, up to 500 MiB/s, for large sequential reads and writes. A random operation costs as much as a sequential megabyte. It cannot be a boot volume.
  • sc1: the cheapest hard disk, for data you rarely read.
  • gp2 and io1 are the older generation. gp2 ties IOPS to size (3 per GiB) and uses burst credits below 1,000 GiB. gp3 costs 20% less per GiB. Migrate; it is an online change.

EBS: how a volume behaves

  • A volume is network storage. Its data is replicated inside one AZ. It attaches to instances in that AZ only.
  • The instance has its own EBS limit for IOPS and throughput, set by its type and size. The workload gets the lower of the two limits. A fast volume on a small instance is wasted money.
  • Elastic Volumes: you raise the size, change the type, or change IOPS and throughput while the volume is in use. A volume can grow and cannot shrink. After a size change you still extend the partition and the file system.
  • A volume takes up to four such changes in 24 hours.
  • Encryption uses a KMS key and happens on the Nitro card. Turn on “encryption by default” per Region. An existing unencrypted volume becomes encrypted through a snapshot copy.
  • Multi-Attach (io2 only) attaches one volume to up to 16 instances. It needs a cluster-aware file system. A normal file system will be corrupted.

Snapshots

  • A snapshot is a copy of a volume at one moment, stored in S3 by AWS. You do not see the bucket.
  • Snapshots are incremental: each stores only the blocks that changed since the one before. You can delete any of them. Blocks that a later snapshot still needs are kept.
  • A snapshot is crash-consistent: it is the disk as if the power was cut. For a database across several volumes, use a multi-volume snapshot, and flush or pause writes first.
  • A volume made from a snapshot is usable at once, and its blocks are fetched from S3 on first read. Until then it is slow. Fast snapshot restore, or a provisioned initialisation rate, removes the wait for a price.
  • The archive tier costs 75% less, holds a full copy, and takes 24 to 72 hours to restore.
  • Data Lifecycle Manager or AWS Backup takes and expires snapshots on a schedule. The Recycle Bin keeps deleted ones for a period you set.

Instance store

  • Instance store disks are NVMe SSDs inside the host. There is no network between the instance and the disk, so they give the most IOPS and the lowest latency in EC2.
  • Types with a d have them, and the I family is built around them. They are in the instance price.
  • The data survives a reboot. It is lost on stop, hibernate, terminate, and when the host or the disk fails.
  • You cannot snapshot them, detach them, or add them after launch.
  • Use them for data you can lose or rebuild: caches, temporary files, shuffle space, and databases that replicate between nodes (Cassandra, Kafka, ClickHouse).

Reboot, stop, start and recovery

  • Reboot: same host. Everything is kept, including the instance store and the public IP.
  • Stop and start: a new host. EBS volumes, private IPs and Elastic IPs follow. Memory, the instance store and an automatic public IPv4 address do not.
  • Hibernate: memory is written to the encrypted root volume and restored at start.
  • Three status checks run every minute. System: the host, its power and its network. Instance: the operating system answers. Attached EBS: the volumes are reachable.
  • When the system check fails, automatic recovery moves the instance to a healthy host with the same ID, addresses and volumes. It is on by default for most types.
  • AWS announces scheduled events before it retires a host. A stop and start on your own schedule moves the instance early.

Systems Manager: the agent and Session Manager

  • The SSM Agent is installed in the common AMIs. It opens an outbound HTTPS connection to Systems Manager and waits for work. Nothing listens on the instance.
  • An instance becomes a managed node when three things are true: the agent runs, the instance role has the AmazonSSMManagedInstanceCore permissions, and the instance can reach the ssm and ssmmessages endpoints through a NAT gateway or interface endpoints.
  • Session Manager gives a shell through that connection. There is no port 22, no key pair and no bastion host (architecture Day 25).
  • Access is an IAM permission, ssm:StartSession, which you can limit by tag. CloudTrail records who opened a session, and the session's input and output go to S3 or CloudWatch Logs.
  • It also forwards ports, for example to a private database through the instance.

Run Command and Patch Manager

  • Run Command runs a document, such as AWS-RunShellScript, on instances that you select by ID, tag or resource group.
  • Two rate controls make it safe on a fleet. Concurrency: how many instances at a time. Error threshold: after how many failures it stops.
  • Patch Manager starts from a patch baseline: which classifications and severities are approved, and how many days after release.
  • It runs as Scan, which only reports, or Install, which patches and can reboot. A maintenance window or a patch policy decides when.
  • The result is a compliance report per instance: missing, installed, failed.
  • Patching in place and replacing instances with a new AMI solve the same problem. An Auto Scaling group is better served by a new image. Servers that cannot be replaced need Patch Manager.

How it fails in production

SymptomCauseHow you find itFix
Database latency rises under load. The volume's metrics are far below its provisioned IOPS. The instance's EBS limit is reached, not the volume's. Often a small size whose 30-minute burst is used up. Instance metrics EBSIOBalance% and EBSByteBalance% fall to zero. InstanceEBSIOPSExceededCheck is 1. A larger size, or a family with more EBS performance. More volume IOPS will not help.
A gp2 volume is fast in the morning and slow after an hour of load. The burst credits are gone. A 100 GiB gp2 volume falls from 3,000 to 300 IOPS. BurstBalance at 0%. VolumeQueueLength rises at the same minute. Change the type to gp3 with modify-volume. No downtime, and it is cheaper.
A volume restored from a snapshot is very slow for the first hours. The restore test passed; the real recovery did not meet its time. Blocks are fetched from S3 on first read. A database that scans its files meets every block for the first time. High read latency on the new volume with low IOPS. It improves as the same data is read again. Fast snapshot restore on the snapshots you would recover from, or a provisioned initialisation rate, or read the whole device once before use.
After a stop and start, the data directory is empty. The data was on the instance store. The instance started on another host. lsblk -o NAME,MODEL: the device is “Amazon EC2 NVMe Instance Storage”, not “Amazon Elastic Block Store”. Durable data on EBS. Use the instance store only for data that another node or a backup can rebuild.
The volume was resized from 100 to 200 GiB. The file system is still full. modify-volume changes the block device. The partition and the file system keep their old size. lsblk shows a 200 GiB disk with a 100 GiB partition. df -h shows 100 GiB. growpart for the partition, then xfs_growfs or resize2fs. Both work online.
After IMDSv2 was enforced, applications in containers cannot find credentials. Processes on the host are fine. The hop limit is 1. The reply with the token is dropped on the extra hop into the container. The SDK reports that it cannot load credentials. describe-instances shows HttpPutResponseHopLimit: 1. A hop limit of 2. Better: a role for the task or the pod, so that containers do not use the node's role at all (Day 13).
The instance does not appear in Systems Manager. Session Manager cannot connect. One of three: no instance profile, or its role lacks the SSM permissions; no path to the endpoints from a private subnet; the agent is not running. aws ssm describe-instance-information does not list it. The reachability check of Session Manager names the missing part. Attach the role. Add a NAT gateway or the ssm, ssmmessages and ec2messages interface endpoints.
A new instance is running and passes its status checks, and the application is not installed. The user data script failed half-way: a package repository was unreachable, or a command returned an error. /var/log/cloud-init-output.log on the instance, or the console output through the API. Bake the software into the AMI. Keep user data short, and make the script stop on the first error so that the health check fails clearly.
A T3 instance has had a slow application for days. CPU is flat at 20%. Or the opposite: the bill of a small instance has doubled. Standard mode with no credits left: the CPU is held at the baseline. Or unlimited mode with steady load: surplus credits are charged. CPUCreditBalance at 0, or CPUSurplusCreditsCharged above 0. A larger T size, or an M or C type for steady load.
Scaling out a cluster placement group fails with InsufficientInstanceCapacity. There is no free host next to the existing ones. The error of the launch request, or the activity history of the Auto Scaling group. Launch the full number in one request. Stop and start all instances together to move the group. Reserve capacity for the group in advance.
Another account cannot launch from your shared AMI. The instance goes to terminated at once. The AMI's snapshot is encrypted, and the other account may not use the KMS key. The state reason of the instance: Client.InternalError. A denied KMS call in CloudTrail. A customer managed key, with a key policy that allows the other account, and a grant for its Auto Scaling service role (Day 18).

Hands-on lab

Goal: launch a Graviton instance with no key pair and no open port, with IMDSv2 required. Manage it only through Systems Manager. See the token rule of IMDS from inside, read the NVMe devices, change a volume while it is in use, snapshot it and scan for missing patches. About 40 minutes.

Cost: under $0.05 for an hour: a t4g.small, 18 GiB of gp3, one public IPv4 address and a small snapshot. The lab uses the default VPC, so that the agent reaches Systems Manager over the internet.

  1. Create a role that lets the SSM Agent register the instance, and an instance profile to carry it. 
    export AWS_DEFAULT_REGION=ap-south-1

cat > trust.json <<'EOF'
{ "Version": "2012-10-17", "Statement": [ { "Effect": "Allow",
  "Principal": { "Service": "ec2.amazonaws.com" }, "Action": "sts:AssumeRole" } ] }
EOF
aws iam create-role --role-name mastery-day04 --assume-role-policy-document file://trust.json
aws iam attach-role-policy --role-name mastery-day04 \
  --policy-arn arn:aws:iam::aws:policy/AmazonSSMManagedInstanceCore
aws iam create-instance-profile --instance-profile-name mastery-day04
aws iam add-role-to-instance-profile --instance-profile-name mastery-day04 --role-name mastery-day04
sleep 15   # a new instance profile takes a few seconds to be usable
  2. Launch the instance. The AMI comes from a public SSM parameter, so no ID is hard-coded. There is no key pair and no security group rule. The second volume is the one you will change. 
    ID=$(aws ec2 run-instances \
  --image-id resolve:ssm:/aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-arm64 \
  --instance-type t4g.small \
  --iam-instance-profile Name=mastery-day04 \
  --metadata-options HttpTokens=required,HttpPutResponseHopLimit=1,HttpEndpoint=enabled \
  --block-device-mappings 'DeviceName=/dev/sdf,Ebs={VolumeSize=10,VolumeType=gp3,DeleteOnTermination=true}' \
  --tag-specifications 'ResourceType=instance,Tags=[{Key=Name,Value=mastery-day04}]' \
  --query 'Instances[0].InstanceId' --output text)

aws ec2 wait instance-status-ok --instance-ids $ID
  3. Check that the instance is a managed node. Repeat until it prints Online. Then define a helper that runs one shell command through Run Command and prints its output. 
    aws ssm describe-instance-information --filters Key=InstanceIds,Values=$ID \

Interview questions

gp3 or io2 for a busy database, and how do you know when you have outgrown it?

I start on gp3. It gives 3,000 IOPS and 125 MiB/s at any size, I can provision up to 80,000 IOPS and 2,000 MiB/s separately from size, and every change is online. io2 Block Express costs about ten times as much for the same IOPS, so I need a reason: steady latency below a millisecond, more than 80,000 IOPS on one volume, or 99.999% durability for a database that has no replica. To know that I have outgrown gp3, I first check that the volume is the limit and not the instance: the instance's EBS limit and its EBSIOBalance%, then the volume's VolumeIOPSExceededCheck, queue length and latency. If the volume is the limit and is below the gp3 maximum, I raise the gp3 figures. If it is at the maximum, or the latency target cannot be met, I move to io2, and I also ask whether read replicas or a cache would remove the load instead.

What is the Nitro system, and why should an application engineer care?

Nitro moves networking, EBS and local storage from the hypervisor to dedicated hardware cards, and leaves a thin hypervisor that only divides CPU and memory. Three things follow for me. Performance is close to bare metal and does not vary with what the neighbours do with their disks. Volumes and instance store appear as NVMe devices and the network uses ENA, so my AMIs need those drivers and my scripts must not assume device names such as /dev/xvdf. And the security model is stronger: encryption of EBS and of traffic between instances happens on the cards, and nobody can log in to the host.

How does IMDSv2 stop the theft of credentials through SSRF?

With IMDSv1, any GET to 169.254.169.254 returns the role's credentials, so an application that fetches a URL for a user can be made to fetch them. IMDSv2 requires a token, which is obtained with a PUT request and then sent in a header. A typical SSRF bug controls only the URL of a GET; it cannot change the method or add a header. Two more rules cover proxies: a PUT with an X-Forwarded-For header is refused, and the reply with the token has an IP hop limit of 1, so it is dropped before it leaves the instance. I set HttpTokens=required as the account default, enforce it with the condition key ec2:MetadataHttpTokens, and watch MetadataNoToken before the change to find software that still uses version 1.

What changes when you stop and start an instance, compared with a reboot?

A reboot stays on the same host and keeps everything. A stop releases the host. At start the instance is placed on a new one, so memory is gone, instance store data is gone, and an automatic public IPv4 address is replaced. EBS volumes, the private addresses, Elastic IPs and the instance ID stay. That is also why stop and start fixes a failed system status check or a scheduled retirement, and a reboot does not. In an Auto Scaling group a stopped instance is seen as unhealthy and replaced, so there I terminate instead.

Snapshots are incremental. You delete the first one of ten. What happens to the other nine?

Nothing is lost. Each snapshot is a full description of the volume at its moment, and only the storage is shared. When I delete a snapshot, EBS removes only the blocks that no other snapshot refers to. Blocks that later snapshots still need stay, and I keep paying for them. So deleting old snapshots frees less than their listed size, and every remaining snapshot can still restore the whole volume alone.

You restore a 2 TB database volume from a snapshot. It is available in seconds and the database is very slow. Why, and what do you do?

The volume is created empty and its blocks are loaded from S3 in the background and on first access. Every block the database reads for the first time waits for that fetch, so the first pass over the data is slow. For a planned restore I read the whole device once before I use it. For recovery where time matters, I enable fast snapshot restore on the newest snapshots in the AZs I would restore into, which gives full performance from the start for an hourly charge, or I set a provisioned initialisation rate on the new volume. I also measure this in a restore test, because it decides the real recovery time.

When do you choose a cluster, a spread or a partition placement group?

Cluster when the nodes talk to each other all the time and latency decides the result, as in HPC. I accept that they are in one AZ and can fail together, and I launch them in one request because capacity next to existing hosts may not be free later. Spread for a handful of instances that must not share a rack, such as three quorum members; the limit is seven per AZ. Partition for large replicated systems: up to seven partitions per AZ, no rack shared between partitions, and the software reads its partition from the metadata to place replicas apart. For an ordinary stateless fleet I use none and spread over AZs.

Golden AMI or user data: how do you prepare instances?

Both, with a clear line. Everything slow and stable goes into the image: the operating system patches, agents, the runtime, and often the application itself. Image Builder rebuilds it on a schedule, tests it and distributes it. User data stays short and does only what differs per environment, such as reading configuration and starting the service. A baked image starts in seconds, starts the same way every time, and does not depend on a package repository during a scale-out. The cost is a pipeline, and a new image for every change. I never put secrets in either one; the instance fetches them with its role.

Why Session Manager instead of SSH through a bastion host?

Session Manager needs no inbound port, no key pairs and no bastion to patch. The agent calls out over HTTPS, so the instance can sit in a private subnet with a security group that allows nothing in. Access is an IAM decision, by tag if I want, with MFA and short-lived credentials, and it ends when the person leaves the identity provider. Every session start is in CloudTrail and the full session can be logged to S3 or CloudWatch Logs. With SSH I would have to build key rotation, host access lists and command logging myself. The requirements are the agent, an instance role and a path to the Systems Manager endpoints.

You are asked to move a fleet from Intel to Graviton to save money. What do you check?

The software first: an arm64 build of every binary, native library, agent and container image, and an arm64 AMI. Interpreted and JVM code usually runs unchanged; the surprises are compiled dependencies and vendor agents. Then performance, with a load test on the real workload, remembering that a Graviton vCPU is a full core and an Intel vCPU is a thread. Then the rollout: multi-architecture images, a second node group or a mixed-instances Auto Scaling group, a canary share of traffic, and a way back. I also check commitments: Compute Savings Plans cover both architectures, and Reserved Instances for the old type do not. Managed services such as RDS and ElastiCache are the easy first step, because the change there is only the instance class.

How do you patch 500 instances without causing an outage?

Where instances are in Auto Scaling groups, I do not patch them: I build a new AMI and replace them with an instance refresh. For the rest I use Patch Manager. A patch baseline approves patches by severity after a number of days, with a shorter delay in dev than in prod, so that dev finds the bad patch first. Maintenance windows per environment run the install, targeted by tag, with a concurrency of a small percentage and an error threshold that stops the run. Instances behind a load balancer are patched one AZ or one group at a time. A scan runs daily and the compliance report shows what is still missing.
