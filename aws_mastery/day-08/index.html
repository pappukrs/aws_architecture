RDS and Aurora in depth

Week 2 opens the data tier. Every stateless fleet from Week 1 ends in a database, and the database is where an outage stops being an inconvenience and starts being data loss. RDS gives you an engine on an instance with an EBS volume, a standby in another AZ, replicas, backups and a maintenance window. Aurora takes the same engines and replaces the disk with a distributed storage service that changes what replication, failover and recovery mean. The centre of the page is one event: the primary dies at 02:00. What happens, second by second, who notices, and how long until your application writes again? Around it: how the storage layers work, RDS Proxy, Serverless v2, Global Database, backups and point-in-time restore, parameter groups, Performance Insights, blue/green deployments and DMS.

The diagram

The whole picture. The application tier connects over a security group to a database that lives in a DB subnet group spanning three AZs. On RDS the database is an engine on an instance with its own EBS volume; Multi-AZ adds a synchronous standby that is not readable, read replicas add asynchronous copies that are, and the newer Multi-AZ cluster gives one writer and two readable standbys with semi-synchronous commits. Aurora keeps the engine but replaces the volume with a shared storage service that holds six copies across three AZs and does its own recovery, so replicas lag by milliseconds and failover needs no crash recovery. RDS Proxy pools connections in front of either. To the right are the operations that happen around a database: backups and point-in-time restore, Global Database for another Region, blue/green deployments for version changes, DMS for migrations, and the metrics, Performance Insights and events that tell you what the database is doing. Below is the one sequence to know by heart: what happens, second by second, when the primary dies.

How it works inside

What RDS is

  • A database engine (MySQL, PostgreSQL, MariaDB, Oracle, SQL Server, Db2) on an EC2 instance you cannot log in to, with an EBS volume, managed by an agent that patches, backs up, monitors and fails over.
  • You get a DNS endpoint, a port, a master user, and the engine's own SQL. You do not get the OS, SUPER / superuser, or the file system. RDS Custom (Oracle, SQL Server) gives OS access for software that needs it.
  • The instance lives in a DB subnet group (subnets in at least two AZs) with a security group; a public address is possible and almost always wrong.
  • Configuration is a parameter group (engine settings) and, for Oracle and SQL Server, an option group (TDE, S3 integration, native backup).
  • Instance classes: t (burstable, credits), m (general), r and x (memory), with Graviton (g) variants cheaper by about 20%. Scaling up is a modify with a restart; Multi-AZ makes it a failover instead.
  • Versions: minor upgrades can be automatic in the maintenance window; major upgrades are yours to run. Versions past end of life move to Extended Support and cost extra per vCPU-hour.

Storage and IOPS on RDS

  • gp3: $0.115 per GB-month with 3,000 IOPS and 125 MB/s included; from 400 GB (MySQL, PostgreSQL, MariaDB) the baseline is 12,000 IOPS and 500 MB/s; you can provision up to 64,000 IOPS and 4,000 MB/s on top. The default for almost everything.
  • io1 / io2: provisioned IOPS up to 256,000 with io2 Block Express; for the few databases that need sustained tens of thousands of IOPS at sub-millisecond latency.
  • gp2 (legacy): 3 IOPS per GB with bursts to 3,000 from a credit bucket. A 20 GB gp2 volume has 100 baseline IOPS; when BurstBalance hits zero the database crawls. Migrate to gp3.
  • Storage autoscaling: set a maximum; RDS grows the volume when free space is under 10% for five minutes. Storage only ever grows; to shrink, restore into a smaller instance via dump or DMS. After any storage change, six hours of cooldown before the next.
  • Max volume: 64 TiB (MySQL, PostgreSQL, MariaDB, Oracle), 16 TiB (SQL Server).
  • Watch DiskQueueDepth, ReadLatency/WriteLatency and the IOPS metrics together: high queue depth with IOPS flat at the limit means the volume, not the engine, is the bottleneck.

Multi-AZ instance deployment

  • A standby instance in another AZ with its own EBS volume. Every write is replicated synchronously at block level before the commit returns, so the standby is byte-identical and no committed data is lost on failover.
  • The standby is not readable and not a replica in the engine's sense; it is a cold copy that becomes the primary. You pay for two instances and two volumes.
  • Failover triggers: AZ outage, primary host failure, storage failure, instance class change, OS patching, and reboot with failover. Typical time 60–120 s; the engine on the standby must run crash recovery first.
  • Failover is a DNS change: the endpoint's CNAME moves to the standby's IP. Clients must re-resolve; a pool holding the old IP fails until it does.
  • Backups and snapshots are taken from the standby, so there is no I/O pause on the primary.
  • Synchronous replication adds write latency, usually 1–3 ms per commit; chatty transactions feel it.

Multi-AZ DB cluster and read replicas

  • Multi-AZ DB cluster (MySQL 8.0.28+, PostgreSQL 13.4+): one writer and two readable standbys in three AZs on instances with local NVMe. Replication is semi-synchronous: a commit waits for one of the two to acknowledge, so a failover loses nothing. Failover typically under 35 s, a reader endpoint, and up to 2× the write throughput of a Multi-AZ instance.
  • Read replicas: asynchronous copies fed by the engine's own replication (binlog, WAL). Up to 15 per source, in the same or another Region, each with its own endpoint and its own parameter group. A replica can be promoted to a standalone instance; that is the manual cross-Region DR for RDS.
  • A replica is as far behind as ReplicaLag says. Lag grows with large transactions, tables without primary keys (row-based replication scans), and a replica smaller than its source. MySQL: raise replica_parallel_workers.
  • Replicas serve eventually consistent reads. "Read your own writes" after a write must go to the primary.
  • Each replica is a full instance on the bill. A replica of a Multi-AZ instance can itself be Multi-AZ.
  • Cross-Region replica traffic is charged as inter-Region transfer; the replica's data is encrypted with a key in its own Region.

Aurora's storage layer

  • The volume is a service, not a disk: data is split into 10 GB segments, each stored as a protection group of six copies across three AZs (two per AZ). A write needs 4 of 6 acknowledgements, a read 3 of 6.
  • That quorum survives the loss of an entire AZ without losing write availability, and of an AZ plus one more copy without losing data. Lost segments are repaired from peers in the background.
  • The instance sends only redo log records to storage; storage applies them to pages itself. No data page writes, no double-write buffer, no checkpoints from the engine: about 1/8 of the I/O of MySQL on EBS for the same work.
  • Crash recovery is not a replay at startup: storage already holds the log and materialises pages on demand, in parallel, so a new writer opens in seconds no matter how much was in flight.
  • The volume grows in 10 GB steps to 128 TiB (256 TiB on recent versions) and you pay for what is used; it shrinks when data is dropped.
  • Because all instances share the volume, a replica is never behind on disk; the 10–20 ms "lag" is the time to invalidate its buffer cache.

Aurora instances, endpoints and failover

  • One writer and up to 15 Aurora replicas on the same volume, placed in different AZs by you. Any replica can become the writer; the promotion tier (0–15, lowest wins, then the largest) chooses which.
  • Endpoints: cluster (always the writer), reader (DNS round-robin over the replicas), custom (a named subset, say the two big instances for reports), instance (one instance).
  • Failover with a replica: typically under 30 s. The cluster endpoint's CNAME flips (TTL 5 s); the new writer needs no crash recovery. Without a replica, Aurora creates a new instance, which takes up to about 10 minutes; a single-instance Aurora cluster is not highly available.
  • The new writer starts with a cold buffer cache unless cluster cache management (PostgreSQL) kept the chosen replica's cache warm.
  • Aurora Serverless v2: an instance class, db.serverless, that resizes between a minimum and maximum in ACUs (2 GiB RAM each, 0.5 ACU steps, 0 to 256) in place, without disconnecting, in seconds. Minimum 0 ACU pauses the instance after idle time and resumes on the first connection, which takes about 15 s. Mix serverless readers with a provisioned writer in one cluster.
  • Other relatives: Limitless Database (sharded PostgreSQL writes beyond one instance), Aurora DSQL (distributed, serverless, active-active across Regions, a subset of PostgreSQL), Data API (HTTP, no connection management, for Lambda).

Aurora Global Database

  • One primary Region and up to five secondary Regions, each with its own copy of the volume and up to 16 readers. Replication happens in the storage layer, not the engine: typically under a second of lag with no load on the writer.
  • Secondaries are read-only. Write forwarding lets an application in a secondary Region send writes to the primary through its local endpoint, with a chosen consistency level.
  • Switchover (planned): the Regions swap roles with zero data loss, used for DR drills and Region moves. Failover (unplanned): promote a secondary, accepting the last second or so of writes may be lost; the old primary is rebuilt as a secondary when it returns.
  • Set rds.global_db_rpo (PostgreSQL) to make the primary refuse writes when lag exceeds your RPO.
  • Secondary Regions pay for their instances, their storage copy, and the replicated write I/O. On a Standard cluster that I/O is a separate line on the bill.
  • Without Global Database, cross-Region DR on Aurora is a cross-Region replica (MySQL, binlog-based, minutes of lag) or copied snapshots.

RDS Proxy

  • A managed proxy in your VPC subnets (at least two AZs) that holds a pool of database connections and shares them among many client connections: multiplexing. Hundreds of Lambda environments can map to a few dozen database connections.
  • It authenticates clients itself (password or IAM) and fetches the database credentials from Secrets Manager, so the application never holds the password.
  • On failover the proxy keeps client connections open, watches the cluster directly and reconnects to the new writer without waiting for DNS: AWS quotes up to 66% faster client-visible recovery on Aurora. In-flight transactions still fail.
  • Pinning: anything that changes session state, such as SET variables, prepared statements in some drivers, temporary tables, locks or advisory locks, binds the client to one database connection for the rest of the session and the multiplexing benefit disappears. The DatabaseConnectionsCurrentlySessionPinned metric tells you.
  • Tuning: MaxConnectionsPercent (share of max_connections the proxy may use), MaxIdleConnectionsPercent, ConnectionBorrowTimeout (how long a client waits for a free connection, default 120 s), idle client timeout.
  • Costs per vCPU-hour of the instances behind it, minimum two vCPUs. Supports MySQL, PostgreSQL, MariaDB and SQL Server on RDS and Aurora, with a read-only endpoint for Aurora readers.

Backups and point-in-time restore

  • Automated backups: a daily snapshot in the backup window plus transaction logs uploaded every five minutes. Together they allow point-in-time restore to any second between the oldest snapshot and LatestRestorableTime, which is up to five minutes ago. Retention 1–35 days (0 turns it off, and turns off PITR and replicas).
  • Snapshots are incremental, stored in S3 you cannot see, and free up to the size of the database. On a Single-AZ instance the daily snapshot briefly pauses I/O; Multi-AZ takes it from the standby.
  • Manual snapshots live until you delete them, survive deleting the instance, and can be copied across Regions and accounts. A snapshot encrypted with the AWS-managed key cannot be shared; copy it with a customer-managed key first.
  • Any restore creates a new instance with a new endpoint: you cannot restore "in place". The new instance uses the default parameter group and no option group unless you pass them. Its volume is lazy-loaded from S3, so the first hours are slow; warm it with a full scan.
  • Aurora: backup is continuous and incremental, PITR to the second within retention, no performance impact. Backtrack (MySQL) rewinds the cluster in place up to 72 hours without a restore. Clone creates a copy-on-write cluster in minutes for testing against production data.
  • Cross-Region automated backup replication copies snapshots and logs to another Region for PITR there. AWS Backup adds vault lock and one policy across services. Snapshots can be exported to S3 as Parquet for Athena.
  • A backup you have never restored is a hope. Restore one a quarter and time it; that number is your RTO.

Parameter groups and maintenance

  • The default parameter group cannot be edited. Create one per engine family and attach it; the attach itself needs a reboot.
  • Dynamic parameters take effect at once. Static parameters (innodb_log_file_size, shared_buffers on some engines, performance_schema, lower_case_table_names) wait: the instance shows pending-reboot until you reboot it, perhaps weeks later at the next unrelated failover. Check ParameterApplyStatus after every change.
  • Modifying an instance (class, storage, Multi-AZ) with apply immediately happens now, with whatever downtime it carries; without it, the change waits for the maintenance window, when RDS also applies OS and minor-version patches, each with a restart or failover.
  • Choose the window deliberately: a 30-minute slot in your quietest hour. "No preference" means AWS chooses.
  • max_connections, innodb_buffer_pool_size and shared_buffers default to formulas on instance memory; that is why a smaller instance also means fewer connections.
  • Blue/Green deployments: RDS creates a green copy fed by logical replication (binlog on MySQL, logical replication on PostgreSQL, which needs primary keys on every table), you upgrade and tune the green side, and a guarded switchover swaps the endpoints in under a minute once replication lag is zero. Supported for MySQL, PostgreSQL, MariaDB and Aurora.

Monitoring and Performance Insights

  • CloudWatch metrics every minute: CPUUtilization, FreeableMemory, SwapUsage, DatabaseConnections, ReadIOPS/WriteIOPS, ReadLatency, DiskQueueDepth, FreeStorageSpace, ReplicaLag, BurstBalance (gp2 and t classes), and on Aurora AuroraReplicaLag, VolumeBytesUsed, ServerlessDatabaseCapacity, ACUUtilization.
  • Performance Insights: samples active sessions every second and shows DB load in average active sessions (AAS), split by wait event and by SQL, user, host. The rule: when DB load exceeds the vCPU count, the instance is saturated, and the wait events say whether on CPU, I/O or locks. Seven days of history free, longer paid.
  • Enhanced Monitoring: an agent on the host reports OS metrics (per-process CPU, memory, file system, swap) every 1 to 60 seconds to CloudWatch Logs. CPUUtilization is from the hypervisor; Enhanced Monitoring shows which process uses it.
  • Engine logs (error, slow query, general, audit, PostgreSQL log) can stream to CloudWatch Logs. Turn on the slow query log with a threshold of one second from day one.
  • Events (failover, low storage, backup finished, parameter change, reboot) go to SNS and EventBridge. Subscribe your on-call channel to failover and storage events at least.
  • DevOps Guru for RDS reads Performance Insights and flags anomalies with a likely cause.

Security and access

  • Encryption at rest with KMS is chosen at creation and cannot be added later; to encrypt an unencrypted instance, snapshot, copy with a key, restore. Replicas and snapshots inherit the key. Aurora encrypts the volume, the backups and the replicas with the same key.
  • TLS in transit with the RDS certificate bundle; force it with require_secure_transport (MySQL) or rds.force_ssl (PostgreSQL). The CA certificate rotates on a schedule; a stale bundle in the client is a classic outage.
  • IAM database authentication: a 15-minute token instead of a password, for MySQL and PostgreSQL, limited to about 200 new connections per second; combine with a pool or with RDS Proxy.
  • Secrets Manager manages the master password (--manage-master-user-password) and rotates it with a Lambda; RDS Proxy reads it from there. Kerberos through AWS Managed Microsoft AD for enterprise engines.
  • Network: no public address, the DB security group allows only the application security group, and the subnet route table has no route to an internet gateway.
  • Auditing: engine audit logs (MariaDB audit plugin, pgaudit), Database Activity Streams on Aurora to Kinesis for a tamper-proof trail, CloudTrail for the control plane.

DMS and moving data

  • Database Migration Service: a replication instance (or serverless capacity) between a source endpoint and a target endpoint, running tasks of three kinds: full load, change data capture (CDC), or full load then CDC. Homogeneous (MySQL → Aurora MySQL) or heterogeneous (Oracle → PostgreSQL).
  • CDC reads the source's log: binlog on MySQL (set binlog retention hours on RDS), logical replication slots on PostgreSQL, LogMiner or Binary Reader on Oracle. A slot that is never consumed makes the source's WAL grow until the disk fills.
  • Schema Conversion (SCT, or DMS Schema Conversion in the console) translates DDL, procedures and functions between engines and reports what it could not translate; that report is the real estimate of the migration.
  • Full load copies tables in parallel with secondary indexes and constraints ideally created afterwards; LOBs need a size limit or a slow "full LOB" mode. Validation compares rows at the end.
  • For the same engine, a snapshot restore or a cross-Region replica is simpler than DMS. For near-zero downtime between engines: full load + CDC, cut over when lag is zero, keep reverse CDC for a rollback window. Day 28 walks through it.
  • Zero-ETL integrations stream Aurora and RDS MySQL tables into Redshift without DMS.

Interview questions

What actually happens, second by second, during a Multi-AZ failover?

I describe the instance deployment first, because that is what most people run. At zero the primary host, its AZ or its volume fails, or someone requested a reboot with failover. Writes stop immediately; open connections hang or get reset. Within about ten to twenty seconds the RDS health checks miss the primary and RDS writes the "failover started" event. The standby has an exact copy of the volume because replication was synchronous at block level, but its engine has never been running on it, so it must do crash recovery: replay the redo log and roll back uncommitted transactions. That takes twenty seconds to a minute, longer if there was a huge transaction in flight. When the engine opens, RDS rewrites the CNAME behind the endpoint to the standby's address; the TTL is five seconds. From that moment a client that re-resolves DNS and reconnects is fine. Total is typically sixty to a hundred and twenty seconds, with zero committed data lost. Then two things people forget. The application's own behaviour decides the real outage: a JVM caching DNS for thirty seconds or forever, a pool that never validates its connections, or no retry logic can turn a one-minute failover into a twenty-minute incident. And afterwards you have no standby: RDS builds a new one in the old AZ and synchronises it, which takes minutes to hours, so you are Single-AZ until then. For a Multi-AZ cluster the sequence is the same but faster, around thirty-five seconds, because the readers already run the engine and semi-synchronous replication means at least one has every commit. For Aurora it is around thirty seconds, with no crash recovery on the instance because the storage layer already holds every committed write; the cluster endpoint flips to the promoted replica, and RDS Proxy can hide even the DNS step.

Multi-AZ instance, Multi-AZ DB cluster, read replica: what does each give you and what does each cost?

The Multi-AZ instance deployment gives availability only: a synchronous standby that is never readable, failover of one to two minutes, no data loss, and it doubles the instance and storage bill. A read replica gives read scaling and a manual disaster-recovery path: an asynchronous copy using the engine's own replication, readable, promotable, in the same or another Region, each one a full instance, and it is as stale as its lag, which can be hours when a large transaction or a table without a primary key is being replayed. It gives no automatic failover. The Multi-AZ DB cluster is the newer option that gives both: a writer and two readable standbys in three AZs on instances with local NVMe, semi-synchronous commits so a failover loses nothing, failover under thirty-five seconds, a reader endpoint, and roughly twice the write throughput of the instance deployment. It costs three instances and exists only for MySQL and PostgreSQL. If I need readers and fast failover and the engine is MySQL or PostgreSQL, I would compare the cluster against Aurora, which gives fifteen readers with millisecond lag for a similar price.

Explain Aurora's storage layer and why it changes failover, replication and recovery.

Aurora keeps the MySQL or PostgreSQL engine but takes the storage out of the instance. The volume is a distributed service that stores every 10 GB segment as six copies across three AZs and accepts a write once four of the six acknowledge it, a read once three do. That quorum means losing a whole AZ does not stop writes, and losing an AZ plus one more copy does not lose data; damaged segments are repaired from their peers in the background. The instance sends only redo log records to storage; storage applies them and materialises pages when they are read, so the engine never writes data pages, never does a checkpoint, and generates a fraction of the I/O of MySQL on EBS. Three consequences follow. Replicas are not copies: they read the same volume, so their only lag is cache invalidation, ten to twenty milliseconds, and they never fall hours behind. Failover does not need crash recovery, because there is nothing to replay on the instance; a replica is promoted and the cluster endpoint moves, typically within thirty seconds. And backups are continuous and non-disruptive, with point-in-time restore to the second, backtrack to rewind in place, and clones that share pages copy-on-write. The costs are that Aurora exists only for those two engines, charges per I/O request on a Standard cluster, and a cluster with a single instance still has to create a new instance on failure, which takes minutes, so a replica is part of the design, not an option.

When do you put RDS Proxy in front of a database, and what is session pinning?

I use the proxy when the number of client connections is large, short-lived or unpredictable, which usually means Lambda, Fargate tasks that scale fast, or a fleet of small services each with its own pool; and when I want failover to be invisible to clients. The proxy keeps a pool of real database connections and multiplexes client connections onto them, so a thousand Lambda environments might need fifty database connections. It also reads the credentials from Secrets Manager and can accept IAM authentication, which keeps the password out of the application. On failover it keeps the client side open and reconnects to the new writer itself, without the DNS wait. Session pinning is what breaks the multiplexing: if a client does something that changes the state of its connection, such as a SET statement, a prepared statement in some drivers, a temporary table, a lock or an advisory lock, the proxy must keep that client on that one database connection for the rest of the session, because another client cannot safely reuse it. If every client pins, the proxy is a slower pass-through. I watch the pinned-sessions metric, remove session-state changes from the connection path, and use the pinning filters for the ones that are harmless. I skip the proxy for a handful of long-lived application servers with a well-configured pool; it costs per vCPU-hour and adds a hop.

After a Lambda deploy, the database fails with "too many connections". What happened, and what are three fixes?

Each Lambda execution environment opened its own connection and kept it between invocations, which is correct for a container but ruinous at scale: a burst to a thousand concurrent invocations means a thousand connections, and the instance's default max_connections, derived from its memory, is a few hundred on a small class. New connections are refused, including the ones from the rest of the application, and FreeableMemory falls because every connection holds a few megabytes. The first fix is RDS Proxy, which multiplexes those thousand clients onto as many database connections as are actually busy. The second is to cap the blast radius: reserved concurrency on the function so it cannot scale past what the database can take, and a queue in front so bursts are smoothed instead of refused. The third is to stop holding connections: close the connection at the end of each invocation if the invocation rate is low, use the Aurora Data API over HTTP, or move the work to a pool-owning service. Raising max_connections is the fix people reach for first; it works until the memory runs out, which it will. In the longer run I ask whether the access pattern is relational at all, because a key-value workload from Lambda is what DynamoDB is for.

How would you upgrade a production PostgreSQL from version 13 to 16 with minimal downtime?

With a blue/green deployment. RDS creates a green environment, a copy of the instance fed by logical replication from the blue one, and on the green side I run the major-version upgrade, change the parameter group to the new family, and maybe resize the instance, while production continues on blue. I test against green with the application in read-only mode or with a shadow copy of the traffic, including the extensions, because an extension that has no version 16 build will stop the upgrade. When replication lag is zero I switch over: RDS pauses writes, waits for the green side to catch up, checks the guardrails, renames the endpoints so the application connects to the new instance without a config change, and keeps the old blue instance with a suffix for a rollback. The pause is under a minute, typically tens of seconds. Prerequisites that bite: every table needs a primary key or a replica identity, or logical replication cannot carry updates and deletes; DDL during the deployment is not replicated; sequences and large objects need checking afterwards. Without blue/green, the in-place major upgrade takes the database down for the duration of pg_upgrade, usually ten to thirty minutes, and I would at least take a snapshot first and test the upgrade on a restored copy to time it.

A parameter group change at midnight took the database down. What probably happened?

Two scenarios, and I would check the events to tell them apart. The first: someone changed a static parameter, such as a log file size or performance schema setting, weeks ago, and it sat in pending-reboot, invisible, until an unrelated maintenance restart or failover at midnight applied it, and the new value was wrong, say a buffer pool larger than memory, so the engine failed to start. The fix is to change static parameters with a planned reboot the same day and alarm on the pending-reboot status. The second: someone modified the instance with apply-immediately, perhaps a class change or a new parameter group, which needs a restart, and did it during business hours, or without it, and the change landed in the maintenance window along with a minor-version patch. The lesson is the same both times: every change that needs a restart happens in a window I chose, on an instance that is Multi-AZ so that the restart becomes a one-minute failover, with the application's reconnection behaviour already proven in a drill. I would also look at whether the dynamic change was wrong in itself: lowering max_connections below the current count disconnects nobody but refuses newcomers, which looks like an outage to the pool that is restarting.

Design backup and recovery for a 2 TB PostgreSQL with RPO 5 minutes, RTO 1 hour, plus a regional DR with an RPO of seconds.

Inside the Region, automated backups with a retention of fourteen days give me point-in-time restore to any second, with the transaction logs uploaded every five minutes, so the RPO of a restore is at most five minutes; Multi-AZ makes the RPO zero for the ordinary failure of a host or AZ, and the failover takes a minute. For the hour of RTO I have to be honest about restores: restoring 2 TB creates a new instance in ten to twenty minutes, but it is lazy-loaded from S3, so the first hour of queries is slow, and the application must be repointed. I script the restore with the right parameter group, option group, subnet group and security groups, I warm the volume with a scan, and I run that script every quarter and record the time; that recorded time is the RTO I can promise. Manual snapshots before every risky change, and AWS Backup with a locked vault in a separate account for the ransomware case. For the regional requirement, RDS cannot give seconds: a cross-Region read replica is minutes behind and its promotion is manual. So I would move to Aurora PostgreSQL with a Global Database: storage-level replication under a second, a secondary cluster that is readable, switchover with no data loss for drills, failover with about a second lost for the real thing, and an RPO parameter that makes the primary refuse writes when lag exceeds the target. The application in the secondary Region needs its own copy of the stateless tier and a Route 53 health check or ARC routing control to move traffic; Day 24 covers that side.

Aurora Serverless v2 or provisioned, and how do you set the minimum and maximum?

Serverless v2 is right when the load is spiky or mostly idle: dev and test, internal tools, a new product with unknown traffic, a reporting cluster used in bursts, or many small tenant databases. It resizes in half-ACU steps in seconds without disconnecting anybody, and with a minimum of zero it pauses when idle and resumes on the first connection in about fifteen seconds. Provisioned is right when the load is flat and known, because a steady eight ACU costs more than the equivalent reserved instance, and because a large working set wants a fixed buffer pool. For the minimum I look at the buffer cache: a database that must answer in milliseconds the moment traffic arrives needs enough ACU to keep its hot pages resident, so I set the minimum to that and accept the cost; zero is for things that may wait fifteen seconds. For the maximum I set the budget ceiling and the point past which the application, not the database, is the bottleneck; a maximum that is too low shows up as ACUUtilization pinned at a hundred and rising latency. A useful hybrid is a provisioned writer with serverless readers, or a serverless reader at half an ACU as the failover target on a provisioned cluster, which is cheaper than a second provisioned instance and still gives a thirty-second failover.

Your read replica is thirty minutes behind. What are the causes and what do you do?

Replica lag is the apply side falling behind the primary's write rate. The classic causes: a long transaction or a bulk statement that the replica must replay as a whole; row-based replication of updates on a table without a primary key, which makes the replica scan the table for every row; a replica with less CPU, memory or IOPS than the primary; a burst-balance or credit exhaustion on the replica; and heavy read traffic on the replica competing with the apply thread. First I confirm it with the ReplicaLag metric and the engine's replica status, which tells me whether the I/O thread is behind, meaning the network, or the SQL thread, meaning apply. Then I fix the cause: add primary keys, split big transactions into batches, raise the parallel apply workers on MySQL, size the replica like the primary, move the heavy reads to another replica. While it is catching up I take it out of the read rotation if the application cannot tolerate stale data. If the lag keeps happening, I say the honest thing: a replica that replays a log will always be able to fall behind, and a workload that cannot tolerate that belongs on Aurora, where the replicas read the same volume and the lag is milliseconds by construction.

Performance Insights shows DB load of 12 on a 4 vCPU instance. How do you diagnose it?

DB load is the average number of sessions active at once, so twelve on four vCPUs means three times more work than the instance can execute: it is saturated and the question is on what. Performance Insights splits the load by wait event, and that split is the diagnosis. If most of it is CPU, the engine is executing: I look at the top SQL by load, almost always a few queries missing an index or a query plan that changed, and fix the queries or scale the instance. If it is I/O waits, such as reading data pages, the working set does not fit in the buffer cache: more memory, better indexes, or on RDS a volume that has run out of IOPS, which DiskQueueDepth will confirm. If it is lock waits, one session holds something the others want: the top SQL shows the blocker and the fix is a shorter transaction or a different access order. If it is client waits, the sessions are idle in transaction and the application is holding them open, which is a pool or code problem, not a database one. I correlate with the hour: did load jump at a deploy, a batch job, or a traffic peak, and I check Enhanced Monitoring to see whether the OS agrees. The thing not to do is scale up before reading the wait events, because a lock wait does not get better with more CPU.
