Microservices

So far one application did everything. Today you split it into small services, each owning one job, its own code and its own database. They use every building block from this week: an API Gateway in front, Lambda or containers inside, and a queue wherever one service does not need another's answer straight away.

The diagram

Full picture: the client talks only to API Gateway, which routes each path to the service that owns it. Every service is a dashed box with its own compute and its own database. When Orders needs a price it calls the Catalog service's API; reading Catalog's database directly is forbidden. Confirmation emails are not urgent, so Orders drops a message on a queue and the Notifications service handles it later.

Concepts

What a microservice is

A small application that does one business job and can be changed and released by itself.

  • Owned by one team, with its own code and release schedule.
  • Reached only through its API or its messages.
  • Free to use whatever fits: here one service is Lambda with DynamoDB, another is containers with a relational database.
  • Scales alone: a busy Users service does not force Orders to grow.

One database per service

The rule that makes the rest possible. A service's data is private to it.

  • Independent change: a team can alter its tables without asking anyone.
  • Failure isolation: one overloaded database slows one service, not all.
  • Right tool: key-value for one, relational for another.
  • If two services share tables, they are really one application deployed in two pieces, with all the coupling and none of the simplicity.

Synchronous or asynchronous

Two ways for services to talk, with very different failure behaviour.

  • Synchronous: an API call; the caller waits for the answer. If the other service is down, so is the caller's feature.
  • Asynchronous: a message on a queue or an event; the caller carries on. The other service can be down for an hour.
  • Use synchronous only when the answer is needed now. Everything else goes on a queue.

The API Gateway's job

Clients should not know how many services exist or where they are.

  • One address for everything; paths decide the service.
  • Authentication and throttling done once, not in every service.
  • You can split, merge or move services behind it without changing the client.
  • Services that only consume messages, like Notifications, are not exposed at all.

What you give up

Separate databases remove two things a single database gives you for free.

  • No joins across services. “Orders with customer names” cannot be one query. Either the Orders service asks the Users service, or it keeps its own copy of the few fields it needs, or reports are built in a separate analytics store fed by events (Day 27).
  • No transaction across services. “Create the order and reduce the stock” cannot be one atomic step. Each service commits its own part, and if a later step fails, earlier ones are undone by compensating actions. This is the saga pattern, and the result is eventual consistency.
  • More moving parts. A request may cross several services, so you need tracing and central logs to find where it went wrong (Day 26).

Monolith or microservices?

Monolith (Day 10)Microservices (today)
DeploymentThe whole application at onceEach service by itself
ScalingAll of it togetherOnly the busy service
A failureCan take everything downContained, if calls are asynchronous
DataOne database, joins and transactionsOne per service, eventual consistency

Microservices solve an organisational problem: many teams stepping on each other in one codebase. A small team usually moves faster with a well-structured monolith, and can split it later.

Check yourself

Why one database per service?

So each service can change, scale and fail independently. With a shared database, a schema change by one team breaks another, one heavy query slows everyone, and no service can be released alone. Private data is what makes the services truly separate.

The Orders service needs a product's price. How does it get it?

By calling the Catalog service's API, or by keeping its own copy of prices that it updates from Catalog's events. Never by querying the catalog database.

Catalog is down and now nobody can place an order. What went wrong in the design, and how do you soften it?

Orders depends on Catalog synchronously, so Catalog's outage became Orders' outage. Soften it with a short timeout and a fallback, a cached or locally copied price, or by receiving price changes as events so no live call is needed.

Notifications is down for an hour. What do customers experience?

Ordering works normally. Messages wait in the queue, and the emails go out when the service returns. That is the benefit of the asynchronous path.

Management wants a report joining orders with customer details. Where does it run?

Not against the services' databases. Services publish events, and a separate analytics store collects them for reporting. Day 27 builds that pipeline.

An order must reserve stock, take payment and create the order record. One fails halfway. What now?

There is no cross-service transaction to roll back. Use a saga: each step has a compensating action, such as releasing the stock, which runs if a later step fails. Step Functions is a common way to orchestrate it.

Why may the Users service use Lambda while Orders uses containers?

Each service is independent, so each team picks what suits its workload. Other services see only the API, not what runs behind it.

A four-person startup is building its first product. Microservices?

Usually not. They would pay the cost of many deployments, networks and databases without having the problem microservices solve, which is many teams in one codebase. Start with a clean monolith.
