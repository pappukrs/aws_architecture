Security Architecture

Security is not one product. It is several independent layers, so that whatever gets past one is stopped by the next. Today you take the web application from Week 2 and add six layers to the same drawing: protection at the edge, the network you already built, identity, encryption, secrets, and detection.

The diagram

Full picture: six layers on one application. 1 Shield and WAF filter traffic at the edge. 2 Private subnets and chained security groups limit who can reach what. 3 An IAM role gives the servers only the permissions they need. 4 Everything stored is encrypted with a KMS key, and every hop uses TLS. 5 The database password lives in Secrets Manager, not in the code. 6 GuardDuty watches the logs for anything that got through.

Concepts

Shield and WAF

  • Shield protects against DDoS, floods of traffic meant to overwhelm you. Shield Standard is automatic and free; Shield Advanced adds more protection and a response team.
  • WAF, web application firewall, inspects each HTTP request: SQL injection, cross-site scripting, bad bots, too many requests from one address.
  • Both attach to CloudFront, a load balancer or API Gateway. At CloudFront, bad traffic is dropped before it reaches your Region.
  • A security group filters by port and address; WAF filters by what the request says.

IAM roles

How one AWS service gets permission to call another, with no passwords or keys.

  • The role is attached to the servers; AWS gives them short-lived credentials that renew themselves.
  • Least privilege: name the exact actions and the exact resources.
  • Never put access keys in code or config files. Stolen keys work from anywhere; a role works only on that server.

KMS

Key Management Service creates and guards encryption keys. Other services use them to encrypt what they store.

  • The key never leaves KMS. Services ask KMS to encrypt or decrypt.
  • Access to data now needs two permissions: to the data and to the key.
  • Every use of a key is logged in CloudTrail.
  • A stolen snapshot or disk is useless without access to the key.

Secrets Manager and GuardDuty

  • Secrets Manager stores passwords and API keys, encrypted. The app fetches the database password at start-up using its role. It can rotate the password automatically, so a leaked one soon stops working.
  • GuardDuty is threat detection. It needs nothing installed: it analyses VPC flow logs, DNS queries and CloudTrail for known bad patterns.
  • GuardDuty only reports. An EventBridge rule turns a finding into an alert or an automatic response, such as isolating an instance.

Who is responsible for what

AWS calls this the shared responsibility model.

  • AWS secures the cloud itself: buildings, hardware, the network, and the software that runs managed services.
  • You secure what you put in it: who has access (IAM), how the network is opened (security groups), whether data is encrypted, and your own application code.
  • The more managed the service, the less is yours: on EC2 you patch the operating system; on Lambda or RDS, AWS does.

Check yourself

Where is data encrypted in transit and at rest in this design?

In transit: TLS on every hop, from the user to CloudFront, CloudFront to the load balancer, on to the app servers, from them to the database, and to every AWS API. At rest: the RDS storage with its snapshots, the S3 objects, the servers' volumes and the secret itself, all with a KMS key.

What is the difference between Shield and WAF?

Shield deals with volume: DDoS floods that try to exhaust your capacity. WAF deals with content: individual requests that are malicious, such as SQL injection. A site usually needs both.

The database already has a security group. Why add WAF?

They work at different levels. The security group only checks that traffic comes from the app tier on the right port. A SQL injection arrives as a perfectly normal HTTPS request through the front door; only WAF reads the request and sees the attack.

Why an IAM role on the servers instead of access keys in a config file?

Keys in a file can be copied, committed to Git or left in a backup, and they work from anywhere until someone rotates them. A role's credentials are temporary, renewed automatically, and never stored by you.

An attacker takes over one app server. What can they reach?

Only what app-role allows: one secret, one bucket, one key, and the database through db-sg. They cannot list other buckets, create users or touch other systems. Least privilege limits the damage; GuardDuty should then notice the unusual behaviour.

An RDS snapshot is shared with the wrong AWS account by mistake. Is the data exposed?

Not if it is encrypted with your own KMS key. The other account can see the snapshot but cannot restore it without permission to use the key, which is a separate grant.

Does GuardDuty block attacks?

No. It detects and reports. To act, send its findings through EventBridge to a notification or to a Lambda function that responds, for example by swapping the instance's security group for one that allows nothing.

A developer needs the database password to run a migration. How should they get it?

From Secrets Manager, through an IAM permission granted to them for that secret, with the access logged in CloudTrail. Not from a chat message, a wiki page or the source code. Rotation then makes any copy they kept useless.
