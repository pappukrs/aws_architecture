Kubernetes on EKS

Kubernetes is the container orchestrator most of the industry uses, and it works the same on every cloud. On AWS you run it with EKS: AWS operates the control plane, the brain of the cluster, and you bring the worker nodes that run your containers. The drawing is yesterday's, with one new box that is not yours and one new layer inside the nodes.

The diagram

Full picture: the control plane is run by AWS outside your VPC. The engineer tells it the desired state with kubectl. Its scheduler places pods on worker nodes, which are EC2 instances in a managed node group in your private subnets. An Ingress object makes a controller create the load balancer, which sends requests straight to pod IP addresses.

Concepts

Control plane

The brain of a Kubernetes cluster. With EKS, AWS runs it for you.

  • API server: the one door everything talks to, including kubectl.
  • etcd: the database holding the desired and actual state.
  • Scheduler and controllers: decide which node gets each pod, and keep correcting drift.
  • It runs across three AZs in an AWS-owned account. You pay a flat hourly fee per cluster and never see the servers.

Worker nodes

The machines your containers actually run on. These are in your VPC and on your bill.

  • Managed node group: EC2 instances in an Auto Scaling group that EKS creates and updates for you.
  • Fargate: no nodes at all; each pod runs on capacity AWS finds, as on Day 18.
  • Nodes go in private subnets across at least two AZs.

Pod, Deployment, Service, Ingress

  • Pod: the smallest unit, one or more containers with one IP address.
  • Deployment: “keep N copies of this pod running”, with rolling updates.
  • Service: one stable name in front of a changing set of pods.
  • Ingress: HTTP routing from outside. On EKS, the AWS Load Balancer Controller reads it and creates a real Application Load Balancer.

Networking and permissions

  • Every pod gets a real IP address from your subnet. A /24 runs out quickly; EKS subnets are usually much larger.
  • The load balancer can therefore target pod IPs directly.
  • A pod gets AWS permissions through an IAM role tied to its service account, the same idea as yesterday's task role.
  • Nodes still need the NAT Gateway or VPC endpoints to pull images.

Check yourself

What does AWS manage in EKS, and what do you manage?

AWS runs the control plane: API server, etcd, scheduler and controllers, across three AZs, patched and backed up. With managed node groups it also provisions and replaces the worker nodes. You manage what runs on the cluster, the add-ons, when to upgrade, and the VPC and IAM around it. You pay for the nodes.

Where is the control plane on the diagram, and why there?

Outside your VPC. It runs in an AWS-owned account and reaches your nodes through network interfaces placed in your subnets. Drawing it inside your VPC is a common mistake.

You delete a pod by hand. Thirty seconds later there are still four. Why?

The Deployment says four replicas. Its controller noticed three running and created a replacement. To have fewer pods you change the desired number, not the pods.

A worker node dies. What happens to its pods, and what happens to the node?

Kubernetes reschedules the pods onto remaining nodes that have room; any that do not fit wait as Pending. Separately, the node group's Auto Scaling group launches a replacement node, and the pending pods are placed on it.

After the failed node is replaced, one node has four pods and the new one has none. Is something broken?

No. Kubernetes does not move healthy running pods to rebalance. The new node fills up as pods are created later, for example at the next deployment.

Why do EKS clusters need larger subnets than the /24s used so far?

Each pod takes a real IP address from the subnet. A few dozen nodes with tens of pods each can exhaust the 251 addresses of a /24, and then new pods cannot start.

You wrote an Ingress object and a load balancer appeared in the AWS console. What created it?

The AWS Load Balancer Controller, an add-on running in the cluster. It watches Ingress objects and creates and configures a matching Application Load Balancer.

A three-person team with no Kubernetes experience needs to run six containers. ECS or EKS?

ECS on Fargate. It does the job with far less to learn and maintain. EKS earns its complexity when you need the Kubernetes ecosystem, portability, or the team already has the skills.
