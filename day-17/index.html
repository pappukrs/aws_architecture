Event-Driven Processing

Yesterday your code sent messages on purpose. Today things simply happen — a file is uploaded, a server stops, the clock reaches two in the morning — and AWS turns each of those into an event that starts your code. Nothing polls and nothing waits. You draw two versions: a service that raises its own events, and EventBridge, which routes any event by rule.

The diagram

Two ways to react to events. Top: S3 raises an event for every uploaded file and invokes a Lambda function directly; the function writes a thumbnail and a database record. Bottom: many kinds of events arrive on an EventBridge bus. Each rule describes the events it wants and sends matching ones to its target. An event that matches no rule is simply dropped.

Concepts

  

    

      
Event

      
A small JSON record saying that something happened: who raised it, what kind it is, and the details.

      
    
        
  • The producer does not know or care who is listening.
    • 
        
  • Consumers are added later without touching the producer.
    • 
        
  • Nothing runs until an event arrives, so idle cost is zero.
    • 
      

    

    

      
S3 event notifications

      
A bucket can announce changes: object created, object removed.

      
    
        
  • Targets: a Lambda function, an SQS queue, an SNS topic, or EventBridge.
    • 
        
  • Filter by prefix or suffix, such as only .jpg files.
    • 
        
  • The function is invoked asynchronously: S3 does not wait, and Lambda retries twice on failure.
    • 
        
  • Never write the output back to the same bucket and prefix. Each output would raise a new event: an endless, expensive loop.
    • 
      

    

    

      
EventBridge

      
A central event router: an event bus that receives events, and rules that pick out the ones to forward.

      
    
        
  • Sources: most AWS services automatically, your own applications, and outside SaaS products.
    • 
        
  • Rules match on the content of the event: any field, numbers, prefixes.
    • 
        
  • Targets: Lambda, SQS, SNS, Step Functions and many more, up to five per rule.
    • 
        
  • It can also keep an archive of events and replay them later.
    • 
      

    

    

      
Schedules

      
EventBridge can raise an event at a set time, replacing a server that exists only to run cron jobs.

      
    
        
  • rate(5 minutes) or a cron expression.
    • 
        
  • The target is usually a Lambda function.
    • 
        
  • Nightly reports, clean-up jobs, stopping test servers after office hours.
    • 
      

    

  


  
EventBridge or SNS?

  

    

      
EventBridgeSNS

      
FilteringOn any field inside the eventOn message attributes, simpler

      
Event sourcesAWS services and SaaS products built in, plus your ownWhatever you publish yourself

      
TargetsMany AWS services directlySQS, Lambda, HTTP, email, SMS, mobile push

      
SubscribersFive targets per ruleMillions per topic

      
Speed and volumeAbout half a second, moderate throughputFaster, very high throughput

      
ExtrasSchedules, archive and replayMessages to people: email and SMS

    

    
Choose EventBridge when many kinds of events must be routed by their content, when you react to events from AWS services, or when you need a schedule. Choose SNS for simple, high-volume fan-out of one kind of message, or to notify people.

Check yourself

  
When would you use EventBridge instead of SNS?
When events of many kinds must be routed by what they contain, when the events come from AWS services or SaaS products, or when you need schedules or replay. SNS suits simple, very high-volume fan-out of one message type and notifying people.

  
The thumbnail function saves its output into the uploads bucket. What happens?
The saved thumbnail is itself a new object, so it raises another event, which makes another thumbnail, without end. Use a separate bucket, or at least a prefix the trigger does not watch.

  
An order of ₹200 arrives on the bus and matches no rule. Is that an error?
No. The event is discarded quietly. A bus is not a queue: nothing is stored for later unless you turn on an archive.

  
The thumbnail function throws an error on one photo. What happens to that event?
The invocation is asynchronous, so Lambda retries it twice. If it still fails, the event goes to a dead-letter queue or failure destination if you configured one, and is lost if you did not.

  
You must run a clean-up script every night. What is the serverless way?
An EventBridge schedule with a Lambda function as its target. No server sits idle for the other 23 hours and 59 minutes.

  
Ten thousand photos are uploaded in one minute. What does this design do, and what might you add?
S3 raises ten thousand events and Lambda runs many copies at once, up to the concurrency limit. To smooth the load or protect something downstream, put an SQS queue between the bucket and the function.

  
You want a message whenever any EC2 instance in the account stops, without installing anything on the instances. How?
EC2 already sends state-change events to the default event bus. Add a rule matching source = aws.ec2 and state = stopped, with an SNS topic as the target.

  
How is today's design different from yesterday's queue?
A queue stores work until a consumer pulls it, so nothing is lost while the consumer is away. An event is pushed once to whoever is listening now. Many designs use both: the event arrives, and its target is a queue.
