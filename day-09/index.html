Auto Scaling

Yesterday's load balancer could skip a broken server but not replace it, and could not add servers when traffic grew. Today an Auto Scaling group takes over the servers: it launches them from a template, keeps the right number running across both zones, and replaces any that fail.

Concepts

Auto Scaling group (ASG)

A group of identical instances that AWS keeps at the size you ask for.

  • You give it subnets in several AZs; it spreads instances evenly across them.
  • It registers each new instance with the load balancer's target group, and deregisters it before termination.
  • It replaces any instance that fails a health check.
  • The group itself is free; you pay for the instances.

Min, desired, max

  • Min (2): never fewer, even at 3 a.m. Two keeps one in each AZ.
  • Max (6): never more, whatever the load. This caps your bill.
  • Desired: how many should be running right now. Scaling policies move it between min and max; the group then launches or terminates to match.

Launch template

The recipe for a new instance, so no human is needed when one is launched.

  • AMI (the disk image), instance type, security group, IAM role, key pair.
  • User data: a script that runs at first boot to install or start the application.
  • Templates are versioned; roll out a new version to update the fleet.

Scale out and scale in

  • Scale out: add instances. Triggered when the metric is above the target, for example CPU over 50%.
  • Scale in: remove instances. Triggered when the metric stays well below the target.
  • Scale-out is fast; scale-in is deliberately slow, to avoid adding and removing servers every minute.
  • Scaling up is different: a bigger instance, not more instances.

One rule this design forces on you

Servers must be stateless. Any instance can be terminated at any moment, by scale-in or by a failure. Anything stored only on that instance is lost.

  • User sessions go in a shared store such as ElastiCache or DynamoDB (Day 11).
  • Uploaded files go to S3 (Day 12).
  • Data goes in a database outside the group (Day 10).

Check yourself

What triggers scale-out and what triggers scale-in?

Scale-out: the tracked metric rises above the target, for example average CPU above 50%, and a CloudWatch alarm fires. Scale-in: the metric stays well below the target for a longer period. In both cases the policy changes the desired capacity and the group launches or terminates instances to match.

An instance crashes. Desired capacity is 4. What happens?

The group sees 3 healthy instances but wants 4, so it launches a replacement from the launch template, in the AZ that is now short. No alarm or scaling policy is involved; this is the group maintaining its size.

An instance is running but its application has hung. Will the group replace it?

Only if the group uses the load balancer's health check. By default it checks only that the instance is running. Turn on the ELB health check so that a target the load balancer marks unhealthy is replaced.

AZ a fails completely. Desired capacity is 4, two in each AZ. What does the group do?

It launches two replacements in AZ b, so four are running again. When AZ a returns, it rebalances the instances across both zones.

The group is at max (6) and CPU is still 90%. What happens next?

Nothing. The group never exceeds max. Users get slower responses until load drops, or until you raise max or use a larger instance type in the template.

Why set min to 2 and not 1?

With one instance, a failure of that instance or its AZ means zero capacity until a replacement boots. Two, one per AZ, keeps the site up through either failure.

A user uploads a profile picture and it is saved on the instance's disk. What goes wrong?

Their next request may hit a different instance that does not have the file, and the file disappears for good when that instance is scaled in. Store uploads in S3.

New instances take four minutes to start serving. How does that change the design?

Scaling reacts too late for sudden spikes. Shorten boot time with a pre-built AMI, keep more spare capacity with a lower target, or add scheduled or predictive scaling for known peaks.
