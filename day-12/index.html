Day 12 of 30 · Week 2 — Compute, Load Balancing, High Availability

Static Website

A completely different shape today: no VPC, no subnets, no servers. The files of a website sit in a private S3 bucket, CloudFront delivers them from an edge location near each user, and ACM supplies the HTTPS certificate. It costs almost nothing and scales to any traffic.

The diagram

Full picture: a user's browser connects over HTTPS to the nearest CloudFront edge location (1). If the edge already has the file, it answers at once. If not, it fetches the file from the private S3 bucket (2), keeps a copy, and answers. The bucket policy lets only this distribution read it, so going to the bucket directly is denied.

Concepts

Amazon S3

Object storage: you put files (objects) into a bucket and get them back by name. There is no server to manage and no size to plan.

  • A bucket lives in one Region; AWS stores every object across several AZs.
  • Buckets are private by default, and Block Public Access keeps them that way.
  • A static website is just files: HTML, CSS, JavaScript, images. S3 can hold them; it cannot run code.

CloudFront

A content delivery network. It keeps copies of your files at the edge locations from Day 1 and serves each user from the closest one.

  • Distribution: your configuration: origin, domain name, certificate, cache rules.
  • Origin: where the real files live. Here, the S3 bucket.
  • TTL: how long an edge keeps a file before asking the origin again.
  • It is a global service: draw it outside every Region box.

Origin access control (OAC)

The link that lets CloudFront, and nobody else, read a private bucket.

  • CloudFront signs every request it sends to S3.
  • The bucket policy allows s3:GetObject only for the CloudFront service acting for your distribution.
  • Any other request, including a direct link to the bucket, gets 403.
  • OAC replaces the older origin access identity (OAI) you will still see in old diagrams.

ACM certificate

AWS Certificate Manager issues the TLS certificate that makes https://www.example.com work.

  • Public certificates are free and renew themselves.
  • For CloudFront the certificate must be requested in us-east-1, whatever Region your bucket is in. This is a favourite exam question.
  • CloudFront then redirects HTTP to HTTPS for every visitor.

Updating the site

After you upload a new file, edges that already cached the old one keep serving it until its TTL runs out. Two ways to deal with that:

  • Invalidation: tell CloudFront to drop cached paths such as /*. Simple, takes a minute or two, and large numbers of paths are charged.
  • Versioned file names: name files app.3f2a1c.js, so a new build is a new name that no edge has cached. Then only index.html needs a short TTL. This is the better habit.

Check yourself

Why keep the bucket private behind CloudFront?

So there is exactly one way in. Every visitor then gets HTTPS, caching, and whatever protection sits on CloudFront, and nobody can bypass it by going to the bucket. It also keeps Block Public Access on, which removes the most common cause of S3 data leaks.

Your bucket is in Mumbai. In which Region do you request the certificate for CloudFront?

us-east-1 (N. Virginia). CloudFront is a global service and reads its certificates only from there. The bucket's Region does not matter.

A user in Delhi loaded the page a minute ago. A user in London now loads it for the first time. Hit or miss?

Miss. Each edge location has its own cache. London's edge fetches the file from S3, and after that London users get hits too.

You uploaded a new index.html but visitors still see the old page. Why?

The edges cached the old file and its TTL has not expired. Create an invalidation for the path, or use a short TTL on index.html and versioned names for everything else.

Where do you draw CloudFront on a diagram, and where S3?

CloudFront outside every Region box, since it is global. S3 inside a Region box but not inside a VPC or subnet; it is a regional service, not something in your network.

Someone copies the bucket's own URL for app.js and opens it. What happens?

403 Access Denied. The bucket policy allows only requests signed by CloudFront for your distribution.

The site needs a contact form that saves messages. Can this architecture do it?

Not by itself. S3 only serves files; it runs no code. The form would call an API, such as API Gateway with Lambda, which is Day 15. The static site plus an API is Day 21.

A page goes viral and gets a hundred times the normal traffic. What do you have to do?

Nothing. There are no servers to scale. Almost all requests are cache hits at the edges, and S3 and CloudFront absorb the rest. You pay for the extra data delivered.
