Decoupling with Queues

When one service calls another directly, the slow one slows both and the broken one breaks both. Today you put a queue between them. The sender drops a message and moves on; the receiver works through messages at its own pace. Then you add a topic so one event can feed several queues at once.

The diagram

Full picture: the order service publishes one message to an SNS topic and immediately returns to the customer. SNS pushes a copy into each subscribed SQS queue. Each consumer polls its own queue and works at its own speed. A payment message that fails three times is moved to the dead-letter queue instead of blocking the others.

Concepts

Why decouple

Without a queue, the order service calls the payment service and waits.

  • Failure spreads: payments down means orders down.
  • Spikes hurt: both sides must be sized for the peak.
  • The user waits for work that could happen later.

With a queue, the order is accepted the moment the message is stored. The queue is a buffer that soaks up spikes and outages.

SQS: a queue

Simple Queue Service stores messages until a consumer takes them.

  • Consumers pull: they ask the queue for messages.
  • Each message is handled by one consumer, then deleted.
  • Messages are kept up to 14 days, so a consumer can be down for hours.
  • Standard queues are fastest; FIFO queues keep strict order.

SNS: a topic

Simple Notification Service delivers each published message to every subscriber.

  • It pushes: subscribers do not ask, they are sent a copy.
  • Subscribers can be SQS queues, Lambda functions, HTTP endpoints, email or SMS.
  • It does not store messages. A subscriber that is down misses them, which is why you subscribe a queue rather than the worker itself.

Dead-letter queue (DLQ)

A second queue for messages that keep failing.

  • You set a limit, such as three receives. Past it, SQS moves the message to the DLQ.
  • One bad message, a “poison pill”, cannot block the queue forever.
  • Put an alarm on the DLQ: anything in it needs a human to look.
  • After fixing the bug, you can send the messages back to be retried.

The life of one message

  1. A worker receives the message. It is not removed; it becomes invisible to other workers for the visibility timeout, 30 seconds by default.
  2. The worker processes it.
  3. On success the worker deletes it. Only now is it gone.
  4. If the worker crashes first, the timeout runs out, the message becomes visible again, and another worker picks it up.

So no message is lost when a worker dies, but a message can be delivered more than once. This is called at-least-once delivery. Workers must be idempotent: handling the same message twice must not charge the customer twice.

Together they make the fan-out pattern in the diagram: SNS announces, and a queue per consumer makes sure each one eventually gets every message. Adding a new consumer means adding a queue and a subscription; the order service does not change.

Check yourself

SQS and SNS: which is pull and which is push?

SQS is pull: a consumer asks the queue for messages and one consumer handles each. SNS is push: the topic sends a copy of every message to all its subscribers.

The payment workers are down for an hour. What does a customer placing an order see?

Nothing unusual. The order service publishes the message and returns. The message waits in the payments queue and is processed when the workers return. The confirmation email is still sent, since that queue is independent.

Why subscribe a queue to the topic instead of subscribing the worker directly?

SNS does not store messages. If the worker is down or slow when the push arrives, the message is lost after a few retries. A queue holds it until the worker is ready.

A worker crashes halfway through a message. Is the message lost?

No. It was never deleted, only hidden. When the visibility timeout ends it becomes visible again and another worker receives it.

How could a customer be charged twice, and how do you prevent it?

A worker finishes the payment but crashes before deleting the message, so the message is delivered again. Make the worker idempotent: record the order ID once processed and skip any message whose ID is already recorded.

The fraud team wants a copy of every order. What changes?

Create a new queue, subscribe it to the topic, and let the fraud service poll it. The order service and the other consumers are untouched.

The payments queue grows to 50,000 messages during a sale. What should happen automatically?

The Auto Scaling group should scale out on queue depth, the number of visible messages per worker, and scale back in when the queue drains. CPU is the wrong signal for queue workers.

What does the customer lose in exchange for all this resilience?

An immediate answer. The order is accepted before payment is confirmed, so the result arrives later, by email or a status page. Asynchronous designs trade instant certainty for availability.
